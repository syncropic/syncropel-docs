## Overview

Every workspace eventually needs credentials: API keys for model providers, database passwords, webhook signing secrets, OAuth tokens. Syncropel lets your work depend on these values without ever putting them in your records.

The rule is simple: **records hold handles, backends hold values**. A record can name a credential, such as "the production model key", without containing the key itself. The value lives in your operating system's keychain or in an environment variable. When something needs the value, it asks for the handle, Syncropel fetches the value from where it is stored, and hands it straight to the caller. The value never enters your records.

A record must never contain a plaintext secret value. Syncropel enforces this in four separate places, so a gap in one still leaves the other three in force.

## Why records never hold values

Records are widely read. Screens show them, paired workspaces copy them, and rules read every field. A credential written into a record would be exposed to every one of those readers. Keeping values out of records entirely removes that risk.

## How secrets are protected

1. **Records with secret fields are refused.** When a record arrives, Syncropel checks that fields marked sensitive do not carry a plaintext value. Credential descriptors and the audit records below hold only a handle and a storage location, never the value.
2. **Secret values cannot be written out by accident.** Inside Syncropel, secret values are wrapped so they cannot be saved to a record or printed in a log.
3. **Logs are scrubbed.** Anything that looks like an API key, token or password is replaced with a marker such as `<redacted:48-chars>` before it is written to a log. This covers common model-provider keys, GitHub tokens, JWTs, Bearer tokens and AWS access keys. The scrubbing errs on the side of hiding too much: a slightly mangled log line is better than a leaked key.
4. **Sensitive fields are hidden when read.** Where a record carries a field that only some members may see, other members see it masked, wherever they read it.

## Credential records

When you tell Syncropel about a credential, you emit a `core.credential.v1` record:

```json
{
  "kind": "core.credential.v1",
  "handle": "anthropic-prod",
  "backend_ref": "keychain://syncropel/anthropic-prod",
  "publisher_did": "did:sync:user:alice",
  "lifecycle": "active"
}
```

That is the whole record. There is no field for a value. The `handle` is the readable name, `backend_ref` points at where the value lives, `publisher_did` records who created it, and `lifecycle` is one of `active`, `rotated`, `invalidated` or `erased`.

When something needs the value, it asks by handle. Syncropel finds where the value is stored, fetches it, returns it to the caller, and writes an audit record of the access first. The value never enters a record.

## The `spl secret` CLI

Manage credentials with these commands:

```bash
spl secret set anthropic-prod          # reads the value from the terminal (hidden) or stdin
spl secret get anthropic-prod          # returns metadata (no value)
spl secret get anthropic-prod --reveal # returns value to stderr with a warning
spl secret list                        # all known handles
spl secret promote ANTHROPIC_API_KEY   # moves an environment variable into the OS keychain
spl secret delete anthropic-prod       # removes the credential and records the deletion
```

Two rules apply to every command:

1. **Values are never command arguments.** `set` reads the value from the terminal (with typing hidden) or from piped input. There is no `--value` flag, so the value never shows up in a process list.
2. **Every operation is audited first.** An audit record is written before you see the result.

## Where values live

Four storage backends are built in:

- **macOS Keychain**: service `syncropel`, account = handle.
- **Linux Secret Service**: through libsecret.
- **Windows Credential Manager**.
- **`env://VAR`**: read-only env-var resolver. Works on every platform, useful for CI and containers.

These run inside your workspace.

## What is audited

Every `set`, `get`, `list`, `delete` and `promote` writes an access record to a dedicated audit thread, `th_secret_audit`. It names the credential, who asked, why, and whether the request was allowed, denied, or failed because the backend was unavailable. Two more records are written when a credential's value is replaced (`secret.rotation.v1`) or wiped without a replacement (`secret.value_invalidated.v1`).

The audit thread is an ordinary thread, so you can query it like any other and use it as evidence of access for compliance reviews.

## Known limits

Secrets stay inside your workspace and are stored only in the backends listed above. Third-party secret managers and sharing credentials between paired workspaces are not supported.
