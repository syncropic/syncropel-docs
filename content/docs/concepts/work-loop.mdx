title: Work loops

## Overview

A **work loop** is what you get when you stop treating "an actor doing goal-structured work" as an opaque process and start treating it as a sequence of records on a thread.

The actor doing the work can be an LLM agent, a human driving a UI, a workflow, or any other automation — the loop primitive is the same. Every turn it takes, every tool it calls, every result it gets, every judgement made about its work, are all records on the loop's thread. You can subscribe to them, query against them, fold them, and audit them with the same tools you use for every other Syncropel record. There is no separate "agent log" to scrape.

```
loop opens on a new thread
  │
  ├─ turn 1: core.work.turn.v1
  │   ├─ tool call: core.work.tool_call.v1
  │   └─ tool result: core.work.tool_result.v1
  │
  ├─ turn 2: core.work.turn.v1
  │   └─ ...
  │
  ├─ (optional) judgement: core.work.turn_judgment.v1
  └─ outcome: core.work.loop_outcome.v1   ← kernel-locked verdict
```

The loop runs in one of two modes:

- **In-process** — the loop runs in the same process that started it (`spl work-loop "..."` does this by default). Workspace tools have direct host access — `bash`, file reads, file writes — confined to a workspace directory.
- **Remote** — the loop runs on the daemon (`spl work-loop ... --remote`, or any `POST /v1/work/loop` call). Tools are substrate-native (no host shell); records land in the substrate and the thread is watchable from anywhere.

## Why "records-native"

Other agent frameworks treat the loop as the source of truth and emit telemetry on the side. Syncropel inverts this: the records *are* the truth. The loop is a managed task whose state is derived from the records on its thread.

The consequence is that everything follows from existing Syncropel primitives:

- **Pause + resume** is free — pause is just halting the runner; resume is re-reading the thread and continuing.
- **Multi-actor visibility** is free — anyone on the loop's thread sees its records.
- **Federation** is free — a peer pulling the thread gets the whole loop.
- **Cancel** is a record (`core.work.loop_cancel.v1` `DO`) that the runtime propagates — no out-of-band shutdown signal.
- **Trust** flows naturally through the record's `actor` field — the loop runs under a real DID (the user's DID, in the chat-actor delegation case), and trust accumulates on that DID, not on an opaque "agent" process.

## The four components

```
goal
 │
 ▼
┌─────────────┐     ┌──────────────────┐
│   Planner   │ ──▶ │  Tool registry   │ ◀── permission checks (CEL)
└─────────────┘     └──────────────────┘
       │                    ▲
       │                    │ tool calls
       ▼                    │
┌─────────────┐             │
│   Driver    │ ────────────┘
│  (the loop) │
└─────────────┘
       │
       │ context via curated projection
       ▼
┌─────────────┐
│  Evaluator  │ ──▶ verdict — the loop never self-asserts "done"
└─────────────┘
       │
       ▼
   outcome record
```

1. **The driver** is the loop itself — read context, call the model, dispatch tool calls, write results, repeat. It does not decide when to stop.
2. **The tool registry** is the set of tools the loop can call. Each tool is permission-checked through the kernel before it runs; tool calls and results are records.
3. **The Evaluator pair** (active in `verify` mode) is independent: a planner expands the goal into success criteria at turn 0, and an evaluator judges the result before the loop completes. The driver and the evaluator can never be the same process — that is what "kernel-locked" means.
4. **Curated projection** assembles context for each turn. The driver does not fold the whole thread; it folds a *projection* that selectively surfaces the records the current turn needs.

## Verify mode and the Evaluator contract

The most important constraint: **a loop never decides it is done**. An independent Evaluator does.

In verify mode (`verification: "evaluator"` — forced on for Trial-tier actors, opt-in for everyone else):

- At turn 0 a **planner** reads the goal and emits `core.work.plan.v1` plus `core.work.criteria.v1` — the success criteria the result will be checked against.
- The loop runs as normal.
- After what the loop *thinks* is the last turn, a separate **evaluator** judges the result against those criteria and emits `core.work.evaluation.v1`.
- Only the evaluator's verdict closes the loop. The outcome record (`core.work.loop_outcome.v1`) carries `verdict: "success"` only when the evaluator says so — never on the loop's say-so.

This closes the well-documented failure mode where models confidently rate mediocre work as complete. The trust signal the rest of the system feeds on now has an honest input.

## Outcomes

Every loop ends with a `core.work.loop_outcome.v1` record. The `outcome` field is one of five values, and any non-success outcome carries enough structure for a reader to know exactly what happened:

| Outcome | `success` | What it means |
|---|---|---|
| `completed` | `true` or `false` | The loop ran to completion. In verify mode, `success: true` is the evaluator's verdict; `success: false` means the loop ran but did not meet the goal. Without verify mode, `success` reflects whether the loop produced a non-empty result. |
| `blocked` | `false` | The loop halted because it could not proceed. A paired `core.work.coercion.v1` record carries the structured reason. |
| `cancelled` | `false` | Someone explicitly cancelled the loop while it was running. |
| `timeout` | `false` | The loop hit its wall-clock or token budget before finishing. |
| `failed` | `false` | The loop crashed unrecoverably — an upstream or infrastructure error, not an agent decision. |

The `blocked` outcome is the most important one to understand, because it is how a well-behaved loop reports an honest "I can't do this" rather than producing noise.

### Coercion reasons

A `blocked` outcome is always paired with a `core.work.coercion.v1` record whose `reason` field is one of:

| Reason | What happened |
|---|---|
| `tool_unavailable` | The loop identified a tool it would need to make progress, but the tool is not in its grant. If the tool is in the actor's *requestable* set, the loop can escalate via a decision request. |
| `ambiguous_goal` | The goal has more than one reasonable interpretation. The loop surfaces the alternatives rather than picking one silently. |
| `precondition_failed` | A goal assumed something that turned out not to hold — for example, "summarise the records on this thread" when the thread is empty. |
| `decision_required` | The loop reached a fork that needs a human call. A `core.work.decision_request.v1` is emitted; the loop blocks until you respond. |
| `input_invalid` | A goal parameter could not be parsed into something concrete — an unparseable date range, a malformed reference. |
| `internal_error` | The language model or an upstream service returned an unexpected error after the loop's retry budget was exhausted. |

The coercion record carries a `narrative` field explaining the situation in prose, and, where relevant, a `missing_tools` array or a `decision_request_ref`. Workspace surfaces render it as a card alongside the outcome.

The contract that makes this work is that the loop's tool registry is the source of truth: a loop cannot "almost" call a missing tool, and the kernel will not let it. When the language model produces a tool call the loop does not have, the registry rejects it and the loop halts with a structured coercion record. There is no path through which a missing tool becomes a confident-but-fabricated answer.

## Tier-shaped guardrails

Every actor has a **tier** (Trial / Paid / Team / Operator), and the tier shapes what the loop can do:

| Tier | Max turns | Wall-clock | Token budget | Daily cost | Daily loops | Verify forced |
|---|---|---|---|---|---|---|
| **Trial** | 5 | 2 min | 20k | $0.50 | 10 | yes |
| **Paid** | 16 | 10 min | 200k | $5 | 200 | optional |
| **Team** | 50 | 30 min | 1M | $50 | 2000 | optional |
| **Operator** | ∞ | ∞ | ∞ | ∞ | ∞ | optional |

Requests that exceed the tier's ceiling are denied up front — the loop does not start, no compensation record is emitted, the actor gets a clear `denial_reason` (`WORK_DAILY_CAP_EXCEEDED` or `WORK_DAILY_COUNT_EXCEEDED`). Use `POST /v1/work/loop/preview` to size goals before sending them.

## Compensation records — when an assumption is violated

Sometimes a loop violates an assumption the kernel made about it — it tries to exceed a ceiling, calls a forbidden tool, produces a malformed tool argument. The kernel emits a `core.work.compensation.v1` record naming the seam (where the violation happened), the assumption (what was violated), and the context.

Compensation records are observable to operators. The review endpoints (`GET /v1/work/compensation/review`, `/review/top`) aggregate per-actor anomalies against the fleet median — actors whose loops compensate at well above the fleet rate are surfaced. This is how the system notices when a previously-trustworthy actor's loops start misbehaving.

Importantly, compensation records are **not punishment** — they are observability. A high compensation count on a single goal might mean the loop is exploring an unusual boundary; a sustained high rate across many goals is what the anomaly score catches.

## Chat-actor delegation — `@agent`

A conversation with [Scribe](/docs/get-started/scribe) or the Syncropic Guide is one-shot: you ask, it answers. For multi-step work, open the message with `@agent <goal>` and the chat-actor delegates to a real loop.

Two things change when delegation happens:

1. **The loop runs as *the user*, not as Scribe/Guide.** It uses the user's identity, permissions, and tier — Scribe steps aside for the duration. Every record the loop emits is signed by the user's actor DID.
2. **The chat-actor's response and the loop's outcome pair up.** A `core.work.delegation.v1` record opens the delegation; the loop's outcome closes it. This is the same pair-completion pattern decision requests use.

Delegation is auto-classified — Scribe sees a message that opens with `@agent` and starts a loop. The classifier is heuristic (verbs like "build", "audit", "find every…"); it can be tightened with an explicit `@agent` opening.

See [Agents](/docs/concepts/agents) for the user-facing view of this seam — what the launch surface shows, what the capability is, what the outcomes mean.

## How to start a loop

Three entry points, same primitive:

```bash
# CLI — local in-process
spl work-loop "Summarise this week's dispatches"

# CLI — daemon-run, verified
spl work-loop "..." --remote --verify

# HTTP API
curl -X POST http://localhost:9100/v1/work/loop \
  -H "Authorization: Bearer $SPL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"goal": "...", "verification": "evaluator"}'

# Chat — @agent delegation
# (type into any Scribe/Guide thread)
@agent audit my last 7 days of dispatches and write a summary
```

See the [CLI reference](/docs/reference/cli#work-loop--spl-work-loop) and [API reference](/docs/reference/api#work-loops) for full surface, and the [body-kinds reference](/docs/reference/body-kinds#kinds-emitted-by-the-work-loop) for the records the loop emits.
