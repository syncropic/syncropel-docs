## Overview

An **agent** in Syncropel is an actor that drives a work loop using a language model. Agents are not a separate kind of thing: they are [actors](/docs/concepts/actors) like any other, with an identity, a trust record, a tier, and an audit trail of records on the threads they work on.

The difference between an agent and a person is how it acts. A person reads a thread and writes records by hand. An agent reads a thread through a [work loop](/docs/concepts/work-loop) and writes records through tool calls that a language model chose to make. Both produce the same records, earn trust the same way, and are audited the same way.

```
person  ─── writes records by hand ──┐
                                    ├──▶ same record, same thread, same audit trail
agent   ─── work loop writes records ┘
```

## How an agent gets started: `@agent`

The most common way to start an agent is from a conversation. In any thread, open a message with `@agent` followed by what you want:

```
@agent count the open tasks in this workspace and tell me how many are blocked
```

When you send the message, the chat-actor (typically [the chief of staff](/docs/get-started/the-assistant)) starts a new work loop **running as you, not as the chief**, with your identity, your tier and your permissions. The chief steps aside while it runs. Two records start the handoff: a `core.user.message.v1` with your message, and a `core.work.delegation.v1` that opens the loop. An outcome record closes it.

You can also start a loop without chat, with `spl work-loop "..."` or `POST /v1/work/loop`. The [work loop page](/docs/concepts/work-loop) covers all the options.

## What an agent can actually do

Every agent has a **capability**: which tools it can call and what budget it has. Its tier sets this, not the launch:

- The **granted** set is what the agent can call without asking, typically reading and writing records on threads.
- The **requestable** set is what the agent can ask the owner to grant for a specific loop, through a structured decision request. The owner approves or declines; either way the request is a record.
- The **budget** is the time and token limit the loop runs under. Loops that exceed the budget are halted with a clear reason.

The launch surface (when you type `@agent <goal>` in Compose) shows the capability before the loop starts, so you know what the agent can do before it tries. If a goal needs something not granted, such as a tool its tier doesn't have or a thread it can't read, the loop stops and says so rather than guessing.

## How to read what an agent did

Every action an agent takes is a record on the loop's thread. The thread carries:

- The original goal (a `core.work.loop.v1` record).
- Each turn the agent took (`core.work.turn.v1`), with the tool calls and results that turn made.
- A final outcome record (`core.work.loop_outcome.v1`).

You don't have to read the records directly: the workspace shows them as a timeline. Anyone with access to the thread sees the same picture.

The outcome of a loop is one of:

| Outcome | What it means |
|---|---|
| **completed** | The loop finished: the agent reached a turn with no tool calls. |
| **blocked** | The agent halted because it could not proceed, typically because it lacks a tool, the goal is ambiguous, or it needs a decision from you. A paired `core.work.coercion.v1` record explains the reason. |
| **cancelled** | Someone explicitly cancelled the loop while it was running. |
| **max_turns** | The loop hit its turn ceiling before finishing. |
| **budget_exhausted** | A token, USD, or wall-clock budget ran out, a `budget_kind` field names which one. |
| **guardrail_halt** | The same tool call with the same arguments failed several times in a row, so the loop was stopped. |
| **failed** | The loop failed, usually because of an infrastructure error rather than an agent decision. |

Blocked outcomes are the most common honest failure mode and the most worth understanding. The coercion reasons are:

| Reason | What happened |
|---|---|
| `tool_unavailable` | The agent identified a tool it would need (e.g. shell execution, file read) but the tool is not in its grant. The agent can request the tool through a decision request if it is in the requestable set. |
| `ambiguous_goal` | The goal has more than one reasonable interpretation. The agent surfaces the alternatives so you can pick. |
| `precondition_failed` | The goal assumed something that wasn't true, for example "summarise the records on this thread" when the thread is empty. |
| `decision_required` | The agent reached a fork that needs a human call. It raises a `core.work.decision_request.v1` for you to respond to. |
| `input_invalid` | A goal parameter could not be parsed into something concrete (e.g. an unparseable date range). |
| `internal_error` | The language model or another service returned an unexpected error after retries. |

A blocked loop is not a bad outcome, it is the agent being honest about what it could not do. The alternative, guessing, is worse.

## What an agent can do on your own machine

An agent running on your own machine can do real work, not just write records. A loop can have a **workspace tool set**: it can run commands and read, write and edit files, but only inside a workspace directory you point it at. That is how an agent builds something: it edits files, runs a test, reads the output and tries again, with every step recorded on the loop's thread.

This depends on who the agent runs as. Running shell commands and touching files is reserved for the owner's own loops (the Operator tier). It is off by default and is enabled only when the owner has set up a workspace directory for the loop. Loops on a shared workspace do **not** get a shell. They work only with records and the storage they are given, never the underlying machine.

In short:

- On **your own machine**, with a workspace directory configured, an agent can run commands and read and write files, and every action is recorded.
- On a **shared workspace**, agents are limited to records and their own isolated storage. They never reach the host machine.

In both cases every tool call is a record, every stop has a stated reason, and every loop runs under a budget set by the actor's tier. See the [work loop](/docs/concepts/work-loop) for the two run modes.

## Trust and audit

Because an agent is an actor, the records its loops emit build trust under its identity, just like a person's records do. An agent that consistently produces approved work earns trust; one whose loops are routinely overridden by a human reviewer does not. Trust is kept per area of work, so an agent that is reliable at one kind of work and unreliable at another is shown as such.

The audit trail is the loop's thread. Any reviewer with thread access can see the goal, every turn the agent took, every tool call it made, every result it got, and the final outcome. The thread is the whole story: there is no separate "agent log" the agent could have written selectively.

## Beyond language models

An agent uses a language model. But a language model is not the only kind of automated participant. A scheduling solver, a classifier that tags incoming records, or a validator that checks data against rules is not a language model, yet each does real work and returns a result.

Syncropel treats all of them like agents: each is an [actor](/docs/concepts/actors) with an identity, a [trust](/docs/concepts/trust) record and an audit trail. What it is inside does not change how it joins a thread or earns trust. Syncropel routes each kind of work to the participant with the strongest track record at it.

The broader family of automated participants is covered on the [helpers](/docs/concepts/helpers) page. An agent is the language-model member of that family; helpers are the rest.

- **[Actors](/docs/concepts/actors)**: the identity every agent has.
- **[Helpers](/docs/concepts/helpers)**: the broader family of automated participants; an agent is the language-model member.
- **[Work loop](/docs/concepts/work-loop)**: the plan, act and check cycle agents run under.
- **[Threads](/docs/concepts/threads)**: the coordination context a loop lives on.
- **[Trust](/docs/concepts/trust)**: how the records a loop emits feed the trust signal.
- **[The chief of staff](/docs/get-started/the-assistant)** is the default conversational assistant; a turn that needs tools escalates to a loop.
