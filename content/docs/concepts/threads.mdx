## Overview

A thread is a named context that records belong to. Its ID is stable, its records never change, and its meaning comes from how it is used. A task is a thread. A run is a thread. Your workspace settings are a thread. Syncing with a paired workspace targets a thread.

*Records on the same thread belong to the same story.* Records on different threads are independent unless you explicitly link them.

A thread is closer to a Git branch than to a Slack channel. It is a unit of history, not of conversation. A single agent run is a thread, and a conversation with a user may span dozens.

## Thread identity

Thread IDs start with `th_`, which makes them easy to tell apart from record IDs and actor DIDs (`did:sync:*`). An ID comes from what the thread is for:
- **Task threads** have a stable ID, so `TASK-0001` always maps to the same thread.
- **Run threads** get a fresh ID for each run.
- **Reserved threads** (`th_engine_config`, `th_instance_registry`, `th_fleet_control`, `th_consent`, `th_namespace_registry`, `th_actor_registry`) have fixed, well-known IDs.

Because an ID is the same everywhere, a paired workspace can refer to a thread by ID alone.

## Lifecycle

Most threads follow this arc, though the shape is flexible:

```
INTEND  →  DO/CALL  →  KNOW  →  KNOW(fulfills)
(open)      (active)    (observed)     (closed)
```

- **Opened** by an `INTEND` stating the goal or purpose. Every thread starts with an INTEND.
- **Active** while `DO` and `CALL` records land. Tools doing the work write these as they go.
- **Observed** when `KNOW` records capture intermediate facts, verdicts, or summaries.
- **Closed** by a `KNOW` carrying `body.fulfills: "<intend_id>"` referencing the opening INTEND. The thread then shows as "done". A thread can also close via cancellation, a `DO` with `body.cancels` or a `KNOW` with `body.verdict: "reject"`.

A thread's status comes from its records and is not stored separately. Two threads with different statuses have different records.

## Fork and merge

Threads can fork into sub-threads and merge results back. This is how fan-out works and how sub-tasks nest:

```
Parent: th_deploy_v2
  ├─ INTEND "deploy v2"
  ├─ INTEND sub-thread th_run_tests     ─ child
  │    └─ KNOW "458/458 pass"
  ├─ INTEND sub-thread th_migrate_db    ─ child
  │    └─ KNOW "migration complete"
  └─ KNOW fulfills "deployed"
```

A child thread has its own ID. The parent has an INTEND that refers to the child (`body.sub_thread`), and the work runs on the child thread. When the child closes, a record on the parent says "child X completed with result Y". A join rule in the parent INTEND decides when the parent closes: `all` (every child), `any` (first accept), `k_of_n`, or a custom expression.

The child thread has the full trace and the parent carries a summary and the result, so you can drill in or stay at the summary.

## Tasks are threads (with conventions)

A task in Syncropel is a thread whose opening INTEND has `body.task = true` and whose body carries alias, assignee, domain, priority, labels, and success criteria. This is a convention: `spl task show` recognizes the pattern and shows it as a task.

This has three practical consequences:

1. **Every task has a thread with real records.** If you want the ground truth on what a task did and when, read its thread. `spl debug replay TASK-XXXX` walks the records with the status changes marked.
2. **Task state can never drift from record state.** The status always comes from the records on the thread.
3. **Two sibling threads are two independent tasks.** Forking a thread creates a child task; the parent task's status depends on when the children close, per its join rule.

## Reserved threads

A few thread IDs are reserved because Syncropel uses them itself:

| Thread | Purpose | Read by |
|---|---|---|
| `th_engine_config` | Settings: routing rules, triggers, permission rules, auth config. | Your workspace, whenever it changes. |
| `th_actor_registry` | Registered actors: DID, display name, category, status. | Routing and permission rules. |
| `th_namespace_registry` | Namespace hierarchy: ORG / PROJECT / ENV / JOB entries. | The namespace check when records are written. |
| `th_instance_registry` | Your workspaces: heartbeats, addresses and capabilities. | Choosing where fan-out work runs. |
| `th_fleet_control` | Kill switch state: soft / hard / emergency freeze records. | Permission rules on every write. |
| `th_consent` | Cross-namespace consent grants. | The consent check on every sync. |

Each of these is an ordinary thread, and its records follow the same rules. Syncropel just reloads them as soon as new records land.

## Participants and roles

Every actor who writes a record on a thread is a participant. Participation comes automatically from the records. `spl thread show <id>` lists participants with record counts and inferred roles (opener, reviewer, adapter, observer).

Roles are inferred, not enforced. The opener is whoever wrote the first INTEND. A reviewer is an actor writing a KNOW with a verdict. An adapter is an actor whose records are paired INTEND/DO/CALL/KNOW with `dispatch_handled = true`. You never maintain a participant list by hand.

## Threads, labels and rooms

A record belongs to *exactly one* thread. There are no multiple tags or rooms, which keeps each thread simple and predictable.

To group across threads, use labels (`body.labels`), `body.topic`, namespace (`body.namespace`) or actor filters.

## When a new thread vs a continuation

Two rules of thumb:

- **New thread when the goal is new.** A new task, run, deployment or sync each gets its own thread. There is no penalty to having many.
- **Continuation on the same thread when the goal is the same.** Follow-up observations, corrections and the final verdict on a long-running task all go on the original thread. Forking into a sub-thread is appropriate when a branch of work is independent enough to need its own close signal.
