## Overview

Syncropel coordinates more than chat assistants. A **helper** is an automated participant that does one kind of work well and returns its result as a record. A scheduling solver that optimises a route, a classifier that tags incoming records, a checker that validates data against a set of rules: each is a helper.

A helper differs from an [agent](/docs/concepts/agents) in how it works. An agent uses a language model in a [work loop](/docs/concepts/work-loop), taking many turns and calling tools. A helper is usually one focused computation: it takes a request, produces an answer, and is done. The answer might come from a solver, a classifier, a rules checker, or a mix. Syncropel does not care how a helper computes.

A helper is an [actor](/docs/concepts/actors), like a person or an agent. It has an identity, a [trust](/docs/concepts/trust) record, a tier, and an audit trail of records on the threads it works on.

```
chat assistant ─── language model, many turns ─┐
solver         ─── one computation, one answer ─┼──▶ same actor, same trust, same audit trail
classifier     ─── one computation, one answer ─┘
```

## How work reaches a helper

A request for work lands on a [thread](/docs/concepts/threads) as a record. Syncropel sends it to the best-suited helper, the helper returns its result as a record on the same thread, and a reviewer's verdict on that result feeds the helper's trust. Anyone with access to the thread sees what was asked, what came back, and whether it was accepted.

Over time, Syncropel **learns which helper to trust for which work**. When more than one helper can do a kind of work, it prefers the one with the stronger track record. Trust is earned from reviewed outcomes. A helper whose results are consistently accepted gets the work, and one whose results are often overridden does not. Trust is kept per area of work, so a helper that is reliable at one thing and not at another is shown as such.

## Why this matters

Most tools assume the only automated participant is a chat assistant. In Syncropel, every automated participant is an actor that produces auditable records and earns trust from reviewed outcomes. A scheduling problem can go to a solver, a tagging problem to a classifier, and an open-ended research problem to an agent, each weighed by how well it has actually done that kind of work.

Whatever did the work, the record shows what was asked, what came back, who reviewed it, and how that moved the participant's trust.

## Adding a helper

Adding a custom helper is an **advanced step for the workspace owner**. The owner configures the helper and points it at the work it should handle, and it then takes part as an actor. Members cannot add one themselves. The built-in [chief of staff](/docs/get-started/the-assistant) and the [agents](/docs/concepts/agents) it hands work to are available in every workspace.

## Where it fits

- **[Actors](/docs/concepts/actors)**: the identity every helper has.
- **[Agents](/docs/concepts/agents)**: the language-model kind of helper, running a work loop.
- **[Trust](/docs/concepts/trust)**: how reviewed outcomes decide which helper work routes to.
- **[Threads](/docs/concepts/threads)**: where a request reaches a helper and its result comes back.
