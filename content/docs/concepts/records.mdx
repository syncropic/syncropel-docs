## Overview

A record is a single fact that never changes after it is written. Syncropel writes nothing else. Task status, trust scores, routing rules, configuration, the output of a CI job and a comment on a design doc are all records.

**The record log is the source of truth, and everything else is worked out from it.** Trust scores, proven patterns and workspace state are not stored separately. They are calculated from the records, the way a bank balance is calculated from a list of transactions. This is what makes your workspace auditable and consistent across paired workspaces. The [State is a fold](#state-is-a-fold) section below explains more.

A record is never changed once it lands. Corrections, cancellations and status changes are new records that point at the old ones.

If you have used Git commits or CouchDB documents, the shape will feel familiar. The difference is that every kind of work uses the same record: code changes, tasks, trust evidence, sync between workspaces, and policies.

## The fields

| # | Field | Part of the ID | What it is |
|---|---|---|---|
| 1 | `parents` | yes | IDs of the records this one builds on. An empty list `[]` for a first record. |
| 2 | `thread` | yes | The thread this record belongs to, a `th_`-prefixed thread ID. |
| 3 | `actor` | yes | Who emitted it, a DID like `did:sync:user:alice` or `did:sync:agent:dev`. |
| 4 | `act` | yes | The act type, one of 8: `INTEND`, `DO`, `KNOW`, `LEARN`, `GET`, `PUT`, `CALL`, `MAP`. |
| 5 | `body` | yes | The JSON content. Syncropel stores it as given. |
| 6 | `clock` | yes | A counter that only goes up for each actor on each thread. Starts at 0 on a new thread. |
| 7 | `data_type` | yes | One of 6: `SCALAR`, `FORMULA`, `DISTRIBUTION`, `REFERENCE`, `MORPHISM`, `VOID`. |
| 8 | `judged_by` | **no** | Pointer to the record whose judgment this reflects. Often null. |

`judged_by` is left out of the ID on purpose. The same observation reviewed by two different people is still the same observation. What changes is who vouches for it, not the content.

## Identity

A record's ID comes from its content: the same content always gives the same ID, and different content gives a different one. This means:

1. **Sending the same record twice does nothing.** If Alice sends the same `(thread, actor, clock, body, act)` again, the second send is ignored because the ID already exists. Retrying after a network error is safe.
2. **The ID proves the record is unaltered.** A record pulled from a paired workspace whose ID does not match its content is rejected.
3. **A record cannot be edited.** Change one character and you have a different record. Two workspaces that hold the same IDs hold the same records.

See the [Glossary](/docs/reference/glossary) for more.

## Act types

Eight act types, partitioned into two groups of four.

**Coordination acts** are what teams of people and AI members use most.

| Act | Meaning | Typical body |
|---|---|---|
| `INTEND` | Declare a goal. Opens a thread or branches a sub-thread. | `{"goal": "..."}`, `{"task": true, ...}` |
| `DO` | Record an action performed. | `{"tool": "bash", "args": [...]}` |
| `KNOW` | Record an observation, fact, or verdict. | `{"topic": "...", "observation": "..."}`, `{"fulfills": "<record_id>"}` |
| `LEARN` | Record an insight or decision that should persist. Often used for config changes. | `{"topic": "routing_rule", "rule": {...}}` |

**Effect acts** are written by tools and integrations when they touch the outside world.

| Act | Meaning | Typical body |
|---|---|---|
| `GET` | Retrieve a value. | `{"key": "..."}` |
| `PUT` | Store a value. | `{"key": "...", "value": "..."}` |
| `CALL` | Invoke a tool or service. | `{"tool": "bash", "cmd": "..."}`, `{"provider": "anthropic", "request": {...}}` |
| `MAP` | Transform data. | `{"from": "...", "to": "..."}` |

Most CLI commands emit a single act, `spl intend` emits `INTEND`, `spl do` emits `DO`, and so on. Larger flows write a chain: an `INTEND` for the goal, a `CALL` when a tool is invoked, then a `KNOW` when the tool returns.

## The body is free-form

Syncropel does not check what is inside `body`. It stores the record as given. Conventions such as "a task `INTEND` has `body.task = true`", "a closing `KNOW` has `body.fulfills`" and "a routing rule is a `LEARN` on `th_engine_config` with `body.topic = routing_rule`" are applied by the tools and SDKs that read the records.

- **New kinds of record need no upgrade.** New task statuses and config topics are just new `body.topic` values.
- **A malformed body is caught when it is used.** A `LEARN` with a broken routing rule is stored, but the rule is left out when rules load, and you get a warning.

The one exception is `body.namespace`, which Syncropel checks when a record arrives, because namespaces are a security boundary.

## Changing your mind

Records are never edited or deleted. Changes are new records:

- **Correct a mistake**: write a `KNOW` with `body.topic: "correction"` and the bad record in `parents`. The later one wins.
- **Cancel an intent**: write a `DO` with `body.cancels: "<intend_id>"`. The task then shows as cancelled.
- **Change a setting**: write a new `LEARN` on `th_engine_config`. The latest record wins.

You cannot backdate a record. If someone disagrees with an earlier observation, they write a later record. Which one wins depends on the rule that applies: usually the latest, sometimes the first accepted, sometimes something specific to the area.

Every change happened when it happened, signed by whoever made it, and nothing later can alter that history.

## State is a fold

There is no second database. Everything you see, such as task status, trust scores, routing rules and namespaces, is worked out by reading the records:

```
current_state = fold(records_on_thread)
```

`spl task show` works out a task's state from its thread. `spl trust` works out trust from every verdict an actor has received. `spl config list-rules` returns the latest rule per name.

This means:

1. **The records are the ground truth.** If a view looks wrong, the records are still right.
2. **Paired workspaces agree.** Two workspaces with the same records show the same state.
3. **State can always be rebuilt.** If a derived view is damaged, Syncropel rebuilds it from the records. It does this automatically on every start.

## What goes in and what doesn't

**Record it if:**
- It is an intent, action, observation or lesson that someone else might need to audit or replay.
- It should survive a crash.
- Another member (person, agent or service) would coordinate around it.

**Don't record it if:**
- It is a cache that is cheaper to recompute, such as search embeddings.
- It is secret material such as private keys or API keys. These live in `~/.syncro/secrets/` and are not records. See [Secrets](/docs/concepts/secrets).
- It is a detail of a running process, such as a process ID.
- It changes faster than records can be written, such as a high-rate telemetry stream. Summarize it and record the summary.

When in doubt, record it.
