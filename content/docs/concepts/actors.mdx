## Overview

An actor is anyone or anything that writes records: a person at a terminal, an AI agent, a CI pipeline calling the HTTP API, or a paired workspace syncing records. Syncropel treats them all the same way. Everyone writes the same kind of record and builds up trust the same way.

Because "who did it" works the same for people and AI, trust, permissions and audit don't need separate rules for each.

An actor has four parts: an identity (its DID), a trust record, a memory that lasts across sessions, and, for anything calling the HTTP API, a way to prove who it is (a bearer token, a signature, or a private key in your keychain).

## DID: the permanent handle

Every actor has a DID, a permanent identifier:

```
did:sync:user:alice          - a human
did:sync:agent:dev           - an AI development agent
did:sync:agent:reviewer      - an AI review agent
did:sync:system:engine       - the workspace itself (writes notifications)
did:sync:system:intelligence - the workspace's proposing agent
did:sync:system:sa_abc123    - a service account (bearer-token authenticated)
did:key:z6Mk...              - an identity based on a public key
did:web:alice.dev            - an identity tied to a domain you control
```

The last part (`alice`, `dev`, `reviewer`) is just a readable label. What matters is the full DID, because every record carries it and trust and routing use it.

Three things hold for every DID:

1. **Permanence.** Trust built up under a DID stays with it. If you swap the AI model behind `did:sync:agent:dev`, its trust stays: the DID is the identity, not the model.
2. **Uniqueness within a namespace.** Two records from `did:sync:user:alice` in the same namespace are from the same person. Two people named Alice at different organizations get different DIDs (such as `did:sync:user:alice@acme`) or live in different namespaces.
3. **No central authority needed.** `did:key` is the public key itself. `did:web` is found over HTTPS at a domain you control. `did:sync` is found through the Syncropic-hosted or your own directory. Pick the one that matches how you want to establish trust.

## Identity, model and session

| Layer | What it is | How often it changes |
|---|---|---|
| **Identity (DID)** | The permanent handle, such as `did:sync:agent:dev`. | Never. |
| **Implementation** | What currently backs the actor: which AI model, which tool, which version. | Occasionally. |
| **Session** | The running process or session. | Every session. |

When you upgrade the AI model behind `did:sync:agent:dev`, its DID and trust don't change, because trust reflects what the actor produced under review, not which model produced it.

If the new model is meaningfully different, you may want to reset trust by writing a `LEARN` record that marks the change, rather than letting old evidence carry over.

## Actor kinds

The second-to-last segment of the DID classifies the actor's kind:

- **`user`**: a human, typically with a keyboard. Emits records via `spl intend/do/know/learn`, through the web UI, or via SDK calls.
- **`agent`**: an AI. Usually started through an adapter (`cli_adapter`, `proxy_adapter`). Each AI in a session has its own agent DID.
- **`system`**: a Syncropel component. It writes notifications (`did:sync:system:engine`), proposes routing rules (`did:sync:system:intelligence`) and records permission denials (`did:sync:system:governance`).
- **`service`**: a machine calling the HTTP API. Phones, CI pipelines, webhooks, federation peers. Authenticated by bearer token minted from `spl service-account create`.

Trust, routing and permissions treat all four the same. The kind only helps `spl actor list` group them and helps people reading audit logs.

## Registration and the actor registry

Register an actor before you use it in routing rules or expressions:

```bash
spl actor register did:sync:agent:reviewer --display-name "Reviewer"
spl actor list
spl actor show did:sync:agent:reviewer
```

Registration writes a `LEARN` record to `th_actor_registry`. The registry is read from that thread. Unregistered DIDs are not rejected, but name-based routing won't find them until they are registered.

Register each non-human actor you hand work to. People are set up by `spl init` and don't need to register again.

## Trust: domain-scoped evidence

Trust shows how reliable an actor has been. Every completed task that passes review adds success evidence; every rejection adds failure evidence. Syncropel tracks it per actor and area of work (domain):

```
                          ACTOR                   DOMAIN    SUCCESS   TOTAL   TRUST
did:sync:user:alice     code            12      14   0.438
did:sync:user:alice     ops              3       3   0.097
did:sync:agent:dev      code             8       9   0.473
did:sync:agent:dev      ops              1       4   0.012
did:sync:agent:reviewer research         0       0   0.000
```

Trust starts at zero. With few observations, the score stays conservative. With many observations, it converges to the empirical success rate. See [Trust](/docs/concepts/trust) for how recent results outweigh old ones, why self-evaluation doesn't count, and how the score shapes what a member may do on its own.

Trust is domain-scoped on purpose. An actor can be excellent in `code` and untrusted in `ops`. Routing rules that match on domain can prefer one actor for code and another for ops.

## Memory: persistent context across sessions

Actors build up memories (preferences, techniques, gotchas, references) that last across sessions:

```bash
spl memory list                         # list an actor's memories
spl memory list --actor did:sync:agent:dev -v   # with full descriptions
spl memory show <name>                  # read one in full
spl memory add <name> --type feedback --description "..."
spl memory remove <name>
spl memory search <keyword>
```

Memories are stored as `LEARN` records on the actor's memory thread. There are four kinds: `user` (stable user preferences), `feedback` (corrections applied in past sessions), `project` (state of ongoing work), and `reference` (useful URLs, conventions, file locations).

When an agent starts, Syncropel loads its manual from `~/.syncro/<agent>-prompt.md` and its memories, and adds both to the session's instructions. That is how an agent remembers "Alice doesn't want emojis in commit messages" even though the AI model itself remembers nothing between sessions.

## Authenticators: how actors prove they're themselves

For command-line work on your own workspace, no proof is needed: the actor comes from `config.toml` or the `SPL_ACTOR` environment variable. HTTP API calls need one when `auth.required = true` (the default):

- **Bearer tokens**: minted per service account via `spl service-account create`. Used by the SDKs, the CLI, paired workspaces and webhooks. Revocable per-token via `spl service-account revoke`.
- **Signed records for federation**: every record pulled from a paired workspace carries its author's signature, which is checked when the record arrives.
- **Keychain-held private keys**: for operators running their own `did:key` or `did:web` identity. The key lives in `~/.syncro/secrets/`; the workspace signs on the actor's behalf.

See the [security model](/docs/operate/security-model) for sign-in, your first service account, tokens, pairing and recovery.

## The instructions an actor runs under

An actor's instructions are a record, not a file. A prompt record holds the text (or a reference to a stored document for long ones), an optional role (constitution, map, procedures, manual, charter), and the actor it is for. The actor's definition names its prompt by record ID. Prompts can build on earlier prompts: the chain reads oldest first, so a charter reads as constitution, then the workspace map, then the actor's own procedures.

When a run starts, Syncropel resolves the chain and records which prompt the run used, next to the definition it ran under. You can always answer "which instructions produced this run" from the log, even after the definition has changed. If the prompt can't be found or is the wrong kind, the run is refused and the record is named. Syncropel never falls back to a default prompt.

```json
{
  "kind": "core.actor.prompt.v1",
  "schema_version": "1.0.0",
  "role": "charter",
  "actor_did": "did:sync:agent:census",
  "text": "You are the census taker of this instance. Every note you record begins with the word CENSUS."
}
```

Write it as a record on any thread, then point the actor at it with `"system_prompt_ref": "record:<id>"` in its definition.

## The threads an actor may read

A work-loop actor can declare the threads that are its domain:

```json
{"work_loop": {"tools": ["query_thread", "record_note"], "reads": ["th_library"]}}
```

Each declared thread is given to the run as standing read access, so a sandboxed run starts able to see its own domain. The declaration is a grant, so it is limited, revocable and reviewable. A limited member can declare reads only over threads it could already read, and an uncovered thread is refused with the thread named. Revoking the member removes everything its definition granted.

## How an actor reads

An actor has three ways to read, in order:

1. `search_records` and `list_threads` find where data lives, so an actor never has to guess a thread ID.
2. `query_thread` reads a thread and prints one line per record. Each line ends with `+fields:` naming the body fields the preview did not show, so the actor can ask for them by name.
3. `read_record` takes a row's thread and clock and returns one whole record, with its `version` so the actor can cite exactly what it read.

An actor can also ask a question instead of paging. `query_thread` takes a `filter` over body fields and a `count_only` flag:

```json
{"thread": "th_library", "filter": {"body.kind": "track.v1", "body.labeled": false}, "count_only": true}
```

The filter shows only what the run's credential could see anyway.

Three similar answers are kept apart so an actor does not draw a wrong conclusion:

- A field **no record carries** shows `(absent)`. If none of the named fields exist anywhere, you get an error naming the fields that do.
- A field set to **null** shows `null`, which is a fact about the record.
- An **empty answer** says what it covers: nothing visible to this run's credential is not the same as nothing anywhere.

## When an actor asks a person to act

An actor that cannot meet its goal calls `request_decision`, the only correct way to stop short. If the reason is `decision_required`, the refusal also becomes a question a person can answer from [your call](/docs/guides/your-call) or from the run's own row.

A proposal may include `claims` about the records it depends on:

```json
{"thread": "th_library", "clock": 12, "field": "body.labeled", "equals": false, "version": "<record id>"}
```

Syncropel checks each claim against the log before anyone is asked to act on it. A claim that does not hold goes back to the actor as an error saying what the record actually contains, so the actor fixes its own proposal. If a `version` is cited and the record has since changed, the actor is told to re-read it.

## When Syncropel corrects an actor

After a tool call, Syncropel may add an observation that the actor sees on its next turn, next to the tool's result. An actor repeating the same call is told so. An actor circling a thread that keeps coming back empty is told that too. A tool call from a reply that was cut off by the output limit is never run, because arguments cut off mid-write can look complete and still be wrong.

Each of these is a `core.work.observation.v1` record naming the rule that fired, so you can read why a run changed course.

## An actor that defines actors

Every work-loop actor has three extra tools. `list_actors` lists every defined actor with its definition ID, tools, instructions, whether it is enabled, and its trust per domain. `explain_run` describes one run: state, turns, spend against its ceiling, the tool-call count, the definition and prompt it ran under, and the open question. `propose_definition` writes a decision request to the workspace owner with a complete blueprint and the difference from what is installed. The run waits for the answer.

Approval installs. When the owner approves, the blueprint is installed as the approver, limited by the approver's own permissions, exactly as if they had installed it. The new definition records who proposed it and which request approved it. The proposing actor cannot shortcut this: it cannot write a definition, and an actor running in the sandbox cannot even reach the approval step.

The **harness engineer** (`did:sync:agent:harness`) is an actor defined this way, whose area of work is the other actors. It reads the actor list first on every run, reads runs before proposing changes, and ends an onboarding conversation with a proposal. Its trust is judged one step removed: a verdict on a run under a definition it proposed also moves its standing in the `harness` domain, and it may never give a verdict on such a run itself (`400 VERDICT_SELF_JUDGMENT`).

A definition may set its own per-run `budget_usd` and `max_turns`. Values you give explicitly when starting a run win. When a run is started with none, the definition's limits apply.

## What actors don't do

**Actors don't carry capability grants.** A DID is *who*, not *what they can do*. Permission comes from namespaces, permission rules and consent grants (for pairing). An actor with a valid bearer token hitting a namespace they don't have permission records for still gets a 403.

**Actors don't have private state known only to themselves.** Everything is records. An agent's memory, preferences and history are all in the log, which is how a new session picks up where the last one left off.

**Actors don't own their records.** A record's `actor` says who wrote it, not who controls it. Any actor with permission can correct or cancel it, not just the original author.
