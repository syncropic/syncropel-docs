A **workspace** is a record that carries a complete interactive surface. It
describes what a screen looks like, how its regions are laid out, which
records feed it, and what it is allowed to do on your behalf. Your
workspace turns that description into a working page.

Because a workspace *is* a record, you don't install software. You write the record, or
someone shares it with you, and the screen is live. There is no build step
and no restart. A new workspace is one `core.workspace.v1` record away.

Every new instance starts with a **Tasks** workspace already installed, so it is never a blank screen. Everything below is the same whether you are looking at that
starter or one you wrote yourself.

## The shape

A workspace body is a record of kind `core.workspace.v1`. It has three
parts: `meta` (what the workspace is), `regions` (what it shows), and
`lifecycle` (where it is in its life).

```json
{
  "kind": "core.workspace.v1",
  "schema_version": "2.0.0",
  "meta": {
    "slug": "tasks",
    "title": "Tasks",
    "icon": "check-square",
    "rail": true,
    "shell": "workspace",
    "defaults": { "bucket": "all" },
    "capabilities": {
      "emit": [ { "act": "INTEND", "kind": "core.task" } ],
      "navigate": "same-origin"
    }
  },
  "regions": {
    "header": { "srp": "0.7", "root": { } },
    "body":   { "srp": "0.7", "root": { } }
  },
  "lifecycle": "published"
}
```

### `meta`, what the workspace is

| Field | What it does |
|---|---|
| `slug` | The workspace's route and its key in the catalog. Unique within your instance. |
| `title` | The human-readable name shown in the UI. |
| `icon` | An icon name used wherever the workspace is listed. |
| `rail` | When `true`, the workspace is pinned to the navigation rail. |
| `shell` | The page layout the regions are arranged into. |
| `defaults` | Optional starting state, such as an initial filter or selected tab. |
| `capabilities` | What the workspace is allowed to do. See [Capabilities](#capabilities). |

### `regions`, what it shows

`regions` is a map. Each key is a slot in the layout (`header`, `body`,
`rail`, `browse`, `status`, `aside`), and each value is a **projection
document**: a description of the screen built from a small set of
parts (tables, forms, text, charts and so on). See
[Projections](/docs/guides/projections) for the document format and
[React components](/docs/guides/react-components) for the parts an app
can show.

A projection document holds **queries, not data**. The
workspace record stays fixed; the records it
shows are looked up when the screen loads. The same workspace, opened
by two different people, shows each their own records, laid out the same way.

### `lifecycle`, where it is in its life

One of `draft`, `published`, or `archived`. Whoever writes the record sets the lifecycle. Changing it means writing a new record; see
[Installing &amp; managing workspaces](/docs/operate/workspace/lifecycle).

## Viewing in Studio

Open a workspace, or any content thread, such as a note, in Studio and
it renders its content directly. A view switcher lets you read the same
thread three ways without changing anything:

- **Document**: the rendered document: the workspace's regions, or a
  note's formatted text. This is the default.
- **Outline**: just the heading hierarchy, for jumping around a long
  document.
- **Records**: the underlying records the document is built from, shown
  as they are. The document is a view *of* these records; this shows
  what is behind it.

Switching views never edits the thread, each is a different reading of
the same records. A thread someone else has [made
public](/docs/guides/federation-discovery#make-your-work-public) renders
the same way for you, read-only.

## Capabilities

`meta.capabilities` is the limit on what a workspace may do. It is part
of the record, so it is fixed when the workspace is written: a workspace cannot quietly grant itself new powers.

| Field | What it controls |
|---|---|
| `emit` | The record kinds the surface may write, as `{ act, kind }` pairs. A surface with no `emit` entry is read-only. |
| `navigate` | Where the surface may send you: `same-origin` (within your workspace), `external-confirmed` (elsewhere, with a confirmation), or `none`. |

Anything a workspace tries that is not declared here is refused by the
host. This is what makes it safe to install a workspace someone else
wrote: you can read its `capabilities` block before you install it and
know exactly what it can touch.

## How workspaces relate to records

Records are the foundation and threads group them. **Workspaces sit on top**: a workspace says "gather records like this, lay them out like that, and let me do these things."

A workspace does not store data. It only describes how to view and act on data. Two people running the "same" workspace are running the same description.

A workspace does **not** contain:

- **Programs.** A workspace does not run code; your workspace displays it.
- **Storage settings.** Your records live wherever you keep them.
- **Sign-in settings.** These are handled separately.
- **Secrets.** A workspace never carries keys.

## The catalog

Your workspaces are kept on a single well-known thread, the
**workspace catalog**. Installing a workspace adds its record there;
listing your workspaces reads that thread.

To find workspaces, ask for records of kind
`core.workspace.v1`. The catalog is not a separate service or an app store. It is records, queried like any others.

```bash
spl workspace list
```

A workspace published on *another* instance reaches yours over
[the Graph](/docs/concepts/graph), Syncropel's way of finding workspaces on other instances. The Graph carries a workspace to you, and your catalog is
where it lands once you install it.

See [Installing &amp; managing workspaces](/docs/operate/workspace/lifecycle)
for the full command surface.
