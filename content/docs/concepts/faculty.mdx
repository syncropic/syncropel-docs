## Overview

A **Faculty** is a unit of intelligence you deploy: it takes in a piece of work and produces a result. It is described by *what it does*, not by *what it is made of*. A language model, a solver, a classifier, an external HTTP service or a plain script can all fill the same role. Each one takes work in and writes a result record.

Syncropel treats a solver exactly like a language model. Both receive work the same way, both produce ordinary records, both are judged by an independent evaluator, and both build [trust](/docs/concepts/trust) from those verdicts. No kind is favoured.

## Why it matters

Most systems tie a task to a method: "summarize this" always calls the language model, and "solve this" always runs the solver. Swapping the method means rewriting code.

In Syncropel, work is addressed to the kind of result you want, and any Faculty that says it can do that work is a candidate:

- **Reliability is measured, not assumed.** You deploy candidates, let them do real work, and let independent evaluators grade the outcomes. The one with the most trust at that task gets the work.
- **You can mix kinds freely.** A cheap solver can handle the cases it is good at while a language model handles the open-ended ones, and work is routed between them on evidence.
- **Swapping is deploying.** Replacing one with a better one means deploying a new Faculty. Nothing else changes.

For example, a weak heuristic and an exact solver can both declare they handle the same problem. Independent verdicts on their results move their trust apart, and the problem starts going to the solver that gets it right. This is the [calibrated marketplace](/docs/concepts/marketplace).

## What a Faculty looks like

A Faculty is deployed as a manifest: a small record describing how to reach it and what it does. The key fields:

| Field | What it declares |
|---|---|
| **actor** | The identity (DID) the Faculty runs as. Its results are attributed to it, and trust builds under it. |
| **mechanism** | What it is made of: `llm`, `solver`, `search`, `model`, `perceptor`, `external_process`, `human`, `cel`, or `composite`. All are treated the same way. |
| **transport** | How work reaches it: `proxy_http` (an HTTP service) or `local_binary` (a process your workspace starts, for owners only). |
| **seam** | Where it plugs in: `inference` (it reasons / produces results), `effect` (it acts on the world), or `both`. |
| **intent kind** | The kind of work it serves: the capability it advertises. |
| **declared kinds** | The result kinds it's allowed to emit. |
| **lifecycle** | `standing`, `default_on`, `on_demand`, or `ephemeral`. |

The mechanism field only describes the Faculty. Routing and trust never use it to decide anything.

## Managing Faculties with `spl faculty`

### Deploy

Deploying a Faculty publishes its manifest. Your workspace checks it and registers it right away, with no restart.

```bash
# An LLM-backed Faculty (the common case; these fields are the defaults)
spl faculty deploy did:sync:agent:writer \
  --mechanism llm \
  --transport proxy_http \
  --endpoint https://api.example.com/v1/chat/completions \
  --model your-model-name \
  --auth-ref secret://my_api_key \
  --prompt-ref embedded:writer.v1 \
  --intent-kind core.user.message.v1

# A non-LLM solver reached over HTTP (note: no model/prompt needed)
spl faculty deploy did:sync:agent:optimizer \
  --mechanism solver \
  --transport proxy_http \
  --endpoint https://solver.example.com/solve \
  --auth-ref secret://solver_key \
  --intent-kind acme.problem.lp.v1 \
  --declares-kind acme.solution.lp.v1
```

The `<DID>` accepts a `name` shorthand that expands to `did:sync:agent:<name>`. Secrets are referenced by handle (`secret://...`), never pasted inline.

### List, show, retire

```bash
# Every deployed Faculty (latest manifest per actor)
spl faculty list
# ACTOR                  MECHANISM   TRANSPORT    SEAM       ENABLED
# did:sync:agent:harness  llm         proxy_http   inference  true

# One Faculty's manifest in full
spl faculty show did:sync:agent:harness

# Retire a Faculty: unregisters it live
spl faculty retire did:sync:agent:optimizer
```

Retiring writes a disabled manifest, and the Faculty stops receiving work immediately. The history of what was deployed when stays in the log.

## What a Faculty must do

A Faculty isn't trusted just because it was deployed. It earns standing on the same terms as every other participant:

- **Grounded**: its results are real records attributed to its own DID, not anonymous output.
- **Legible**: anyone with access to the thread can read what it produced and why.
- **Accountable**: an *independent* evaluator judges its work; it can never grade itself. (See the evaluation gate in [Trust](/docs/concepts/trust).)
- **Bounded**: it runs under a budget and a capability, and it can only emit the result kinds it declared.

A new Faculty starts with no trust and earns it by producing results and being judged. It cannot displace a proven one until it has earned the standing.
