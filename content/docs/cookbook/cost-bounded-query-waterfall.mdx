---
title: Cost-bounded query waterfall
description: Try the cheap AI model first, move to a stronger one only if the answer is weak, and use the most expensive only as a last resort, all within a 5-cent limit.
---

## Problem

You have a classification task that is easy 80% of the time and hard 20% of the time. Always using the strongest AI model wastes money. Always using the cheapest gives wrong answers. You want to try models in turn, stop as soon as one is confident, and stop for good if spending passes 5 cents.

## Recipe

The `waterfall` pattern: models are tried in order, it stops as soon as an answer is accepted, and it never goes over the budget.

```bash
spl infer "Classify this review as positive / negative / neutral: 'great product fast shipping'" \
  --kind core.classification.v1 \
  --responder llm:haiku \
  --responder llm:sonnet \
  --responder llm:opus \
  --orchestration waterfall \
  --budget 0.05 \
  --timeout 60 \
  --reversible \
  --wait
```

The command builds this setup:

```json
{
  "pattern": "waterfall",
  "stages": [
    { "responders": [{ "kind": "llm", "model": "~haiku" }] },
    { "responders": [{ "kind": "llm", "model": "~sonnet" }] },
    { "responders": [{ "kind": "llm", "model": "~opus" }] }
  ],
  "accept_expression": "fold.answer.confidence >= 0.85"
}
```

To set your own acceptance condition (not available as a command option), use an SDK or `--query-file`:

```json
{
  "kind": "infer.query.v1",
  "input": { "inline": "Classify this review: 'great product fast shipping'" },
  "responders": [
    { "kind": "llm", "model": "~haiku" },
    { "kind": "llm", "model": "~sonnet" },
    { "kind": "llm", "model": "~opus" }
  ],
  "fold": { "function": "best_of" },
  "orchestration": {
    "pattern": "waterfall",
    "stages": [
      { "responders": [{ "kind": "llm", "model": "~haiku" }] },
      { "responders": [{ "kind": "llm", "model": "~sonnet" }] },
      { "responders": [{ "kind": "llm", "model": "~opus" }] }
    ],
    "accept_expression": "fold.answer.confidence >= 0.85"
  },
  "answer_shape": {
    "kind": "core.classification.v1",
    "required_fields": ["body.label", "body.confidence"]
  },
  "side_effects": {
    "reversible": true,
    "max_cost_usd": 0.05,
    "max_latency_secs": 60
  }
}
```

Run it with `spl infer`:

```bash
spl infer --query-file waterfall-query.json --wait
```

## The happy path (stage 1 wins)

```text
answer:
  {
    "label": "positive",
    "confidence": 0.94
  }
provenance (1 contributor)
trust_summary: mean 0.62 min 0.62 max 0.62 n=1
cost: $0.0011
fold: best_of
thread: th_6b8a21...
know_record: 4c3f87a2...
```

Haiku returned confidence 0.94, which passes the 0.85 acceptance threshold, so it stopped there. Total cost: a tenth of a cent.

## The escalation path (stage 2 wins)

When Haiku returns `confidence: 0.68`:

1. Stage 1's answer arrives. With only one answer, `best_of` takes it.
2. The acceptance condition is checked: `0.68 >= 0.85` is false.
3. A record notes that stage 1 failed.
4. Stage 2 (Sonnet) is asked. It returns `confidence: 0.89`.
5. That passes, so the answer is saved as the result.

Total cost for the cascade: Haiku + Sonnet ≈ $0.012.

## The budget ceiling

`max_cost_usd: 0.05` is checked **between stages**. Before each stage, the total spent so far plus the estimated cost of the next stage is compared with the limit. If it would go over, the query stops with an `infer.error.v1` record with `code: "cost_budget_exceeded"`.

So the cascade can spend up to the limit but never past it. If stage 3 (Opus) would break the budget, it is never run, and you get an error record showing the cost so far.

## The trade-off

`waterfall` runs stages one after another. Stage 2 waits for stage 1. That is its benefit (skip expensive stages when a cheap one works) and its cost (the worst case takes as long as all stages added together).

If your models take very different times (say Haiku 3 seconds, Opus 30), the worst case is about 40 seconds in total. Asking all of them at once with `consensus` takes about 30 seconds, the time of the slowest. The cascade is cheaper in the usual case and slower in the worst case.

Note that `waterfall_first` is something different: it picks the first acceptable answer from a group that were all asked at once. The `waterfall` pattern above asks one at a time. See [Fold Functions — waterfall_first](/docs/guides/inference/fold-functions#function-waterfall_first).

## Try it on a test workspace

With Haiku, Sonnet and Opus set up as providers, the query above runs as written. Watch the records arrive on the query's thread:

```bash
spl thread records <thread-id>
```

You'll see:
- An `INTEND` with the query.
- One `CALL` for each stage that ran, with its cost in `body.cost_estimate_usd`.
- `DO` records with each model's answer.
- `LEARN` records between stages, with `body.kind: infer.orchestration.waterfall.state.v1`.
- The final `KNOW`.
