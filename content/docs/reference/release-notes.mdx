## Overview

This page summarizes releases in plain language: what changed and why it matters for using Syncropel day to day.

## 0.288.0

**A key now gets exactly the access it's asked for, and full access only when it's named. A list says when it was cut short and when something may be kept from you. The kernel's code was split into more parts, which changes nothing in how a workspace behaves.**

- **A device or a key gets full access only when you ask for it by name.** Before this version, `spl pair` picked a device's access from its name, and a name starting `browser-` got full access. Now a device paired without `--scopes` can read and write records, whatever it's called, and a name starting `viewer-` can only read. `--scopes admin` gives full access. The command says the access a device will hold before it writes anything. With no access named it says "No access was named, so this device can read and write records. To give it full access, add --scopes admin." With full access it says "This device will have full access to this workspace. Pair it only if it's yours, or belongs to someone you mean to give that." A key made for a service account holds the access its request names, and read and write when it names none. Pairings and keys already made keep the access they have.

- **Only the owner makes a key that acts as someone else, or a key with full admin.** Before this version, a member with full admin could make both. Now that member can still make keys that act as themselves, without full admin. Anything else is refused: "Only the workspace's owner can make a key that acts as someone else, so nothing was made or changed. Make one that acts as you, or ask the owner." The owner's keys work as before, the ones made before this version included. On every workspace Syncropic runs, counted on 2026-11-24, no working key was found that someone other than its own person had made. Keys already revoked or expired weren't counted.

- **Rotating a key keeps its access and its end date.** Before this version, `spl token rotate` made a replacement that never expired. A rotated key now has exactly the access the old one had, and the earliest end date among the keys it replaces. A rotation that names different access, more or less, is refused: "Rotating a key keeps the access it had, and this asked for different access, so nothing was rotated. To change what a key can do, make a new key and name the access." An account whose keys don't all have the same access isn't rotated: "Rotating keeps the access a key had, and the keys on this account don't all have the same access, so nothing was rotated. Revoke the keys you don't need and rotate again, or make a new key and name the access." Neither is an account with no key that still works: "Rotating keeps the access a key had, and no key on this account still works, so nothing was rotated. Pair a device again, send a guest a new invite, or make a new key and name the access."

- **`spl doctor` reports what the workspace records about who made what.** From this version a workspace records who made each key, who saved each tool and who set up each automation. `spl doctor` has new rows for the owner that count what has no such record: keys, tools that use a stored key, and enabled automations. It also lists the assistants that act for the owner, checks that the workspace's list of owners names a person, and counts keys that act as one of the owner's assistants and weren't made by the owner. These rows change nothing in this version. A later version is planned to act on the records: a key will need a record that the owner made it to do what only the owner can do, a tool will need a record that the owner saved it to use a stored key, and an automation with no record of who set it up will still start, but its runs won't use anyone's connected accounts or stored keys. Each row says what to do now.

- **`spl --no-token` runs a command without the saved key.** The command line sends the key saved on a machine with every request. `--no-token`, before the command's name, sends none, so on the workspace's own machine the request is the machine owner's. Use it to make a key, save a tool again or resume an automation so that it records the owner.

- **A list says what it may be keeping from you.** Everyone who isn't the owner now reads one note on a list, on its text form and on a summary's answer: "This is what you may read here. Some rows or values may not be shown." It's decided by who the reader is and never by what the list holds, so it says nothing about any one list. The owner reads "Nothing on this page was kept from you." Before this version, a guest could be told nothing was held back while each row named a field closed to them. A list grouped by a field can also say it isn't complete: "This list is grouped by a field. Rows may be missing if that field is one you can't read."

- **A list that was cut short says so, and why.** When a list or an answer isn't complete it now gives its reason from one named set, each with its sentence, and says which reasons mean the workspace is still catching up. A cut list no longer reads as complete.

- **Open questions aren't lost on a busy workspace.** Before this version, once a workspace had written more than 5,000 questions, the answered ones included, the newest weren't read. A new question could be missing from the list of what needs you, from the conversations marked as needing you, and from the inbox count. Every open question is now listed, unless more than 5,000 of a reader's own are open at once. Then the ones that have waited longest are listed and the list says so: "There are more open questions here than can be listed at once. The ones that have waited longest are listed, so newer ones may be missing.", with how many more are open. What other people have open never pushes a reader's own questions out, and tells them nothing.

- **Each guest has a memory space of their own.** Before this version, guests' memories were kept in one space that all guests shared, by mistake. Memories written from this version on are the guest's alone. A guest's memories from before this version aren't carried over to their own space. The owner's, members' and named assistants' memories are where they were. On every workspace Syncropic runs, counted on 2026-11-24, the shared space held no memories.

- **A wake that never came now reads as missed.** A hosted workspace sleeps when it's idle and is woken for scheduled work. Before this version, if nothing woke it, it could still read as on time. The owner now gets one notice, "Scheduled work came due while the workspace was asleep and nothing woke it, so each schedule followed its catch-up rule.", and `spl doctor` names the schedules, the times and what happened to each. The catch-up rule itself is unchanged.

- **Who can change an assistant.** Defining an assistant no longer replaces one you may not change, and a new assistant can't take a name already used by another assistant or by a person in the workspace. Only the owner, or whoever defined an assistant, can define it again or retire it: "Only the workspace's owner, or whoever defined this assistant, can retire it, so nothing was changed." Renaming an assistant stays the owner's.

- **The workspace page answers sooner after a start.** On a workspace bound to a backing repository, each read of the workspace page in the first minutes after a start waited up to 3 seconds for a check of the off-machine copy. The page no longer waits. A check still running shows in `spl doctor` as not yet checked.

- **If you run your own workspace, when you upgrade:**
  - Run `spl doctor` as the owner and read the new rows. For a key that needs to do what only the owner can do, make a new one on the workspace's own machine with `spl --no-token service-account create --name <name> --scopes <scopes> --with-token`, then revoke the old one. A key made from another machine with an old key doesn't record the owner.
  - Save again the tools that use a stored key, on the workspace's own machine: `spl --no-token tool resave --all-stored-key`. It now also saves the tools that were the owner's only because nobody had saved them as anyone's.
  - For each enabled automation the row counts, pause it and resume it on the workspace's own machine: `spl --no-token trigger pause <name>`, then `spl --no-token trigger resume <name>`.
  - A script that paired a browser by name and relied on full access now gets read and write. Add `--scopes admin`, which works on every version.
  - A script that rotated a device's key and expected full access back now gets the key's own access. Full access is asked for by name, with `spl pair --scopes admin`.
  - A rotated key keeps the old key's end date. A script that rotated to get a key with no end date gets one that ends when the old one did.
  - A guest's memories from before this version aren't in their own space. If a guest relied on one, it has to be written again.

- **For the command line and the API.**
  - Pairing. `spl pair` with no `--scopes` gives `records:read,records:write`, and `records:read` for a `viewer-*` name. `--scopes admin` gives full access. `spl pair --scopes ""` is refused and pairs nothing. `spl pair --browser` with `--scopes` is refused, since a browser holds the access of the person who signs in there. `spl pair` checks that the device name fits the QR code before it writes anything.
  - Making keys. The service-account door gives a key the access its request names, `records:read,records:write` when it names none, and full admin only when the request names `admin`. A request from anyone but the owner for a key that acts as another person is refused `ACTOR_NOT_DELEGABLE`. A member with full admin who asks for a key with full admin is refused `SCOPE_INSUFFICIENT`.
  - Rotation. `POST /v1/service-accounts/{id}/rotate-key`, with or without `expect_actor`, `POST /v1/tokens/{id}/rotate` and `spl token rotate` keep the key's access exactly. The rotate-key body takes an optional `scopes`: naming nothing, or the key's own access, rotates. Any other access is refused `409 ROTATE_KEEPS_ACCESS`. An account whose live keys hold different access is refused `409 ROTATE_KEYS_DIFFER`, and one with no live key `409 ROTATE_NOTHING_TO_KEEP`. Both paths keep the earliest live end date. `spl token list` and `GET /v1/tokens` show each key once, at its latest record.
  - What you may do. Each `may` word on `GET /v1/self` is now answered by the same rule its door uses. An owner's device key without full access is no longer offered removing members or leaving. A member with full admin is offered leaving. A guest invited to a conversation is offered the member list, writing and defining assistants. An owner's session is offered acknowledging notices.
  - Lists. A ledger read, its text form and a reduction's answer carry the page note for every reader who isn't the owner. A reduction's answer to such a reader counts only the records they can read, and names only fields closed to them by the workspace's rules. A member is told which columns are closed to them. A guest is told neither the columns' names nor their classes. A list or answer that isn't complete serves `complete: false` with `incomplete_reasons`.
  - Open questions. The register serves `asks_capped` and `asks_more_open` to every reader, for their own list, and `proposals_capped` and `proposals_more_open` to the owner. `GET /v1/lanes/{lane}`, `GET /v1/decisions`, the first page of `GET /v1/context` and the inbox on `GET /v1/self` serve the same two. `GET /v1/decisions` lists the questions a reader is asked first, then the oldest of the rest up to 1,000. `asks_scanned` counts the question records read and doesn't mean the limit is near.
  - A missed wake. `/v1/health` and the workspace read carry `missed_wake` with `count`, `count_is_at_least`, `since`, `occurrences`, `detected` and `runs`. The wake state reads `late` until a wake lands in time or the owner acknowledges the notice. A schedule's next run is always on the published list, so the wake for a weekly schedule after a week asleep is accepted.
  - Assistants. Defining an assistant under a name another assistant or a person has is refused. `ACTOR_ALREADY_DEFINED` answers someone who is neither the owner nor the one who defined it, and `RETIRE_FORBIDDEN` answers the same person on the retire door.
  - Memories. Each guest has a memory space of their own, and so does an assistant named by a run.

- **Correction to the 0.287.0 notes.** Those notes named four places where a guest is no longer told what kind of thing is kept from them. There was a fifth: the list of data classes a guest is shown. It now lists only the classes the guest can read somewhere, and no longer says who reads them.

- **Inside.** The kernel's code was split into more parts again. The crates at its core went from 7 to 10. Its largest source file went from 8,646 lines to 3,369. The largest knot of files that depend on each other went from 103 files to 86 in one part of the kernel, and from 81 to 66 in another. A fingerprint of how a workspace behaves was compared at every step and didn't change.

- **Known limits.**
  - Someone with full admin access can still, in some cases, act as the owner, and so reach the owner's stored keys and connected accounts. Give full admin only to people you would trust with everything in the workspace.
  - After restoring into a fresh store, the workspace doesn't remember that you erased your newest list of assistants. Name the assistants that act for you again after a restore.
  - Someone who isn't the owner is still told which fields are kept from them by the workspace's rules.
  - A list can show a row for a record you can't read, with its cells empty.
  - A summary can show an older value where a list shows an empty row for a newer record you can't read.
  - A question that stays open after its run has ended can be asked again. Someone who answers an earlier copy and can't see the later one is told nothing about it, and may notice that the run behind their copy didn't continue after they answered. Nothing of the later question is shown to them.
  - When more questions are open than the workspace reads at once, the newest ones may not be delivered.
  - A list grouped by a field can read as possibly incomplete to anyone but the owner, because a single entry can be kept from them.

## 0.287.0

**An invite now has to say what it allows, and a question takes one answer. A key the owner stored outside a connected account is kept for the owner's own work.**

- **An invite has to say what it allows.** Before this version, an invite made without saying what it allows gave full access to the workspace to whoever opened it. A membership invite made without a level did the same: whoever accepted it became a full admin, and a member renewed with one became a full admin too. On the command line, an invite made with only a device's name did too. Each of these is now refused, and nothing is made. The command line says "An invite has to say what it allows, so no invite was made. Add --preset reader or --preset contributor, or list what it allows with --scopes." Through the API, an invite with no level at all is answered "An invite for a guest has to say what they're allowed to do, so no invite was made.", and a membership with no level is refused too. Full access is given only when you ask for it by name, and the command then says so: "This invite gives full access to this workspace to whoever opens it. Send it only to a device of your own, or to someone you mean to give that." Across every workspace Syncropic runs, counted over all history on 2026-11-21, no invite of this kind was ever used, so no key was made this way.
- **A guest is no longer told what kind of thing is kept from them.** A guest reading a list, its columns, its totals or a conversation's summary was told the kind of each field closed to them, such as "Contact details". They're no longer told the kind. Each row still names the field that's closed to them, whether or not that row has a value in it.
- **A key stored outside a connected account is kept for the owner's own work.** Before this version, a tool that used a key the owner had stored could be run by a member, or by a member's assistant, and the key was sent to that tool's service for them. Such a key is now used when the owner calls the tool, or in the owner's own runs, and only by a tool the owner wrote. Anything else is refused before the key is read. A direct call by anyone else is answered as if there were no tool by that name. Inside a run, the tool's answer says "This tool uses a stored key that isn't part of a connected account. That key is for the owner's own runs on tools the owner wrote, and this isn't one, so nothing was sent. To use that service here, the owner can connect it as an account, point the tool at that account, and give access to it." The owner's own assistants and automations work as before on tools the owner wrote themselves, and so do connected accounts. A tool that came with an installed package doesn't count as one the owner wrote. On every workspace Syncropic runs, counted over all history on 2026-11-22, no such key was ever used by anyone but the workspace's owner.
- **A question takes one answer.** Before this version, two answers sent at the same moment, from two tabs or two devices, were both written. The second answer is now refused: "This question was already answered, so your answer wasn't added." A vote takes answers until it's decided, then refuses the same way.
- **The owner can close questions that were withdrawn and still showed as open.** A question withdrawn with an automation's key on an earlier version could stay in the list of open questions. `spl decisions withdrawals` now lists them and `spl decisions withdrawals close` closes them. Each close is the owner's own record, and `spl doctor` counts what's left.
- **Erasing your newest list of assistants that act for you no longer brings back the one before it.** Before this version, erasing the newest list made the list before it count again, which could bring back an assistant you had removed. Now no assistant acts for you until you name them again with `spl config owner-agents set`.
- **The member list says who has full admin.** `spl member list` now ends a member's line with "full admin" when they have it. The owner and admins see it. Before this version the list didn't show it.
- **More refusals read in plain words.** A grant written by hand that drops or widens the limit of the grant it comes from was refused with a code and a technical line. It now says what's wrong and that nothing was saved. Making an assistant's key that can't be given now says why.
- **The owner's workspace overview reads far less to answer.** On a test workspace with about 400 invites and 7,800 records, a repeat read went from 3,002 stored rows to 77, and the first read after a start from 8,397 to 737. The answer is the same, with one field added.
- **If you run your own workspace, when you upgrade:**
  - Check for members who became full admins without your meaning it. Renewing a member with an invite that named no level made them one, and the "Add a teammate" guide showed that command until it was corrected alongside this version. After the upgrade, run `spl member list` and look for "full admin" on anyone you didn't mean to make an admin. To put one right, send a new invite with the level you mean, `spl invite create --member --preset contributor --label <name>`. When the member accepts it, their old key stops working. Then revoke any invite they made while they were an admin.
  - Revoke invites made before the upgrade that you didn't mean to give full access. An invite made without a level before this version still gives full access after it. `spl invite list` lists them, `spl invite show <id>` shows what one gives, and `spl invite revoke <id>` revokes it.
  - To let a member, their assistant or their automation use a key you stored, connect that service as an account and give them access to it. `spl doctor` lists the tools that use a stored key outside a connected account.
  - An automation set off by another automation's record can't use such a key. Connect the service as an account.
  - A tool that came with a package you installed isn't counted as written by you. If it uses a key you stored outside a connected account, your own runs can't use it after the upgrade. `spl tool list --stored-key` lists such tools and says which you saved yourself. `spl tool resave <name>`, or `spl tool resave --all-stored-key`, saves them again as you, and `--dry-run` shows what would be written. Or connect the service as an account. A later update of the package that rewrites the tool needs the same again.
  - If two of your automations share a name in different namespaces, neither can use such a key. Rename one, or connect the service as an account.
  - A script that made an invite with no level and meant a device pairing now asks for full access by name: `--scopes admin` on the command line, `"scopes": ["admin"]` through the API. That works on older versions too.
- **For the command line and the API.**
  - Invites. `POST /v1/invites` with no `membership` and no `scopes` is refused `400 INVITE_SCOPES_REQUIRED` and no invite is made, including one addressed to a person (`address`, `to`). A membership with no level (no `preset`, `can` or `role`), including one with only a label or an expiry, is refused `400 INVALID_MEMBERSHIP`. A device pairing asks for admin by name, `"scopes": ["admin"]`, which works on 0.286 too. `spl invite create` with no level, or with only `--device-label`, exits 2 before anything is sent. `--scopes admin` prints the full-access line.
  - What a guest is told. A guest and a reader with no key get no class names from the ledger read (no `disclosure.withheld_columns`), the reductions read (no `disclosure.withheld_classes`), `GET /v1/ledgers/{id}/columns` (`disclosure: null`, `classes: []`) and `GET /v1/rooms/{t}` (no `disclosure` on a held column, no `widens`). A member keeps the names. The reductions read still names the withheld path (`withheld_fields`). The ledger read's page note doesn't, and each of its rows still names the closed field (`withheld`).
  - Questions. On the decide door, a second answer is refused `409 ASK_ALREADY_ANSWERED`, with `details.answered_by` naming the answer that stands, and nothing is written. Two answers sent together write one. A later answer through `POST /v1/records` is refused too. A question with a `quorum` refuses once its rule has decided.
  - Withdrawals. `GET /v1/decisions/withdrawals` lists withdrawals the store filed as proposals. `POST /v1/decisions/withdrawals/close` with `{"withdrawal_ids": [...]}` or `{"all": true}`, and `"dry_run": true` to write nothing, answers `closed`, `would_close` or `already_admitted`. Each close is the owner's record. A service-account key and an admin member are refused `403 WITHDRAWAL_CLOSE_OWNER_ONLY`, including an admin member naming the owner in `X-Syncropel-Actor`. An id that isn't a listed withdrawal is `409 WITHDRAWAL_NOT_LISTED`, with `details.reason` `unknown` or `not_a_withdrawal`. The command is `spl decisions withdrawals [close <ID>... | --all] [--dry-run]`, and `spl doctor` has a `listed_withdrawals` row.
  - Members and grants. When the owner or an admin reads `GET /v1/members`, every row carries `admin: true|false`. A contributor's read has no `admin` field. `GRANT_LIMIT_DROPPED`, `GRANT_LIMIT_WIDENS` and `GRANT_CHAIN_MISMATCH` answer `POST /v1/records` with `400` in plain words, with `details.field`. Defining an assistant and making an assistant's key answer `422 GRANT_REFUSED` with a base line and, for some causes, a second sentence, with the cause in `details.cause`. Erasing the newest owner-agents declaration leaves the set `degraded`, with no assistant, until it's declared again.
  - Stored keys outside a connected account. Such a key is used by the owner's direct call, or the owner's own run, on a tool the owner saved. A tool a package installed or updated doesn't count. A member's direct call (`POST /v1/self/use`, MCP `tools/call`) is answered `404 TOOL_UNKNOWN`, and so is the owner's on a tool they didn't save. A run's call answers `STORED_KEY_OWNER_ONLY`, and the probe door answers `403 STORED_KEY_OWNER_ONLY`. The commands are `spl tool list --stored-key` and `spl tool resave <tool_id>... | --all-stored-key [--dry-run]`. `spl doctor`'s row "stored keys outside a connected account" counts the tools and names them.
  - Packages. The first person bound to a venture role takes the token its install minted. `GET /v1/installs/{id}` then reads that bind `null` and names it in `binds_adopted`.
- **Inside.** The kernel's code was split into more parts. Its 20 crates are now 23. Source files over 1,000 lines went from 249 to 233, those over 2,000 from 56 to 39, and those over 4,000 from 6 to 1. The integration test programs of its two largest crates went from 176 to 2, and from 49.4 GiB on disk to 0.6. Building after an edit takes as long as before.
- **Known limits.**
  - Someone with full admin access can still, in some cases, act as the owner, and can reach the stored keys and connected accounts of everyone in the workspace, not only their own. Give full admin only to people you would trust with all of that.
  - After restoring into a fresh store, the workspace doesn't remember that you erased your newest list of assistants. Name the assistants that act for you again after a restore.
  - Someone who isn't the owner can still be told, in some places, how many rows have a value kept from them and what those fields are called.
  - On a list, the page's own note tells a guest nothing was held back, while each row names a field that's closed to them.

## 0.286.0

**Search now shows a member only what they may read, and a conversation's people and status come from the part a member or guest may read. A key with a limit can't give itself more. And a workspace you sync with can't write as you.**

- **An admin key with a limit no longer acts as an admin.** Before this version, an admin key limited to some conversations, a namespace, a tree of conversations, or by a read limit still acted as an admin almost everywhere. It could make itself a key with no limit, replace the workspace's recovery code, make an assistant key from another member's access, let others invite, export the workspace, change its automations and settings, remove members, promote guests, and read the owner's copy of any conversation whole. Such a key now works as a member with the same limits, on every way of reading and acting we test. In earlier versions an invite could also make an admin key limited to a tree of conversations. No such key was found on any workspace Syncropic runs, counted on 2026-11-20. An admin key limited to one conversation can no longer invite people unless it also holds the right to invite: to keep inviting, the owner invites that person again as a member with the places they need, and gives them the right to invite.
- **Keys made for assistants carry their maker's limits.** Before this version, a member or guest whose access had a limit on what they may read, write or open could give themselves an assistant key without those limits, and read everything their limit withholds. An admin with a read limit could make an assistant key that was a full admin. No such key had been made on any workspace Syncropic runs, counted on 2026-11-20. Every assistant key now carries every limit of the access it was made from, and a key made that way before this version is held to those limits from the first request after the upgrade. A key with no read limit, made by a member whose every membership has one, stops working: make a new one from your own account. When you define an assistant, its write limit must sit within your own, or leave it out and it takes yours.
- **Changing someone's access keeps their assistant keys working.** When the owner changes what a member or guest may do in a place, the keys that person made for assistants keep working and follow the new limits. A key with nothing left once narrowed ends with the old access.
- **Search shows only what you may read.** Before this version, search could show a member with a read limit the words of messages in conversations their limit withholds, with the conversation's title and who wrote in it. No member with such a grant was found on any workspace Syncropic runs, counted on 2026-11-20. An assistant's run could also find messages written after the run was started, and on a workspace with sign-in off, a request with no key could find words in every conversation in the workspace's main namespace. Search now keeps a match only when you may read that message, and a match names only the writers you may read. Records only their author may open, and a few kinds the workspace keeps for itself, are now left out of search, for the owner too.
- **Reading part of a conversation shows its people and status from that part.** For a member or guest who may read only part of a conversation, who took part, how many records it holds and whether it's closed are now worked out from what they may read. Before this version, the list of who took part named everyone who wrote, including writers of messages that reader is never shown, and a conversation could show as closed because of a message they couldn't read.
- **An assistant invited into a conversation reads it the ordinary way.** Before this version, an assistant's run that held a conversation only by an invitation to it was given the whole conversation as stored: every writer and time, counts of each kind of record, the latest record, and details of other runs started there. It now reads that conversation through the ordinary ways of reading, sees only what it was let in to, and can't write there.
- **Support access works only with the workspace's own support key.** Before this version, the owner could give access for help to any key, and the owner's list and notice said Syncropic had read the workspace. Access can now be given only to the workspace's own support key, and it stops being honoured when that key changes. Access given to any other key isn't honoured. The owner's list marks such access "Ended: it was given to a key this workspace no longer takes help from." and the owner can still revoke it. The list and the notice name Syncropic only on a hosted workspace, and only for Syncropic's current support key. Otherwise the notice says your workspace was opened with the access you gave for help, with the date and the reason you gave, and names nobody. A self-hosted workspace that gives access for help sets its helper's key first. Hosted workspaces have it already.
- **A workspace you sync with continuously can't write as you.** Before this version, a workspace paired for continuous sync could move who owns a conversation, open a conversation to someone with an invitation written in your name, add a connected account, hide something an assistant remembers, widen someone's access to a tree of conversations, or give support access. From a workspace that isn't marked as your own, a sync now refuses anything written as your workspace, anything only your workspace or its owner writes, and invitations. A conversation that stays in its workspace is never synced from anyone. The sync's status counts what it refused and says what to do: "This workspace is refusing some records from the other one, because the other one isn't marked as your own workspace." The owner can mark the other workspace as their own, from this machine or from a fresh sign-in with a passkey. Each workspace's owner marks its own side. The status then says "Marked as your own workspace: yes. That is your word for it. Nothing checks the other workspace by a signature, so whoever answers at that address is trusted as yours." A workspace reached over plain HTTP on another machine never counts as your own. The one-time pairing and the one-off sync command work as before.
- **Studio loads again for members and guests where someone was erased.** From 2026-11-15, on a workspace where anyone had been erased, every member and guest was refused the way Studio reads its lists, so Studio did not load for them. The owner was not affected. Studio was fixed on 2026-11-20, and this version serves that way of reading again. Another program that reads this way is refused by a workspace on the previous version until the workspace moves to this one.

The file now stays listed, says that its contents are missing, and opens as soon as a complete copy arrives.
- **"Download a copy" says three numbers.** How many files the copy carries, how many distinct contents that is, and how many files could not be included, each stated rather than worked out from the others.
- **Ask for an app and get one.** The assistant's instructions now say how to write an app when you ask for one, so a plain "build me a tip calculator" is enough. Existing workspaces pick this up with `spl workspace repair --apply`.

## The Honest Reading

**Three places where the workspace told you something that was not quite what it was doing.**

- **A repeating job now shows the hour it actually runs.** If you asked for something to happen
  at nine in the morning in your own timezone, the list of scheduled work showed nine o'clock
  UTC instead, which for most people is a different time of day. The job itself always ran at
  the right hour; only the time you were shown was wrong. That is the more troubling half, because
  a time on a screen is the one you plan your day around.
- **The welcome no longer sends you past your first question.** A new workspace greets you and
  asks you one real question. The greeting said "open a thread and say what you are working on",
  which is a perfectly good instruction and quietly walks you around the question sitting just
  below it. It now points at the question. The question itself is unchanged and still looks like
  any other item, because that is the point of it.
- **A refused save is recorded as refused.** When a workspace declines to save something because
  the credential was not entitled to write it, the record of that decision now says plainly that
  it was enforced. It previously described the workspace's general settings instead, which could
  be read as "we would have declined" when in fact nothing had been saved. Nobody lost work either
  way; the account of what happened is now accurate.

## The Doors Open

**Your work is attributed to you, and only you can write as you.**

- **A device writes as itself and nobody else.** A browser or app paired with your workspace
  could put any name on the work it saved, including yours. It can no longer name anybody but
  itself. If you have invited people in, this is what makes "this was written by Wren" true
  rather than merely claimed, and a teammate's browser can no longer save work under your name.
- **A paired browser is signed in as the person who paired it.** Until now a device you paired
  from the command line was nobody in particular, which is why a second browser could not invite
  anyone even when you could. Pairing now records who did it, so your other devices can do what
  you can do. Devices you paired earlier keep working exactly as before; pair again to give one
  a name.
- **Leaving a workspace.** You could already remove your own membership, and nothing told you so.
  Your workspace now tells a device who it is signed in as, which is what a screen needs before it
  can offer you the option.
- **A workspace can no longer be pointed at the wrong storage by accident.** If a workspace was
  never told where to keep its saved copy, it used to guess, and the guess named real shared
  storage. It now says it has not been told, and a workspace with no storage configured starts
  normally and simply does not publish.

## The Second Person

**You can invite somebody into your workspace, see who joined, and take it back.**

- **Inviting from your own browser.** Most of this existed and was out of reach: the browser you
  opened your workspace in could already add and remove people, and could not create an invitation,
  see the invitations it had sent, or read the record of who used them. All three now work from the
  browser you already use.
- **You can see who joined and when.** The list of invitations shows each person who used one and
  the moment they did. Nothing new is recorded to answer this; it was already known and not shown.
- **Your workspace tells a screen what you may do.** Rather than a screen discovering your
  permissions by trying something and being refused, your workspace says plainly what this device
  may do. A hosted owner previously saw no members page at all for exactly that reason.
- **When somebody's access changes, open screens notice.** Removing a member raises a signal that
  tells other screens to re-check what they may do, instead of waiting for a reload.
- **Two fixes underneath.** A badly formed key is now refused instead of being treated as a
  sign-in, and a workspace that could not recognise its own owner can do so again.

## The Body With History

**Fixes that only show up on a workspace that has been used for a while.**

- **Scheduled work stopped failing on established workspaces.** Six places worked out where they
  were in a workspace's history in a way that was correct on a new workspace and wrong on a busy
  one, including the daily run of a scheduled assistant and the emergency path for getting back
  into a workspace you are locked out of.
- **A restored workspace no longer says "still setting up" forever.** A workspace restored from a
  saved copy, with enough history that first-time setup will never run again, used to report that
  it was configuring and wait for something that could not happen. It now says what is actually
  needed and how to do it.
- **Sending a record is simpler.** Anything sending work into a workspace had to compute a position
  in its history first, which it could not always see correctly. That is now optional and the
  workspace works it out.
- **Testing against realistic workspaces.** Almost every check ran against an empty workspace, and
  the defect that reached people needed one with history. There are now four sizes to test against,
  and the very first run against them found a real problem.

## The Free Clock

**A workspace that has been running for months keeps working like a new one.**

- **Automations work on a busy workspace.** Creating, pausing and resuming a scheduled task
  failed on a workspace with a long history, and worked on a fresh one, which is why it was not
  caught earlier. Pausing and resuming were quietly broken on such workspaces too.
- **A change is in effect before you are told it happened.** Creating a task and immediately pausing
  it could report that the task did not exist, and resuming then pausing could report no change at
  all. Both now answer from the state they actually wrote.
- **A clearer refusal.** When a workspace cannot record something, it now names what it was trying
  to record rather than leaving a gap in the sentence.

## The Standing Order

**You can ask your workspace to do something on a schedule, without being there.**

- **Schedules you can create.** On a hosted workspace you can create an automation, pause it, resume
  it, and see its history.
- **Time zones.** A schedule can name a time zone, so "every weekday at 9" means nine where you
  are. The two awkward days of the year are handled deliberately: the spring change moves the run
  rather than skipping it, and the autumn change runs a fixed-time job once.
- **Nothing runs away with your budget.** A workspace has a daily ceiling across all its scheduled
  work, and you can stop everything at once.
- **Missed runs are visible.** A run that was missed because the workspace was asleep is recorded
  rather than silently skipped, and you choose whether it catches up.

## The Answer Arrives Checkable

**A saved copy of a workspace says what its summaries were computed from.**

- **You can tell whether a summary is current.** When you restore a workspace elsewhere, its
  precomputed answers now say which records they were built from, and you are told plainly whether
  each one is current, partial, out of date, or missing. Before this you had to trust them or
  rebuild them, and rebuilding needed a running workspace, which is the thing a saved copy exists
  to avoid.
- **A read says what it left out.** A filtered result used to look the same as an empty one. It now
  says that it was narrowed, without revealing anything about what was withheld.

## The Current Value

**A workspace can say, once, how to get from a pile of records to the current value of something.**

- **One place to define "the latest".** A team can declare how to reduce many records to the
  current value per item, and every screen and assistant reads the same answer instead of each
  working it out. A list of records stops showing every past version of everything.
- **Assistants can read those answers too.** A scheduled assistant can consult a declared summary
  rather than re-reading raw history.

## The Shared Thread

**Who is on a thread, what each person can do, and what each may see, decided in one place.**

- **A guest sees only what their invitation covers.** A guest whose invitation covered one thread
  could still list things across ten other parts of a workspace. Each of those now answers for the
  person asking: what they may not see reads as missing.
- **Acting as the owner requires being the owner.** Claiming to be the workspace owner now requires
  a sign-in entitled to it, rather than only naming an owner who exists.
- **Adding somebody to one thread.** You can bring a person into a single thread with what they
  need to take part, without giving them the rest of the workspace.

## The Honest Machine

**The workspace says what it did and why, and a failure lands on whoever can fix it.**

- **An assistant is offered exactly the tools its definition names.** Each run records what it
  was offered and names every declared tool it was not offered, with the reason. A definition
  that names no tools is offered none, and naming a tool the workspace does not have is refused
  when you define or shape the assistant.
- **Failures are sorted by who can fix them.** A missing key, a spent budget, a provider that is
  out of credit and a service that is briefly down are told apart. A missing key raises one
  question for you, and answering it once unblocks every run waiting on that key. An unfunded
  provider stops the run with a reason instead of letting the model try again and again. Only the
  mistakes the model can correct go back to it.
- **Notices instead of piles of questions.** Something you may need to know, such as runs failing
  for the same reason, appears once as a notice with a count, and you can acknowledge it. Questions
  stay for things that need your answer.
- **Decide a whole class of suggestions at once.** Suggested rules are grouped by what they are
  about, so you can apply one or stop that kind of suggestion in one step, and a stopped kind
  costs nothing afterwards.
- **Run a schedule by hand.** You can run a scheduled trigger once now, even while it is paused,
  without moving its schedule, and pausing or resuming it survives reinstalling its blueprint.
- **Files travel with a published repository.** Publishing a workspace now carries the files you
  stored in it, and restoring gives them back, each checked against its fingerprint. The publish
  report says whether every file was carried. Files written while the workspace is continuously
  saving to its repository are not carried.
- **Smaller fixes.** A new workspace's welcome thread always shows as your conversation, run lists show the runs you just started, and an assistant started right after an install no longer fails on its first step.

## The Unattended Workspace

**If you use a hosted workspace: it now keeps saving your work on its own through sleep and restarts, and your plan's limits apply to every run.**

- **It keeps saving through every sleep and restart.** If a hosted workspace cannot save when it
  wakes, it tries again on its own within a minute instead of waiting for a restart, and its first
  request after waking no longer fails. Files stored in a workspace are not part of its saved copy,
  and the workspace says so.
- **Scheduled work and sleep.** Schedules run while a hosted workspace is awake.
- **Your plan's limits hold everywhere.** Every run on a hosted workspace with a plan, scheduled
  ones included, follows that plan's limits, and those limits cannot be raised by writing
  configuration.
- **Scheduled assistants can run unattended.** An assistant that runs on a schedule no longer reads
  as done when it promised a result and produced nothing, and a question it asks every day replaces
  yesterday's copy instead of piling up.

For people running their own workspace or using the API:

- `/health` and `spl doctor` say whether a workspace is saving (`attach`), and if not, why and for
  how long. Publish and restore now report that files are not carried.
- A replacement machine for the same workspace takes over saving once the old one stops; while
  the old one still runs, the replacement reports that it cannot save rather than that it is
  standing by.
- An actor's definition can name the threads and kinds its runs write, what they promise to
  produce, and how their effects are undone.

## The Kept Repository

**If you use a hosted workspace: it can keep a saved copy of itself with nothing for you to manage, and when an assistant needs your decision it now offers clear choices.**

- **A saved copy without a key to manage.** A hosted workspace can keep its own repository from the
  moment it is created, and keeps that copy current as you work.
- **Asks you can answer.** When an assistant needs your decision it offers two to six choices,
  each with a line saying what it would do and one it recommends. Pick one, pick several when
  allowed, or answer in your own words, and the work resumes on what you chose.

For people running their own workspace or using the API:

- **One writer at a time.** Publishing takes the repository's write lease before it moves the
  published state, so a second workspace can no longer overwrite a live writer; it is refused by
  name and told who holds the lease.
- **Handing a repository on.** A standby takes over by itself when the lease frees, a clean stop
  hands the lease on after a last flush, and a writer stopped mid-write no longer loses records the
  published state had already committed.
- A hosted workspace declares its repository, publishes it, and becomes its writer, so continuous
  write-back keeps the published copy current.

## The First Question

**A new workspace greets you with one real question: "What are you working on?"**

- **Answering opens your first thread.** The thread is titled with exactly what you typed, and you land inside it. Answering twice takes you to the same thread, never a second empty one. If something fails part way, you keep the thread and the question stays open.
- **Only new workspaces get it.** The question appears when a workspace is first set up with a preset other than `blank`. Existing workspaces gain nothing.
- **Your own wording.** If you run your own workspace, set `SPL_FIRST_RUN_ASK` before the workspace is first configured to change the question.
- **Your call reads honestly.** An empty list means "nothing needs you", not "never set up". Decisions (which need an answer) are counted apart from heads-ups (which need only a nod), and the count says whether it is exact or a minimum.

## The Stranger

**A record you send is stored exactly as you sent it, and the name you get back is the name of what was stored.**

- **Exact numbers.** A number with many decimal places used to be stored with slightly different digits, so a client that worked out its own record name could disagree with the workspace. That is fixed for anything sent to the workspace directly.
- **Fewer repeated suggestions.** When an automated member proposes the same thing over and over, you see one row with a count, and deciding it once settles the whole group. A genuinely new proposal with the same wording shows again.
- **Disk use you can see.** A workspace can say what fills its disk and keep its caches under a limit you set. A disk limit refuses ordinary writes above it but never refuses a settings change, so a limit set too low can always be lifted. With no limit set, a workspace behaves as before.
- **Clearer checks.** `spl doctor` lists the actions available on any open thread.

## The Proven Copy

**Recovery from the copy kept off the machine works, and is checked.**

- **A full rebuild.** A fresh workspace can be rebuilt from the live copy of a busy workspace with every record back under its own name and the same signing keys.
- **What you read is what is stored.** Every way of reading a workspace returns the stored records unchanged, so a name you work out from what you read matches the name the workspace holds.
- **A restore explains itself.** It says what it refused and why, and tells a record whose parent was already missing at the source apart from a record the workspace turned away.
- **Less false alarm.** `spl repo drift` expects a copy taken from a live workspace to run slightly behind, and no longer calls that drift. A missing save is always reported.
- **A safer first start.** A credential request with no credential no longer locks everyone out of a new workspace. On a brand-new local workspace, `spl run` works on its first turn. A local workspace with no model tells you what to do next (`spl config set-key`).
- **Ask, don't guess.** A run asks when its goal is unclear, and pauses until you answer.

## The Seat

**A run that asks you a question pauses, and resumes when you answer.**

- **You know whether answering matters.** If the run behind a question has already ended, the question says so ("an answer records your decision and resumes nothing") and is counted apart.
- **Deleting a file in a member's copy.** A member working in its own copy of a repository can delete a file there, one named file at a time. It can't delete a directory or anything outside its own copy.
- **`spl doctor` says when nothing is happening.** It shows whether the workspace is saved anywhere, and whether an enabled scheduled trigger has a target that is unavailable or has stopped itself.
- **Task briefs are backed up.** Your task briefs join the daily backup.
- **Fixes.** `spl repo drift` no longer reports a faithful copy as drifted. A restore cannot rename a record. A built-in routing rule that failed on most records now works.

## The Faithful Round Trip

**A copy of your workspace is a faithful copy.**

- **Nothing renamed.** Export and import, publish and restore, and the continuous off-machine copy all keep every record under the name it was stored under.
- **Import checks every record.** A bundle cannot smuggle in a record under another name.
- **Records with no thread can be exported again.**
- **One error shape.** Every request with a malformed body gets the same error, whichever endpoint you sent it to.
- **Commands that do what they say.** `spl adapter remove` removes, and `spl repo publish` says plainly when it only staged and did not publish.
- **Recovery on a fresh workspace works.** The documented recovery steps on a new workspace work again.
- **Known limit.** A workspace that has ever retired a member cannot be exported.

## The First Hour

**The first things a new person touches are safer and clearer.**

- **No credentials on a running workspace.** The first-start credential step closes after first start, so nobody can create a credential on a running workspace without one.
- **Fixes.** Writing a record no longer fails on the second call. The command line no longer quietly talks to a different workspace when the one you named is down. `spl health check` no longer calls a healthy workspace unhealthy. `spl token rotate` revokes the old token.
- **Close a thread from the command line.** `spl know`, `spl do` and `spl learn` accept `--fulfills`.
- **Documentation matches the software.** The Quickstart was tested end to end.

## The Door

**The sandbox does real repository work end to end.**

- **A private working copy.** A member actor takes a private copy of the repository, edits and tests the code, and hands back a diff the run names. The rest of the host's files stay read-only, and any attempt to write outside the working copy is refused by name.
- **Runs that wake on new records.** A run can declare what it consumes and what it promises, so a record landing on a thread a live run watches wakes that run.
- **Paid plans take effect.** A subscription's plan now reaches the workspace, within a ceiling no status can exceed.

## The Developer's Day

**You can sit at the terminal with a run.**

- **Fix, check, diff.** A member actor gets its own copy of the repository, runs the repository's declared check, makes the fix, turns the check green, and `spl run` streams it all and prints the diff.
- **A run can only write to its own copy.** A run names a repository rather than a path.

## The Honest Builder

**The instructions a run works under can be edited.**

- **Editable instructions.** The guiding instructions come from a stored prompt at the start of every run, so an override reaches the next run.
- **Short failure reasons.** A failed run says why in one line.
- **Direct record tools.** `query_records` and `emit_record` let a bounded member read and write records directly.
- **Limits you can edit.** The spend and turn limits for each tier are settings you can change.

## The Governed Session

**Engines like Claude Code run as first-class runs.**

- **Same record as a native run.** A dispatched task records its start, its questions and a report with clear outcomes.
- **Your questions, ranked.** `spl register` ranks your open questions, blocking first.
- **Answers become policy.** An answer you give can become a permission rule, a hook, or a remembered fact.

## The Measured Actor

**Actors remember, and search finds the newest first.**

- **Actor memory.** A run can `remember` a fact on the thread it is about. It is private by default and shown the next time that thread is touched.
- **Newest first.** Record search returns the newest matches first.
- **No trial limits for installed actors.** An installed actor runs at its installer's tier.

## The Record That Steers

**A post-tool hook is a record you can write.**

- **Add a lesson.** `core.hook.v1` lets an operator add a short lesson that a running actor is shown after a matching tool call. It takes effect on the next call, with no restart.
- **Observation only.** A hook can add an observation but never silence or reorder anything.

## The Turn That Escalates

**A conversation can run code and use tools when the work needs it.**

- **Escalate when needed.** Instead of replying that it cannot, a reply can escalate to a full tool run. The answer records whether it ran, was refused, or was unavailable.
- **Turn it off.** You can turn this off for a given assistant.

## The Improvement Loop

**You can measure whether an actor is getting better.**

- **Compare definitions.** A run is graded against an evaluation suite, and a new definition is compared with the one it replaced, axis by axis.
- **History.** `spl eval history` shows the graded history for an actor.

## The Self-Configuring Actor

**When an actor needs a service nobody set up, it asks you properly.**

- **A complete proposal.** It names the service, the operations and the credential it needs, instead of failing quietly.
- **Keys stay secret.** You provide the key, and it is stored as a secret, never as a record.
- **See what is reachable.** `spl tool` shows what the instance can reach and whether each tool's credential works.

## The Program That Calls

**A JavaScript program run by an actor can call a granted tool.**

- **One controlled way out.** Network access goes through a single checked route that can refuse a call mid-flight. Every other host is refused.
- **Install the runtime.** `spl runtime install` installs the JavaScript runtime.

## The Kind Decides

**What a program may reach is separate from what it may spend.**

- **Network access is a decision.** A program's network access is checked, not left open.
- **Decision requests work again.** A valid decision request can be answered again from the pending list.
- **Clearer refusals.** An unknown field in a request is refused, naming the fields that are accepted.

## The second principal

**Runs for people other than the owner are sandboxed by default.**

- **Sandboxed by default.** Runs for anyone other than the owner use the sandbox. The owner's own runs stay in process unless they choose otherwise.
- **Missing tools are named.** A tool the sandbox cannot serve is named on the run instead of being dropped silently.
- **Stop takes effect at the next step.** A stopped run ends as cancelled.
- **Approving wakes the run.** Approving a proposal wakes the run that made it, so it reads the decision and finishes.
- **More on every run.** Each run shows what it was told, why a provider failed, and how long each tool took. Runs can be listed across actors, and `spl runs list|show|tail` reads them from the terminal.

## An actor that defines actors

**An actor can propose another actor, and you approve it.**

- **New tools for actors.** Actors can read the roster (`list_actors`), read a run (`explain_run`) and propose a definition (`propose_definition`).
- **You decide.** A proposal reaches you with a complete blueprint and what would change. Approving it installs the blueprint with your own permissions. A proposer can never judge a run of its own proposal.
- **Instructions as a chain.** An actor's instructions can be a chain of prompts.
- **The roster.** `GET /v1/actors/roster` lists every actor with its limits.

## Deploy an actor from a blueprint

An actor is now something you can write down, sign, review and install. A
blueprint can declare an actor with its model, its tools, the words it runs
under and the kinds of record it may write, plus the tools and permission
rules it needs. `spl blueprint plan` shows exactly what would land and a
plan hash; `spl blueprint sign` and `spl blueprint trust-author` establish
who wrote it; `spl blueprint install --accept-plan <hash>` deploys it. The
instance writes the records itself and bounds the actor by what the
installer may grant, so a member cannot deploy an actor with more reach
than they have.

The words are records too. An actor's prompt is a record it names by id,
prompts compose through parents, and every run stamps the exact prompt it
read next to the exact definition it ran under. A prompt that cannot be
resolved refuses the run and says which record is missing.

And a judgment got cheaper: `spl judge <winner> over <loser> --feature short`
records that one thing was preferred over another and what differed, the
smallest signal there is about what you value.

See [Blueprints](/docs/concepts/blueprints#blueprints-that-deploy-an-actor)
and [Actors](/docs/concepts/actors#the-instructions-an-actor-runs-under).

## Intelligent task tooling

The system now turns its own activity log into proactive help.

- **`spl task suggest`** ranks your open tasks by relevance to what you've been working on and tells you what to pick up next. It understands the *meaning* of your recent work (run `spl embed --loop` to enable that), and falls back to a priority-and-recency ranking when the backlog hasn't been embedded yet.
- **`spl task triage`** finds stale open tasks that newer or completed work has likely superseded, pairs each one with its probable replacement, and hands you a reviewable close-list. It never closes anything itself; you decide.
- **`spl insights`** surfaces observations the system noticed on its own: shifts in an actor's recent review outcomes (trust drift) and open work that's been lingering. Run it alongside `spl status` to catch problems before you go looking.

See [Task suggestions & triage](/docs/guides/task-suggestions) and [Insights & observability](/docs/guides/insights-observability).

## Mechanism-independent intelligence: Faculties and the marketplace

Intelligence in Syncropel is no longer assumed to mean "call a language model." A **Faculty** is a deployable unit of intelligence addressed by *what it does*, not *what it's made of*: an LLM, a deterministic solver, a classifier, an external service, or a script can all serve the same capability. Deploy and manage them with `spl faculty deploy / list / show / retire`.

When several Faculties can do the same kind of work, the **calibrated marketplace** routes the work to whichever has earned the most trust at it, measured purely on independently-judged outcomes, blind to mechanism. A non-LLM solver competes on equal footing with a language model, and a fresh candidate has to earn its standing before it can displace a proven one. This was proven end to end: an exact solver and a deliberately-weak heuristic competed for the same capability, their trust diverged on real verdicts, and the system routed new work to the one that actually produced the right answers.

See [Faculties](/docs/concepts/faculty) and [The calibrated marketplace](/docs/concepts/marketplace).

## A friction-free local start

Getting a local instance running is three short verbs, with no credential to manage:

```bash
spl init    # generate your identity + config
spl serve   # start the instance in the background
spl task add "Try out Syncropel"   # works immediately, no token needed
```

The local CLI talks to the instance over a private socket on your machine; filesystem permissions are the authentication, so there's nothing to paste. Bearer tokens are still the right tool when you want to *delegate* scoped access (pairing a browser, a phone, an MCP client, or a remote CLI), but they're no longer in the way of just trying things locally.

See [First run](/docs/get-started/first-run).
