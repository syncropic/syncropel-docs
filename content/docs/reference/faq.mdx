## Vocabulary

### What's an instance?

An **instance** is any running copy of Syncropel: one on your laptop, a hosted one at `<label>.syncropel.app`, or a server you host yourself. Every instance has the same capabilities, wherever it runs. See the [glossary entry](/docs/reference/glossary) and the [federation pair guide](/docs/guides/federation-pair).

### What's a thread? How is it different from a record?

A **record** is the basic unit: one signed item with 8 fields that never changes once written. A **thread** is the piece of work that records belong to. Every record carries a `thread` field, and the records on one thread form a history you read in order to see the current state. See [Records](/docs/concepts/records) and [Threads](/docs/concepts/threads).

### What's a namespace? Is it the same as a tenant?

A **namespace** groups records for access control and sharing. Namespaces form a 5-level hierarchy: `DEFAULT → ORG → PROJECT → ENV → JOB`. Records cross from one namespace to another only with consent. On an instance shared by several customers, each gets a namespace. On an instance run by one person, everything lives in `DEFAULT`. See [Namespaces](/docs/guides/namespaces).

### What's the difference between an actor and a service account?

An **actor** is anyone who writes records: a human (`did:sync:user:alice`), an AI agent (`did:sync:agent:dev`), a system component (`did:sync:system:engine`), or a service account (`did:sync:sa:cmv-adapter`). A **service account** is a specific kind of actor authenticated by a bearer token. Actors are *who*; service accounts are *how a non-human actor authenticates*. See [Actors](/docs/concepts/actors).

## Operations

### How do I switch between instances?

There are three ways:
1. **CLI**: point `spl` at another instance with `SPL_DAEMON_URL=https://<other>.syncropel.app spl <cmd>`, or set it permanently in `~/.syncro/config.toml`.
2. **Web UI**: the profile picker in the status bar switches to a different paired instance.
3. **Browser**: go to `<other>.syncropel.app` directly. You need a bearer token paired for that address.

### Why am I getting `AUTH_REQUIRED` when I `curl` my instance?

Sign-in is required by default. Four possible causes:

1. **No `Authorization` header.** Add `-H "Authorization: Bearer <token>"`. See [Service accounts and tokens](/docs/get-started/service-accounts).
2. **Expired or revoked token.** Verify with `spl serve --status` and re-pair if needed.
3. **Hitting `/v1/health`** (auth-protected, rich body) instead of `/health` (open, minimal liveness). For probes that don't have a token, use `/health` or `/.well-known/syncropel`.
4. **Calling an `--insecure-localhost` instance from another machine.** `--insecure-localhost` listens only on 127.0.0.1, so requests from other machines can't reach it.

For a guided diagnostic, see [Troubleshooting connection](/docs/operate/troubleshooting-connection).

### How do I leave hosted Syncropel and take my data with me?

`spl export` produces a portable bundle (records, threads, federation pairs, secrets, consent grants, identity); `spl import` loads it into a fresh instance. Hosted and self-hosted behave the same, so [every customer can leave at any time](/docs/concepts/federation). See [Portability](/docs/guides/portability).

### How do I reset trust scores?

Trust is built from records on the actor's trust thread. To reset it:
1. Stop new evidence from accumulating by removing or replacing the relevant routing rules (use `spl trigger pause` or `spl trigger remove` for a trigger).
2. Write a `LEARN` record on `th_trust_<actor>` with `body.kind = "trust.reset.v1"`.
3. The next trust query counts only evidence recorded after the reset.

Resetting is rarely the right move. It is usually better to add more evidence than to discard history.

### Why did my `spl task dispatch` fail with `E2BIG` (Argument list too long)?

Older versions passed briefs over about 7 KB on the command line, which can exceed the operating system's limit. Upgrade with `curl -sSf https://get.syncropic.com/spl | sh` and restart your instance.

If you still see this after upgrading, open an issue and include the output of `spl version`.

## Hosted vs. self-hosted

### Where does my data live in hosted mode?

On your own hosted instance, in its own record store on persistent storage. We manage snapshots for you, and you can take a full copy with `spl export` at any time. See [Hosted instance signup](/docs/get-started/hosted).

### Can I federate hosted ↔ self-hosted?

Yes. `spl federation pair` works wherever each peer runs. You can have a laptop self-hosted instance paired with a hosted instance and a friend's self-hosted instance simultaneously. See [Federation pair](/docs/guides/federation-pair).

### Is there a free trial?

No. Your first workspace is **Free** instead, with no card and no time limit. When you want more storage, included assistant use or a name for your organization, move it to **Pro** ($25 a month per workspace) and keep everything in it. See [Plans and billing](/docs/get-started/pricing).

## Federation

### What's a federation pair?

A lasting link between two workspaces, established by `spl federation pair add <peer-url>`. The pair holds both sides' DIDs, scoped tokens, and a state (`active` / `paused` / `degraded` / `revoked`). All sync between the two goes through the pair; without a pair, nothing syncs. See [Federation pair](/docs/guides/federation-pair).

### Is federation push or pull?

**Pull-first.** Bob's instance asks Alice's `/v1/sync/changes` endpoint for new records. Alice never pushes to Bob, so each side controls how fast it takes in records.

### Can I revoke a pair?

Yes: `spl federation revoke <peer-did | pair-id>`. This cannot be undone. To connect again, run a fresh `spl federation pair` handshake. The revocation is saved as a record, so the history of who paired with whom is kept.

## Troubleshooting

### My provisioning failed with "provisioning did not complete"

Setting up the instance took longer than expected. It may already be running. Wait 30 to 60 seconds and try signing up again with the same label. If it keeps failing, use the retry link on the page and include its diagnostics when you contact support.

### `spl federation pair` returns "manifest signature does not verify against advertised DID"

The peer's `/.well-known/syncropel` manifest carries a signature that doesn't match the DID it claims. Possible causes: the peer runs an older version, a key change hasn't reached you, or someone is intercepting traffic (rare). On the peer, run `spl identity verify` to confirm its local key matches the DID it publishes. See the [federation pairing guide](/docs/operate/federation-pairing).

### Where do I find logs?

Three places, depending on what you need:

| Surface | Command | What's there |
|---|---|---|
| Instance logs | `spl serve --logs` (or `~/.syncro/logs/spl.log`) | The instance's own log lines. |
| Records | `spl thread records <thread-id>` | Anything saved as a record (most of what happens). |
| Trace correlation | `spl logs --trace-id <id>` | All log lines and records sharing one trace ID. |

For dispatch debugging specifically, `spl task diagnose <id>` walks the records on a dispatch thread. See the [dispatch observability guide](/docs/guides/dispatch-observability).
