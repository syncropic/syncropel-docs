description: The app read door (dark on hosted) and the first stage of publishing a workspace's pages. Since v0.279.
---

Two doors arrive in v0.279.0 behind flags. Both are dark by default on hosted workspaces. A dark door answers exactly as an unknown route does (same status, body, headers and timing), for every method including `OPTIONS` and `HEAD`. A client can't tell a dark door from a path that doesn't exist.

## Apps read live data

A `core.app.v1` record can declare what it reads:

```json
{ "reads": { "kinds": ["core.task.record.v1"], "threads": [] } }
```

The declaration is checked when the app is saved. A bad one is `422 APP_READS_INVALID {field, reason}`. The rules:

- `kinds` is an exact allow-list of registered record kinds. Account, keyring, private and kept, connection plumbing, run internals, engine config, assistant memory and site kinds are never readable.
- System threads (`th_site*`, `th_alerts`, and the like) are never readable.
- Each thread must be one its writer can read.
- A later version can't widen `reads` unless the basis person is the head's or the owner. A `venture update` that widens an app's `reads` is a definitions widening by id `app:<title>` and is refused with `UPDATE_WIDENING_NOT_ACCEPTED` unless accepted.
- Package apps declare kinds only.

`POST /v1/apps/{app_id}/read` (flag `apps_read`, scope `records:read`) serves each viewer their own reach intersected with the head's `reads`.

| Status | Code | Meaning |
|---|---|---|
| `404` | `APP_NOT_FOUND` | One answer for an unknown, unreachable or hidden app. |
| `404` | `APP_HAS_NO_READS` | The app declares no `reads`. |
| `403` | `APP_READ_UNDECLARED` | The request names something the app didn't declare. |

A by-id read of anything absent, unreachable or undeclared answers `{record: null}`. An answer holds at most 200 rows and 1 MiB, with `read.truncated {at, next}` when cut short. The cursor is sealed and bound to the viewer, app, head and filter. A read through an app counts as the viewer's read: the owner's `GET /v1/reads` shows it with `reader_kind: app`, door `app:<root>`, and `app {id, title}`, `via` and `for_name`.

An app's code receives the raw actor ids of the records it reads, exactly what `POST /v1/records/query` serves that viewer.

Person-facing words, from the manifest: {/* story: draft (all four approved D540/D357 in the manifest; placement here for story to confirm) */}

- `APP_READS_INVALID`: "This app's list of what it reads has a problem, so it wasn't saved." followed by the reason line.
- `APP_NOT_FOUND`: "This app isn't available to you."
- `APP_READ_UNDECLARED`: "This app tried to read something it didn't say it would, so nothing was read."
- `APP_HAS_NO_READS`: "This app doesn't read anything." (never shown on screen; the command line and developers only)

## Publishing pages (stage 1)

Stage 1 lets the owner publish an app's files as a page at the workspace's own address. The `sites` flag gates the doors.

- `core.app.v1` gains `slug`: this workspace's own label, set by the owner. One holder per slug.
- `POST /v1/sites/propose` raises a publish proposal (`proposal.proposes: "publish"`). The owner's yes at `POST /v1/decisions/{id}/decide` settles it. The proposal is bound to `{site, version, manifest_digest}` and rebuilt when accepted. Only a closing admitted as one settles a proposal.
- `GET /v1/sites` lists published sites. `POST /v1/sites/unpublish` and `POST /v1/sites/checked` complete the doors.
- The history lives on `th_site_<label>`, which is the kernel's alone: a client write to any thread whose id starts `th_site_` is `403 SITE_THREAD_KERNEL_ONLY`. A thread of your own with that prefix keeps its records. Write new ones to a differently named thread.
- Records: `core.site.publish.v1`, `core.site.publish_result.v1`, `core.site.purge.v1` (kernel kinds) and `core.site.checked.v1` (owner kind), all owner-read only.
- A file's first write now also writes a `core.data.revision.v1` (`prev_hash: null`) naming its writer. Files uploaded before 0.279 have no first revision: re-save such a file to publish it (`SITE_FILE_NOT_OWNERS` until then).
- A site file an erase withheld is served nulled by every door: `{path: null, sha256: null, removed_by_erase: true}`, to the owner too.
- Overrides: `SPL_SITES_DOOR_URL` (the publishing service's address) and `SITES_RECEIPT_PUBLIC_KEY` (normally fetched from `GET /v1/sites/keys`).

Not in this stage: a node sealed to a person is never published (`SITE_SOURCE_PRIVATE`). Two apps holding one address after a merge import fold to the older claim. The assistant has no publish tool, so the owner proposes.

Person-facing words for the refusals come from the manifest (approved D540, D541 and D545). Quote the manifest entry for each code, don't write new ones. Examples: {/* story: draft (approved entries quoted; placement for story to confirm) */}

- `SITE_THREAD_KERNEL_ONLY`: "Only the workspace itself writes a page's history, so this wasn't saved."
- `SITE_FILE_NOT_OWNERS`: "That file wasn't added by the owner, so it can't go on a page."
- `SITE_SOURCE_PRIVATE`: "Only some people can read that file, so it can't go on a page."
- `SITE_PUBLISH_STALE`: "The files changed since this was asked, or it was asked more than a day ago, so nothing was published. Ask again."
