| Flag | Description |

## Server

```bash
# Short verbs (canonical for operator interactive use)
spl serve            # start the instance in the background
spl stop             # stop the running instance
spl restart          # stop + start

# Full form (canonical for systemd, Docker, K8s, managed cloud platforms, and other process supervisors)
spl serve [--port 9100] [--memory] [--echo] [--store sqlite:///path]
spl serve --daemon
spl serve --stop
spl serve --restart
spl serve --status
spl serve --logs [-n 100] [--no-follow]
spl serve --insecure-localhost
spl status
spl version
```

`--port` and `--host` follow one precedence everywhere (`serve`, `start`, `stop`, `restart`): an explicit flag wins, then the `[server]` block in `~/.syncro/config.toml`, then the compiled default (`9100` / `127.0.0.1`). Before spawning, the instance probes the target port and **refuses to start** when something is already serving there — you get an immediate error naming the port instead of a phantom second daemon.

`spl serve` / `spl stop` / `spl restart` are convenience aliases over the instance-mode `spl serve` flags. Use them for interactive work. Use `spl serve` (foreground) under process supervisors that expect the instance to stay attached for log capture + restart-on-crash semantics — systemd `Type=simple` units, Docker `CMD`, Kubernetes pods, and managed cloud platforms.

| Command | Description |
|---|---|
| `serve` | Start the Syncropel server |
| `serve --daemon` | Start in background mode |
| `serve --memory` | Use ephemeral in-memory store (for development) |
| `serve --echo` | Echo mode — no AI provider needed |
| `serve --stop` | Stop the background instance |
| `serve --restart` | Stop the instance if running, then start in background mode |
| `serve --status` | Print instance status without starting the server |
| `serve --logs` | Tail the instance log file. `-n` controls the initial line count; `--no-follow` prints once and exits |
| `serve --insecure-localhost` | Dev escape hatch: skip bearer-token authentication. Forces the instance to bind to `127.0.0.1` regardless of `--host` and emits a WARN log on startup. Intended for local dev instances and E2E tests — never pass in production |
| `status` | Show server health, uptime, record count |
| `version` | Show version |

### Run as a system service

On Windows, register the instance with the Service Control Manager so it survives logoff and starts at boot. See the [Windows service guide](/docs/operate/windows-service) for the full runbook.

```bash
spl serve --install-service [--service-name <name>]
spl serve --uninstall-service [--service-name <name>]
```

| Flag | Description |
|---|---|
| `--install-service` | Register `spl serve` with the Windows Service Control Manager. Must be run from an elevated shell. Idempotent: if a service with this name already points at the current binary, succeeds without changes |
| `--uninstall-service` | Remove the SCM registration. Stops the service first if running. Safe on a host that does not have the service installed |
| `--service-name <name>` | Override the default service name (`SyncropelInstance`). Useful on multi-instance hosts |
| `--service` | Internal — invoked by the SCM when the service starts. Operators should not pass this directly |

On Linux and macOS these flags return a clear error and point at systemd / launchd. See the [operator runbook](/docs/operate/runbook) for the systemd unit template.

## Reset

```bash
spl reset                   # interactive: print plan, prompt, back up hub.db, wipe
spl reset --dry-run         # print plan + exit (no prompt, no backup, no deletes)
spl reset --force           # skip the confirmation prompt
spl reset --json            # structured output (composes with all flags)
spl reset --keep-keys       # preserve identity (same DID after re-init)
spl reset --keep-config     # preserve config.toml
spl reset --keep-secrets    # preserve secrets/
spl reset --wipe-task-data  # also delete ~/.syncro-data/ (extra confirmation)
```

Wipes `~/.syncro/` back to a fresh state by listing the directory at runtime and deleting every entry not protected by a `--keep-*` flag. With no `--keep-*` flag the home dir itself is also removed, so the next `spl init` works without `--force`.

Refuses if any of four signals indicate an instance is running: PID file at `~/.syncro/run/spl.pid`, Unix socket connect, TCP `127.0.0.1:9100` connect, or `systemctl --user is-active spl-serve.service`. The TCP and systemd signals are scoped to the default `~/.syncro/` home so `SYNCROPEL_HOME=/some/other/path` invocations don't false-positive on unrelated instances. If you use a systemd user unit, stop it (`systemctl --user stop spl-serve.service`) — `spl stop` alone is insufficient because the unit respawns the instance.

Backs up `hub.db` to `~/.local/share/syncropel/backups/hub.db.pre-reset.<iso8601>` (outside `~/.syncro/` so the backup survives the reset) before deleting anything. Never touches `~/.syncro-data/` (task content + alias mappings) by default.

| Flag | Description |
|---|---|
| `--dry-run` | Print the plan + exit cleanly. No prompt, no backup, no deletes. Scriptable; useful as a CI gate that asks "what would reset touch right now" |
| `--force` | Skip both the main confirmation prompt and (when combined with `--wipe-task-data`) the extra task-data prompt |
| `--keep-config` | Preserve `config.toml` so API keys, routing rules, and CORS settings survive the reset |
| `--keep-keys` | Preserve `keys/` so the actor DID stays the same after `spl init` (use when rolling back a corrupted record store without re-establishing identity) |
| `--keep-secrets` | Preserve `secrets/` (encrypted API keys + secret backend) |
| `--wipe-task-data` | ALSO delete `~/.syncro-data/` — destructive, requires an additional `[y/N]` prompt unless paired with `--force` |
| `--json` / `-o json` | Emit a `reset_outcome` JSON envelope with the plan, backup path, deleted/failed counts, and the OS-keyring caveat |

The full reset/uninstall guide is at [Reset and Uninstall](/docs/get-started/reset-uninstall) — including the manual `rm -rf` fallback for when `spl` itself is broken and can't run `spl reset`.

## Find

Blended text search over file names, file contents, and conversations — ranked together, with snippets. No embedding provider needed; see the [Find guide](/docs/guides/find).

```bash

spl find "budget" --types material --limit 5      # files only

spl find --rebuild --scope all                    # drop + re-index (incremental, safe live)
```

## Search

Semantic search over the record log. Embeds the query through a configured provider and returns the top K records ranked by cosine similarity. See the [semantic search guide](/docs/guides/search) for setup and patterns.

```bash
spl search "authentication failure logs" -k 10
spl search "query" --thread th_abc --actor did:sync:agent:dev --kind core.task.record --after-clock 100
spl search "query" --json | jq '.hits[].record.id'
```

Requires an embedding provider configured first — see the [Configuration → Embedding provider](#embedding-provider) section below.

### Judgments

```bash
spl judge <winner> over <loser> [--feature F]... [--loser-feature F]... [--basis "..."] [--thread T]
```

A pick is the cheapest judgment there is: this record over that one, and the
features that separated them. `--feature` names something the winner has and
the loser lacks; `--loser-feature` the reverse. Both candidates must be
records the instance holds; the verdict lands on the winner's thread unless
`--thread` says otherwise, and both candidates ride as its parents.

## Blueprints

```bash
spl blueprint init [name] [--author DID] [--output FILE]
spl blueprint plan <file> [--extends PARENT]... [--regime self-host|hosted]
spl blueprint sign <file> [--extends PARENT]... [--key-file PATH]
spl blueprint trust-author [--author-did DID] [--public-key B64] [--key-file PATH] [--revoked-after UNIX]
spl blueprint install <file> [--extends PARENT]... --accept-plan <hash>      # alias of materialize
```

`plan` reviews without writing anything: actors, tools, rules, triggers and
the plan hash. `sign` signs the file in place with a 32-byte signing key
(default `~/.syncro/secrets/operator-identity.key`); `trust-author` records
that key as trusted on the instance. `install` sends the blueprint to the
instance, which re-checks consent and the installer's bounds before writing.

## Files

Browse and manage an instance's [filesystem](/docs/concepts/files). See the
[filesystem guide](/docs/guides/filesystem) for a walkthrough.

```bash
spl fs ls [PATH]                 # list a directory (defaults to the root)
spl fs stat <PATH>               # show a path's metadata
spl fs cat <PATH>                # print a file's contents to stdout
spl fs cp <LOCAL> <DEST>         # upload a local file into /files
spl fs mkdir <PATH>              # create a directory
spl fs mv <FROM> <TO>            # move or rename a path
spl fs rm <PATH> [--recursive]   # remove a file, or a directory and its contents
spl fs publish <PATH>            # promote a working file to an immutable artifact
spl fs mounts                    # list connected external drives
```

| Command | Purpose |
|---|---|
| `ls` | List a directory — `/files`, `/artifacts`, `/mnt/<name>`, `/threads` |
| `stat` | Metadata for one path — kind, size, content hash |
| `cat` | Print a file's bytes to stdout |
| `cp` | Upload a local file into the `/files` working area |
| `mkdir` | Create a directory |
| `mv` | Move or rename a path |
| `rm` | Remove a path — `--recursive` for a non-empty directory |
| `publish` | Promote a working file to a permanent, read-only artifact in `/artifacts` |
| `mounts` | List external drives mounted into the instance |

Every subcommand accepts `-o json` (or `--json`) for scripting.

## Workspaces

A workspace is a `core.workspace.v1` record that carries an interactive
surface. You install one from a document file at runtime — no rebuild. See
[the workspace concept](/docs/concepts/workspaces) for the full picture.

```bash
spl workspace install <file>
spl workspace update <slug> <file>
spl workspace list
spl workspace show <slug>
spl workspace archive <slug>
spl workspace subscribe <workspace-ref> [--version-pin <sha-or-label>] [--pinned-publisher <did>] [--grant <scope>] [--federated | --private]
spl workspace unsubscribe <workspace-ref> [--reason <text>]
```

| Command | Description |
|---|---|
| `workspace install <file>` | Validate a `core.workspace.v1` document file and emit it onto the instance's workspace catalog. The workspace is live immediately |
| `workspace update <slug> <file>` | Re-emit the workspace under an existing slug. The file's `meta.slug` must match. Identical content is a no-op |
| `workspace list` | List the workspaces the instance serves — the latest record per slug |
| `workspace show <slug>` | Print the full `core.workspace.v1` body — `meta`, `capabilities`, `regions`, `lifecycle` |
| `workspace archive <slug>` | Re-emit the workspace with `lifecycle: "archived"` — soft delete; existing subscriptions keep working |
| `workspace subscribe <ref>` | Record your subscription to a workspace by its content hash, optionally pinning a publisher and version. Namespace-local unless `--federated` |
| `workspace unsubscribe <ref>` | Re-emit the subscription as inactive (records are immutable; no delete) |

Workspaces are walked in [Build your first workspace](/docs/tutorials/first-workspace).

## Chrome

Your instance's chrome — the navigation rail, side panels, and footer that
wrap every screen — is a `core.instance.shell.v1` record. The `spl chrome`
family authors it. See [the instance chrome
concept](/docs/concepts/instance-chrome) for the full picture.

```bash
spl chrome show [--published]
spl chrome init [--template <name>] [--force]
spl chrome validate <file>
spl chrome publish
spl chrome archive
```

| Command | Description |
|---|---|
| `chrome show` | Print the current chrome record — the draft if one exists, otherwise the published record. `--published` forces the published lookup |
| `chrome init` | Scaffold a draft `core.instance.shell.v1` from a bundled template. `--template` is one of `personal` (default), `graph-showcase`, `library`, `team`. Fails if a draft already exists — re-run with `--force` to overwrite |
| `chrome validate <file>` | Schema-check a `core.instance.shell.v1` body in a local file. No instance needed — good for pre-commit hooks. Exit `0` on valid, `1` on invalid |
| `chrome publish` | Promote the current draft to `lifecycle: published` — the live chrome that `GET /v1/instance/shell` serves and renderers draw |
| `chrome archive` | Archive the published record. Renderers fall back to the bundled default chrome |

The command is named `chrome`, not `shell`, to keep it clear of the
"shell = terminal" reflex; the record it writes is `core.instance.shell.v1`.

## Share

One-shot bug-repro bundles. Share a thread (with explicit consent) so a
developer can replay the exact records that triggered an issue.

```bash
spl share send <thread-id> --to <recipient-did> [--include-deps] [--depth <n>] [--expires <duration>] [--out <path>]
spl share receive <bundle-path> --from <sender-did> [--dry-run]
```

| Command | Description |
|---|---|
| `share send <thread> --to <did>` | Bundle the thread's records as JSON Lines, emit a consent record granting the recipient read access, write a single-file bundle |
| `share send --include-deps` | Walk parent edges recursively so cross-thread parent chains land in the same bundle. Bounded by `--depth` (default 8, hard cap 10K records) |
| `share send --expires <duration>` | Time-bound the consent. Format: `7d`, `24h`, `45m`, `30s` |
| `share send --out <path>` | Write the bundle to a specific path. Default: `<thread>.bundle.jsonl` |
| `share receive <bundle> --from <did>` | Verify signatures and content hashes, replay records into the local instance |
| `share receive --dry-run` | Verify the bundle without ingesting (good for sanity-checking before replay) |

The bundle format is just records. The receiving instance ingests them through
the same path it uses for any record. Tampering is detectable — re-hashing
the seven-field record envelope catches any mutation.

## Secrets

Operator-facing surface for managing credential handles. Syncropel stores the handle + audit metadata; the value lives in your OS keychain (or the backend you reference). See [Secrets concepts](../concepts/secrets) for the four-layer enforcement design.

```bash
spl secret set <handle>          # interactive — TTY echo disabled, or piped stdin
spl secret get <handle>          # returns metadata only (no value)
spl secret get <handle> --reveal # prints value (warns to stderr)
spl secret list                  # tabular: handle, backend, lifecycle, last_accessed
spl secret promote <ENV_VAR>     # graduate env var to OS keychain after confirmation
spl secret delete <handle>       # tombstone descriptor + audit record
```

| Command | Description |
|---|---|
| `secret set <handle>` | Reads value from a TTY (`tcsetattr` echo disabled) or piped stdin. Never accepts a `--value` flag. Writes a `core.credential.v1` descriptor + sets the value at the configured backend |
| `secret get <handle>` | Returns the descriptor metadata. Audit record emitted before the response returns (record-before-result invariant) |
| `secret get <handle> --reveal` | Prints the value to stdout. Audit record marks `outcome: allowed` with `purpose: revealed_to_operator` |
| `secret list` | Lists every credential descriptor visible to the caller. Backend resolution is lazy — listing does not unlock values |
| `secret promote <ENV_VAR>` | Reads the named environment variable, prompts confirmation, writes the value to the OS keychain, emits the descriptor + a `secret.access.v1` audit record |
| `secret delete <handle>` | Marks the descriptor `lifecycle: erased` and removes the value from the backend. The descriptor record stays in the audit log |

Backend URI schemes shipped today:

- `keychain://syncropel/<handle>` — platform-native (macOS Keychain, Linux Secret Service, Windows DPAPI/Credential Manager)
- `env://VAR_NAME` — read-only env-var resolver (compiles + tests on every platform)

Future schemes: `1password://`, `vault://`, `kms://`.

### Indexed field registry

Declare which `body.<field>` paths for a given `body.kind` should be backed by SQLite expression indexes. See the [body-kind manifest guide](/docs/guides/body-kind-manifest) for when and why.

```bash
spl config add-body-kind-manifest \
  --kind music.catalog.track \
  --indexed-field body.title \
  --indexed-field body.artist_id \
  [--description "..."] [--disable]

spl config list-body-kind-manifests [-o json]
```

The instance applies manifests at config-reload time: each declared field becomes a `CREATE INDEX ... ON records(json_extract(body, '$.<field>'))` so rich-query filter predicates on that path use the index transparently. Re-adding the same `--kind` replaces the manifest (latest LEARN wins).

### Embedding provider

Configure the provider used for [semantic search](/docs/guides/search). Writes an `embedding_provider` LEARN record on `th_engine_config`; the instance rebuilds its embedder on broadcast — no restart. The `ollama` provider ships today; hosted adapters land in a subsequent release.

```bash
# Enable semantic search against a local Ollama (nomic-embed-text is the default model).
spl config embedding-provider set ollama \
  [--endpoint http://localhost:11434] \
  [--model nomic-embed-text]

spl config embedding-provider show
spl config embedding-provider clear             # disable semantic search
```

Without a configured provider, `spl search` and `POST /v1/records/search` return 503 and both SDKs surface a `disabled: true` flag instead of raising.

### Async federation relay

Configure relay mailboxes for peers that aren't always online. See the [async federation guide](/docs/guides/async-federation) and the [relay runbook](/docs/operate/relay) for setup and operation.

```bash
spl config relay set <url> [--for-pair <did|all>]
spl config relay show
spl config relay status [--for-pair <did>]
spl config relay clear [--for-pair <did|all>]
spl config relay push --peer <did> --thread <thread_id>
```

| Command | Description |
|---|---|
| `relay set` | Configure a relay URL for a peer. `--for-pair` defaults to `all` — the catch-all applied to any peer without a more specific mapping |
| `relay show` | List configured relay entries |
| `relay status` | Probe configured relays against their `/health` endpoint. With `--for-pair <did>`, probes only the relay that would be used for that peer (specific match or catch-all fallback) |
| `relay clear` | Remove a relay entry. `--for-pair` defaults to `all` to drop the catch-all; pass a DID to clear a specific mapping |
| `relay push` | Deposit one thread's records into the configured peer's relay mailbox. Used when a direct pair is known to be offline. Returns an envelope ID on success |

Relay entries are stored as `federation.relay` LEARN records on `th_engine_config`. Outbound `set` / `clear` / `push` take effect immediately; enabling a new relay URL for **inbound** receive requires an instance restart, since the receive loops are spawned at startup.

```bash
# Catch-all: route to the hosted relay for any peer without a specific mapping
spl config relay set https://relay.syncropel.com

# Override for one peer
spl config relay set https://my-relay.example.com --for-pair did:sync:peer:alice

# Deposit a thread now
spl config relay push --peer did:sync:peer:alice --thread th_abc123...
```

### Responder manifest overrides

Curate the responder list surfaced on `/v1/capabilities` and `/.well-known/syncropel`. The manifest auto-populates from actor/adapter records; these commands let operators add custom entries, override auto-populated values, or suppress specific DIDs.

<Callout type="info">
The responder manifest is dormant in this release — the schema is persisted and surfaced on discovery endpoints so peers can already read it, but the instance does not yet consume these fields for its own routing decisions. A subsequent release will make them load-bearing. Configure now if you're already coordinating cross-peer discovery; otherwise there's no rush.
</Callout>

```bash
spl config responders-add --did <did> [--kind <kind>] [--capability <tag>]... \
  [--trust-floor <json>] [--cost-model <json>] [--availability <json>] [--metadata <json>]
spl config responders-list [--json]
spl config responders-remove --did <did>
```

| Flag | Applies to | Description |
|---|---|---|
| `--did <did>` | `add`, `remove` | Target responder DID (actor or synthetic). Required |
| `--kind <kind>` | `add` | `actor`, `llm`, `pattern`, or `system`. Omitted defers to the auto-populated value; when none exists, defaults to `actor` |
| `--capability <tag>` | `add` | Repeated. Passing this replaces the entire capability list for this DID |
| `--trust-floor <json>` | `add` | JSON trust-floor object, e.g. `{"code": 0.75}` |
| `--cost-model <json>` | `add` | JSON cost-model object, e.g. `{"per_query_usd": 0.04}` |
| `--availability <json>` | `add` | JSON availability object, e.g. `{"timezone": "PST"}` |
| `--metadata <json>` | `add` | Free-form, non-normative JSON object |

`responders-add` overrides matched auto-populated entries; unmatched DIDs are appended as operator-authored. `responders-remove` tombstones a DID so it is suppressed from the manifest even if an auto-populated entry exists.

```bash
# Advertise a custom responder with an explicit cost model
spl config responders-add \
  --did did:sync:agent:reviewer \
  --kind actor \
  --capability code \
  --capability review \
  --cost-model '{"per_query_usd": 0.02}'

# Hide an auto-populated entry
spl config responders-remove --did did:sync:agent:deprecated
```

## Inference — `spl infer`

Emit an `infer.query.v1` INTEND and (by default) wait for the KNOW. See the [Inference guide](/docs/guides/inference/overview) for what every field means.

```bash
spl infer <goal> --responder <KIND:SELECTOR> [--responder ...] \
  [--kind <body.kind>] \
  [--fold consensus|best_of|waterfall_first|ensemble_weighted|expression] \
  [--fold-expression <CEL>] \
  [--orchestration single_shot|verify|waterfall|retry_on_low_confidence|escalate|ensemble_with_audit] \
  [--dial <0..1>] \
  [--budget <USD>] [--timeout <seconds>] \
  [--min-quorum <int>] [--top-k <int>] [--relevance-threshold <0..1>] \
  [--answer-schema <URI>] \
  [--reversible] \
  [--obligation-resolution lwd|fulfills_wins|validation_error] \
  [--metadata k=v] [--thread <id>] [--actor <did>] \
  [--wait | --no-wait] [--poll-interval-ms 500] [--poll-timeout-secs 300]
```

### Responder selector grammar

| Form | Maps to |
|---|---|
| `llm:<model>` | `{ kind: "llm", model: "<model>" }` |
| `llm:<model>:<did>` | `{ kind: "llm", model: "<model>", did: "<did>" }` |
| `pattern:<capability>` | `{ kind: "pattern", capability: "<capability>" }` |
| `actor:<did>` | `{ kind: "actor", did: "<did>" }` |
| `system:<domain>` | `{ kind: "system", domain: "<domain>" }` |
| `capability:<domain>:<kind>` | `{ kind: "any", domain: "<domain>", capability: "<kind>" }` |
| `cel:<expression>` | `{ kind: "any", expression: "<expression>" }` |

### Three flag combinations

**Simple — two responders, default consensus fold, budget ceiling:**

```bash
spl infer "summarise this paper" \
  --responder llm:sonnet \
  --responder pattern:summary-v2 \
  --fold consensus \
  --budget 0.50 \
  --wait
```

**Verify orchestration with human tiebreaker:**

```bash
spl infer "review this diff" \
  --responder llm:sonnet-4-6 \
  --responder actor:did:sync:user:alice \
  --orchestration verify \
  --budget 0.40 \
  --timeout 1800
```

**No-wait fire-and-forget for long-running queries:**

```bash
spl infer "long research task" \
  --responder llm:opus \
  --budget 2.00 \
  --timeout 3600 \
  --no-wait
# prints: correlation_id: <sha256>; thread_id: th_<sha256>
# poll: spl thread show <thread>
```

For queries more complex than the CLI can build, pipe a JSON file:

```bash
spl infer --query-file query.json --wait
```

## Work loop — `spl work-loop`

Run a records-native work loop with workspace tools. The loop emits records onto its thread as it works (`core.work.turn.v1`, `core.work.tool_call.v1`, etc.); the engine decides terminal success in `--verify` mode. See the [Work loop concept page](/docs/concepts/work-loop) for the full primitive.

```bash
spl work-loop "<goal>" \
  [--workspace <DIR>] \
  [--max-turns <N>] \
  [--model <NAME>] \
  [--tools <CSV>] \
  [--remote] \
  [--verify] \
  [--token <BEARER>] \
  [--json]
```

| Flag | Meaning |
|---|---|
| `<goal>` | The goal in natural language (positional, required). |
| `--workspace <DIR>` | Directory the workspace tools (`read`/`write`/`bash`/etc.) are confined to. Default: current dir. |
| `--max-turns <N>` | Cap on loop turns. Default: 20. Tier ceilings may clamp this below the requested value. |
| `--model <NAME>` | Inference model. Default: `claude-sonnet-4-6`. |
| `--tools <CSV>` | Allowlist of tool names (comma-separated). Default: all available tools. |
| `--remote` | Run the loop on the instance (built-in tools, no host `bash`) instead of in-process. Records land on the instance and the thread is watchable from anywhere. |
| `--verify` | Run under independent evaluation: a planner expands the goal into acceptance criteria, a separate evaluator judges the result, and the loop never self-asserts "done". Forced on for Trial-tier actors. |
| `--token <BEARER>` | Bearer token for instance auth. Precedence: `--token` > `SPL_TOKEN` env > `~/.syncro/token`. |
| `--json` | Emit machine-readable progress instead of pretty text. |

```bash
# Local in-process run, no verify
spl work-loop "Summarise this week's dispatches"

# Instance-run, verified, JSON output
spl work-loop "Find every record tagged 'beta' and emit consent grants" \
  --remote --verify --json
```

## Review a work loop — `spl work-loop-review`

Record an external verdict on a completed work loop. This is how a loop's outcome is judged: an actor with standing accepts or rejects what the loop produced, and that verdict folds into the loop actor's [trust](/docs/concepts/trust). A loop's own self-reported outcome never earns it trust — only this external verdict does, and it must come from a different actor than the one that ran the loop. See the [work loop concept page](/docs/concepts/work-loop#the-cognitive-loop-read-do-be-judged).

```bash
spl work-loop-review <THREAD> \
  [--accept | --reject] \
  [--domain <DOMAIN>] \
  [--notes <TEXT>] \
  [--token <BEARER>] \
  [--json]
```

| Flag | Meaning |
|---|---|
| `<THREAD>` | The loop's thread id (`th_…`), or a unique prefix (positional, required). |
| `--accept` | Accept the loop's outcome. This is the default if neither flag is given. |
| `--reject` | Reject the loop's outcome. |
| `--domain <DOMAIN>` | The work domain this verdict counts toward (e.g. `code`, `research`). Default: `general`. |
| `--notes <TEXT>` | Review notes on an accept, or the reason on a reject. |
| `--token <BEARER>` | Bearer token for instance auth. Precedence: `--token` > `SPL_TOKEN` env > `~/.syncro/token`. |
| `--json` | Emit machine-readable output. |

```bash
# Accept a loop's work, attributed to the "code" domain
spl work-loop-review th_a1b2c3 --accept --domain code --notes "tests pass, change is clean"

# Reject with a reason
spl work-loop-review th_a1b2c3 --reject --domain code --notes "introduced a regression in the parser"
```

## Namespaces

5-level hierarchy for tenancy, governance, and policy composition. See the [Namespaces concept page](/docs/concepts/namespaces).

```bash
spl namespace create <id> [--description X] [--policy X]
spl namespace list [--json]
spl namespace show <id> [--json]
spl namespace archive <id>
spl namespace delete <id>
```

Namespace IDs are slash-separated, max 4 segments under DEFAULT, lowercase ASCII + digits + `-` + `_`:

```bash
spl namespace create acme-corp                              # ORG
spl namespace create acme-corp/payments                     # PROJECT
spl namespace create acme-corp/payments/staging             # ENV
spl namespace create acme-corp/payments/staging/job-42      # JOB
```

Records that set `body.namespace` to a namespace that doesn't exist (or whose ancestor chain contains an archived/deleted entry) are rejected with `403 NAMESPACE_REJECTED`. Records without `body.namespace` fall through to the implicit DEFAULT and are always accepted.

## Developer Tools

```bash
spl doctor [--json]                         # Top-down diagnostic (7 checks)
spl debug replay <task-or-thread> [--json]  # Walk records, show status transitions
spl debug thread-diff <a> <b> [--json]      # Structural diff of two threads
spl audit export [--since 24h]              # JSONL export for SIEM
                 [--categories system,decision,dispatch,governance]
                 [--actor X] [--thread X]
spl completion bash|zsh|fish|powershell|elvish   # Shell completion script
```

**`spl doctor`** runs 7 read-only checks and prints PASS/WARN/FAIL with a short reason for each. Exit code 0 = all pass, 1 = any warn, 2 = any fail. Suitable for cron/monitoring.

**`spl debug replay`** walks every record on a task thread in clock order and runs the same `derive_status` fold that `spl task show` uses. Status transitions are highlighted with an arrow and yellow highlight, so you can see exactly which record moved the task from `inbox → active → review → approved`.

**`spl debug thread-diff`** prints a side-by-side structural comparison of two threads: record count, participants, fold status, act distribution.

**`spl audit export`** emits one JSON object per line for security-relevant records (system actor writes, decision-gate decisions, dispatch outcomes, governance events). `--since` accepts relative durations (`24h`, `7d`), ISO 8601 timestamps, or unix seconds. Output is directly ingestable into Splunk, Elastic, Loki, or Datadog.

**`spl completion`** generates shell completion scripts via `clap_complete`. Pipe to the shell's completion directory:

```bash
spl completion bash > ~/.local/share/bash-completion/completions/spl
spl completion zsh  > ~/.zfunc/_spl
spl completion fish > ~/.config/fish/completions/spl.fish
```

## Fleet

<Callout type="warning">
This section covers multi-instance deployments.
</Callout>

Multi-instance coordination primitives (instance registry + kill switch) and the task fan-out + barrier. See [Your first fan-out](/docs/tutorials/first-fanout) for a walkthrough and [Operator Runbook: Fleet Operations](/docs/operate/runbook#multi-instance-fleet-operations) for day-2 procedures.

### Fleet lifecycle

```bash
spl fleet start [--workers N]        # Boot coordinator + N worker instances
spl fleet stop [--workers | --all]   # Stop workers only, or everything
```

`spl fleet start --workers 2` boots two worker instances on auto-assigned `SYNCROPEL_HOME` paths (`~/.syncro-worker-{a,b}`) and auto-assigned ports (9201, 9202), with the current `~/.syncro` prod instance acting as coordinator. Each worker inherits `SPL_FLEET_COORDINATOR_URL` pointing at the coordinator and begins emitting heartbeats within ~15 seconds.

Worker state roots are persistent across fleet restarts. Next `spl fleet start --workers 2` reuses them. To start fresh, delete `~/.syncro-worker-*` before booting.

### Fleet observability

```bash
spl fleet list                       # Snapshot: DID, endpoint, status, role, uptime
spl fleet show <did>                 # Detailed view of one instance
spl fleet ping <did>                 # HTTP /health reachability + latency check
spl fleet status [--live]            # Aggregate: live/stale/archived counts + frozen ns
```

`spl fleet list` reads the coordinator's `th_instance_registry` fold. Each instance is classified as `live` (heartbeat within last N seconds), `stale` (2-3 N windows old), or `archived` (older than 3N).

`spl fleet status --live` opens a continuously-refreshing view showing active dispatches per instance, pending fan-outs, and fleet-wide frozen namespaces.

### Kill switch

```bash
spl kill --namespace <ns> --level soft [--reason "..."]
spl kill --namespace <ns> --level hard [--grace <secs>] [--reason "..."]
spl kill --emergency [--reason "..."]

spl unkill --namespace <ns>
spl unkill --emergency
```

**Soft** (level 1, reversible, preferred): denies new `INTEND`/`DO`/`CALL` records in the namespace; allows `KNOW`/`LEARN` so in-flight dispatches drain cleanly. Common use: release-window lockdown, one-namespace debugging.

**Hard** (level 2, reversible with data loss): same as soft plus after `--grace <secs>` (default 60) the engine refuses all record ingest in that namespace. Use when the drain-cleanly semantics of soft are not safe.

**Emergency** (level 3, reversible, fleet-wide): every namespace's effective dial drops to 0. No new CALL or DO records land with non-trivial effects. GETs and KNOWs/LEARNs still pass so state remains inspectable. Use when you don't know what's wrong and need everything to stop immediately.

All kill records are LEARN records on `th_fleet_control` with full audit trail in `spl audit export`.

### Task fan-out

```bash
spl task fan-out <task-alias> \
  --subtask 'goal=...,target=worker-a,budget=2.00,timeout=1800' \
  --subtask 'goal=...,target=worker-b,budget=2.00,timeout=1800' \
  --subtask 'goal=...,target=least-loaded-worker,depends=0+1' \
  --join all

spl task join-status <parent-alias>             # Current join state
spl task retry <parent-alias> --subtask <index> # Re-dispatch one failed child
```

`spl task fan-out` creates a parent INTEND on the coordinator with the subtask list derived from the `--subtask` flags. The fan-out reconciler spawns one child INTEND per descriptor and POSTs each to its target worker's `/v1/records` endpoint via the instance registry.

Each `--subtask` flag is a comma-separated list of `key=value` pairs. Supported keys:

- **`goal`** (required) — the child subtask's INTEND goal, passed verbatim to the worker
- **`target`** (required) — one of `worker-<alias>`, `specific:<full-did>`, `least-loaded-worker`, `round-robin` (see "Routing strategies" below)
- **`budget`** (optional) — advisory per-subtask USD budget
- **`timeout`** (optional) — worker-side timeout in seconds, default 600
- **`depends`** (optional) — plus-separated list of 0-based subtask indices this child depends on. `depends=0+1` means "wait for subtasks 0 and 1 to accept before spawning this one." The reconciler validates depends indices for cycles at parse time.

<Callout type="info">
Declaring subtasks via a task body file isn't supported yet. The `--subtask` CLI flag form is the only shape shipped. A future release may add body-file parsing as an alternative form.
</Callout>

The `--join` flag accepts shorthands (`all`, `any`, `k_of_n:K`) or a custom CEL expression evaluating against the `children` binding. Examples:

```text
all                                               # all subtasks must accept
any                                               # any one subtask accepting is enough
k_of_n:3                                          # at least 3 of N subtasks accept
children.all(c, c.verdict == "accept" && c.cost_usd < 5.00)   # custom CEL
```

`spl task join-status` prints which children have reported, which are pending, the current verdict-so-far, and whether the join predicate currently evaluates true.

`spl task retry --subtask <index>` re-dispatches a single failed subtask (e.g. to a different worker after the original went stale) without disturbing the rest of the fan-out.

### Routing strategies

Fan-out descriptors set `target` to one of:

- **`worker-<alias>`** — direct lookup by instance DID last-segment alias
- **`specific:<full-did>`** — exact DID match
- **`least-loaded-worker`** — live worker with lowest `active_dispatches`, tie-break on longest uptime
- **`round-robin`** — deterministic pick based on `hash(parent_id + descriptor_index) mod live_worker_count`

Custom strategies (e.g. trust-weighted selection).

## Federation — Pair Lifecycle (canonical)

The `spl federation` verb is the canonical surface for federation pair management. One command establishes a pair; subsequent verbs manage its lifecycle. See the [federation pair guide](/docs/guides/federation-pair) for a walkthrough.

```bash
# Establish (the one-command primitive)
spl federation pair <peer-url>                  # Discover + verify + handshake + persist
spl federation pair add <peer-url> [--auto-approve]   # Same; explicit verb

# Lifecycle CRUD
spl federation list [--json]                    # All pairs with state column
spl federation show <peer-did | pair-id>        # Detail (auto-detects which kind of id)
spl federation refresh <peer-did | pair-id>     # Re-fetch peer manifest

# State transitions
spl federation pause <peer-did | pair-id>       # Stop sync; cursors preserved
spl federation resume <peer-did | pair-id>      # Resume a paused pair
spl federation revoke <peer-did | pair-id>      # Terminal; emits pair.revoke.v1

# Sync mode + cadence
spl federation set-mode <pair-id> {continuous|polling|on-demand}
spl federation set-poll-interval <pair-id> <secs>   # Only meaningful when mode=polling

# Cross-namespace consent grants (composes with consent records)
spl federation grant <pair-id> <namespace>      # Add consent grant
spl federation revoke-grant <grant-id>          # Remove a specific grant

# Thread filtering
spl federation thread-allow <pair-id> <thread-id>           # Add thread to allowlist
spl federation thread-rule <pair-id> '<CEL expression>'     # CEL rule on `record` + `thread()`

# Flat aliases (skip the `pair` verb; equivalent to the above)
spl federation list                              # ≡ spl federation pair list
spl federation show <id>                         # ≡ spl federation pair show
```

**Pair states**: `not_paired`, `establishing`, `active`, `paused`, `degraded` (peer unreachable; auto-retry), `revoked` (terminal).

**Pair direction**: a pair on X with `peer_did=Y` means X pulls from Y (records flow Y→X). For bidirectional sync, run `spl federation pair` on each side.

## Federation — Pair Sync (legacy `spl fleet sync` surface)

Legacy surface for federation pair management. Still functional but **superseded by `spl federation`** above for new pairs. See the [federation guide](/docs/guides/federation) for the legacy walkthrough.

```bash
spl fleet sync add [--peer-url URL] <PEER_DID> <THREAD_ID>   # Create a pair
spl fleet sync list [--json]                                 # List all pairs
spl fleet sync status <PAIR_ID> [--json]                     # Detail on one pair

```

`--peer-url` overrides DID resolution — useful when the peer's DID isn't in a shared directory.

**One-shot sync** (bulk-fetch a thread from a peer without a continuous pair):


Uses thread snapshot/restore under the hood. Useful for onboarding a new instance with existing history.

## Federation — Peer Discovery

Find other instances without hand-configured peer URLs. See the [federation pair guide](/docs/guides/federation-pair) for the canonical pairing flow once a peer is found, and the [federation discovery guide](/docs/guides/federation-discovery) for when each discovery method fits.

```bash
spl fleet sync peers discover                       # Try all available methods
spl fleet sync peers discover --method mdns         # LAN broadcast (mDNS)
spl fleet sync peers discover --method did-web --domain alice.dev
spl fleet sync peers discover --method did-sync --namespace acme-corp
spl fleet sync peers discover --method did-sync --directory https://directory.myorg.com
spl fleet sync peers discover --method transitive --via <peer-did>
spl fleet sync peers discover --method static       # Peers from local config
```

Output groups results by method and deduplicates peers seen via multiple methods. Use `--json` for programmatic consumption.

**Discovery never creates pairs automatically.** Review the output, then run `spl fleet sync add` for the peers you want.

### Manifest-based discovery

Query a peer's signed federation manifest directly. `spl discover` fetches `/.well-known/syncropel` from the given URL, extracts the federation manifest, verifies its Ed25519 signature against the advertised instance DID, and prints a ranked result. See the [federation discovery guide](/docs/guides/federation-discovery) for the manifest format and how it fits with the other discovery methods.

```bash
spl discover --peer-url <url> [--capability <tag>] [--kind <body.kind>] [--strict] [--json]
```

| Flag | Description |
|---|---|
| `--peer-url <url>` | Peer URL to query. Accepts a bare host (`https://alice.dev`) or a full `/.well-known/syncropel` URL |
| `--capability <tag>` | Filter the manifest by an advertised capability tag. Matches against `advertises.kinds` |
| `--kind <body.kind>` | Filter by an advertised `body.kind` |
| `--strict` | Reject stale (expired) manifests entirely. Without this flag, expired manifests are surfaced with a warning |
| `--json` | Emit the verified manifest as JSON for programmatic consumption |

```bash
# Fetch and verify a peer's manifest
spl discover --peer-url https://alice.dev

# Only return a result if the peer advertises a matching capability
spl discover --peer-url https://alice.dev --capability code

# Filter by record kind and fail on stale manifests
spl discover --peer-url https://alice.dev --kind music.catalog.track --strict --json
```

Direct-peer fetch with did:key verification is supported today. Directory aggregation and did:web / did:sync resolution arrive in a follow-up release.

### Identity — publish a did:web document

Generate a W3C-conformant DID document for operators who control a domain. Upload the resulting file to `https://<domain>/.well-known/did.json` via your existing web hosting.

```bash
spl identity publish-did-web --domain alice.dev [--output did.json]
```

The document includes the instance's current public key and a service entry of type `syncropel` pointing at the instance's advertised endpoint. Anyone who knows `alice.dev` can then resolve `did:web:alice.dev` without a directory service.

## Emergency Recovery

```bash
spl config permissions-unlock [--force]    # Unlock from permission lockout
```

`permissions-unlock` writes a `permissions_enabled=false` LEARN record directly to the SQLite store, bypassing the HTTP middleware that would otherwise deny the disable (the classic lockout trap). Refuses to run while the instance is up unless `--force` is passed — you still need to restart the instance for the change to take effect. Only sqlite stores are supported.

See [Permission Enforcement](/docs/guides/cel-expressions#permission-enforcement) for the pre-flight check that prevents the trap from firing in the first place.

## Authentication

Service accounts, bearer tokens, and device pairing. See the [Authentication & Service Accounts guide](/docs/operate/keyring) for the full story — when to use each, security model, federation composition.

### Service accounts

```bash
spl service-account create --name "<label>" [--scopes <csv>] [--actors <csv>] [--with-token] [--env-tag <tag>] [--namespace <ns>] [--bootstrap]
spl service-account list [--namespace <ns>]
spl service-account describe <sa_id> [--namespace <ns>]
spl service-account revoke <sa_id> [--reason "<text>"] [--namespace <ns>]
```

| Flag | Applies to | Description |
|---|---|---|
| `--name <label>` | `create` | Human-readable label (required) |
| `--scopes <csv>` | `create` | Capability scopes (default `records:read,records:write`). Valid: `records:read`, `records:write`, `threads:write`, `federation:manage`, `config:read`, `config:write`, `admin` |
| `--actors <csv>` | `create` | DIDs allowed to claim this SA via `X-Syncropel-Actor`. Empty ⇒ SA derives its own DID |
| `--with-token` | `create` | Mint an initial bearer token atomically with the SA |
| `--env-tag <tag>` | `create` | Env tag on the minted token (default `prod`). Only meaningful with `--with-token` |
| `--bootstrap` | `create` | Use the privileged bootstrap endpoint (no auth required). One-shot per namespace — closes after first SA exists |
| `--reason "<text>"` | `revoke` | Revocation reason recorded in the audit trail |
| `--namespace <ns>` | all | Namespace scope (default `default`) |

**Plaintext bearer tokens are printed once to stdout only.** They never appear in `--json` output. Save the token immediately on creation; you cannot recover it later (rotate to replace).

### Tokens

```bash
spl token create --sa <sa_id> [--env-tag <tag>] [--namespace <ns>]
spl token list [--sa <sa_id>] [--namespace <ns>]
spl token info <bearer_token>
spl token rotate <sa_id> [--env-tag <tag>] [--reason "<text>"] [--namespace <ns>]
spl token revoke --sa <sa_id> --token-id <token_id> [--reason "<text>"] [--namespace <ns>]
```

| Command | Description |
|---|---|
| `create` | Mint a new bearer token for an existing SA. Prints plaintext token once |
| `list` | List tokens (all, or filtered by `--sa`). Shows status `active` or `REVOKED` |
| `info` | Parse a token client-side — no network. Reports env_tag, sa_id, token_id (SHA-256 of secret) |
| `rotate` | Mint a fresh token FIRST, then revoke old ones. Safe against partial failure |
| `revoke` | Revoke a single token. SA and its other tokens keep working |

### Device pairing

```bash
spl pair --device "<label>" --url "<remote_url>" [--scopes <csv>] [--namespace <ns>] [--env-tag <tag>] [--actors <csv>]
```

Creates a dedicated service account, mints a token, and renders pairing payload three ways:

1. **One-click URL** — first thing printed, of the form `https://syncropel.com/pair#<encoded-payload>`. Click it (or copy into a browser) to auto-pair without typing or scanning. The token rides in the URL fragment (after the `#`), which never reaches any server.
2. **QR code** — for phones / camera-scan flows.
3. **Plain-text payload** — for paste flows when QR scanning isn't an option.

Used to connect phones, browsers, and other devices to a `spl serve` instance.

| Flag | Description |
|---|---|
| `--device "<label>"` | Device name (e.g. `"iPhone 17"`, `"browser-chrome"`) — required. The `browser-*` prefix defaults to scope `admin` so the dashboard's privileged panels render; `viewer-*` defaults to `records:read`; `emitter-*` defaults to `records:read,records:write`. |
| `--url "<remote_url>"` | URL the device will call — required. Must be reachable from the device |
| `--scopes <csv>` | Token scopes (default depends on device prefix — see `--device` above) |
| `--env-tag <tag>` | Env tag on the token (default `prod`) |
| `--namespace <ns>` | Namespace (default `default`) |
| `--actors <csv>` | Allowed claimable DIDs (empty ⇒ SA derives its own DID) |

Examples:

```bash
# Bootstrap the first service account on a fresh install
spl service-account create --bootstrap --name "First admin" --scopes admin --with-token

# Mint a read-only token for a dashboard
spl service-account create --name "Grafana" --scopes records:read --with-token

# Pair a phone
spl pair --device "iPhone" --url "https://your-host.example.com:9100" --scopes records:write

# Rotate a token (device stays connected; old token killed last)
spl token rotate sa_abc123def456ghi7

# Revoke just the lost-phone token
spl token revoke --sa sa_abc123def456ghi7 --token-id 7a2936eccf...

# Nuke the whole service account
spl service-account revoke sa_abc123def456ghi7 --reason "laptop stolen"
```

|---|---|---|
| `--member` | `create` | Membership invite: redemption mints a **principal** (identity + membership grant + credential parented to the grant), not just a bearer |
| `--preset <p>` | `create` | Scope preset (`reader` / `contributor` / `admin`). With `--member`, resolves the membership grant's scopes |
| `--label <name>` | `create` | Pin the member label. Redemption must use this label; if the label already belongs to a member this instance holds custody for, redemption becomes a **renewal** (same principal, fresh grant + bearer, old grant revoked) |
| `--grant-ttl <secs>` | `create` | Membership grant lifetime (1h to 10y; default 180 days). Distinct from `--ttl` |
| `--scopes <csv>` | `create` | Explicit scope wire strings; overrides `--preset` |
| `--ttl <secs>` | `create` | Invite *link* lifetime (default 24h) |
| `--max-uses <n>` | `create` | Maximum redemptions (default 1) |
| `--device-label "<text>"` | `create` | Label shown on the invite page |
| `<filter>` | `bulk-revoke` | `expired`, `exhausted`, or `holder:<did>` |

`spl invite audit` prints the invite lifecycle feed — issued / redeemed / exhausted / refused / `member_revoked`. `spl invite presets` and `spl invite templates` list the scope presets and saved invite templates.

```bash
# The golden path: invite a teammate as a contributor
spl invite create --member --preset contributor
# → prints the link; send it; the teammate redeems in the browser

# Renew an existing member (admin-pinned invite)
spl invite create --member --label mora
```

### Roster — `spl member`

```bash
spl member list [--json]
spl member adopt <label> [--sa <sa_id>] [--ttl <secs>] [--json]
spl member revoke <label> [--reason "<text>"] [--json]
```

| Command | Description |
|---|---|
| `list` | The membership roster. Admin sees all rows; any other caller sees only their own |
| `adopt` | Adopt an existing actor as a principal. Without `--sa`: binds a label whose signing seed this instance already holds (the operator, a paired device) — after this, that actor's signed task verdicts verify. With `--sa <sa_id>`: mints a custodial principal for the service account's holder and re-parents the credential to a membership grant without breaking the bearer |
| `revoke` | Offboarding as one revocation: the membership grant is revoked and every credential parented to it (bearers, agent sub-grants) dies with it — the bearer 401s on its next request. Bilateral (a member may revoke their own); idempotent; local-ledger scope |

```bash
# Adopt the operator so their verdicts verify
spl member adopt dpwanjala

# Re-home an agent's existing service account under a member
spl member adopt mora --sa sa_1f8e2c9a

# Offboard
spl member revoke mora --reason "contract ended"
```
