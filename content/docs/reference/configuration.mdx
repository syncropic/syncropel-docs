## Configuration File

Syncropel stores local settings in `~/.syncro/config.toml`:

```toml
[identity]
actor = "did:sync:user:alice"
display_name = "Alice"

[store]
url = "sqlite:///home/alice/.syncro/hub.db"

[server]
host = "127.0.0.1"
port = 9100
```

View the configuration:

```bash
spl config show
spl config path    # Shows the file location
```

## Workspace settings

Workspace settings are saved as records, so every change is kept in history and takes effect without a restart.

### Routing Rules

```bash
# Add a routing rule
spl config add-rule \
  --name "code-to-dev" \
  --domain code \
  --act INTEND \
  --target did:sync:agent:dev

# List rules
spl config list-rules
```

Rules are evaluated in order. The first matching rule determines where a record is routed.

### Event Triggers

Event triggers wake up actors when specific records appear:

```bash
# Create a trigger
spl config add-trigger \
  --name "review-on-completion" \
  --match "act=KNOW,body.topic=task_completion" \
  --target did:sync:agent:reviewer \
  --goal "Review the completed task" \
  --budget 1.0 \
  --timeout 300 \
  --cooldown 60

# Create a scheduled trigger
spl config add-trigger \
  --name "daily-summary" \
  --schedule "0 9 * * *" \
  --target did:sync:agent:reporter \
  --goal "Generate daily project summary"

# List triggers
spl config list-triggers

# Disable a trigger
spl config add-trigger --name "review-on-completion" --disable
```

Trigger options:

| Flag | Default | Description |
|---|---|---|
| `--match` | — | Record pattern: `"act=KNOW,body.topic=task_verdict"` |
| `--schedule` | — | Cron expression: `"*/15 * * * *"` (mutually exclusive with match) |
| `--target` | — | Actor DID to dispatch to |
| `--goal` | — | Goal text for the dispatched actor |
| `--budget` | 1.0 | Maximum cost per dispatch (USD) |
| `--timeout` | 300 | Maximum duration per dispatch (seconds) |
| `--cooldown` | 60 | Minimum seconds between fires |
| `--max-concurrent` | 1 | Maximum simultaneous dispatches from this trigger |

### Authentication

These settings control bearer-token sign-in for `spl serve`:

**1. Sign-in switch.** Turn this on to require a token for every request. It is a settings record (a `LEARN` record on the `th_engine_config` thread, which holds workspace settings). There is no `spl config` command for it, so you send the record yourself:

```bash
# Turn on required sign-in (set your actor and the next clock value)
curl -X POST http://127.0.0.1:9100/v1/records \
  -H "Authorization: Bearer $SPL_TOKEN" -H 'content-type: application/json' \
  -d '{"thread":"th_engine_config","actor":"<your member id>","act":"LEARN","clock":<next clock>,
       "body":{"topic":"auth_required","enabled":true}}'
```

| Field | Type | Default | Description |
|---|---|---|---|
| `topic` | string | — | Must be `"auth_required"` |
| `enabled` | bool | `false` | When `true`, every non-exempt endpoint requires `Authorization: Bearer <token>` |

Exempt routes (always unauthenticated): `GET /health`, `POST /v1/bootstrap/service-account`, `GET /.well-known/syncropel`.

The change takes effect on the next request. You do not need to restart.

**Per-actor plan level.** An actor you define yourself starts on the Trial level, whose daily limit is too low for an hourly schedule. One settings record gives that actor a higher level:

```json
{"topic":"actor_tier","actor":"did:sync:agent:director","tier":"team"}
```

There is no `spl config` command for this, so you write the record to the `th_engine_config` thread as the system actor (`did:sync:system:engine`). Only an owner or admin can do this.

| Field | Type | Default | Description |
|---|---|---|---|
| `topic` | string | — | Must be `"actor_tier"` |
| `actor` | string | — | The actor DID the assignment applies to |
| `tier` | string | — | `"paid"` or `"team"`. An assignment never grants owner rights; higher values are treated as `team`. An empty or missing `tier` removes the assignment. |

The latest record for each actor wins. The new level applies the next time actors are reloaded, which happens when the server starts and whenever you change an actor's definition. If you only write this record, restart the server to apply it. If the actor also has a level from its invite, the higher one is used.

**2. Allowed websites (CORS).** List the websites that may call your workspace from a browser:

```bash
spl config auth-set-cors-origins https://your-app.example.com
```

The list applies only when required sign-in is on. With sign-in off, any website may call your workspace.

**3. Emergency recovery.** If you lose your tokens, `spl serve --insecure-localhost` starts the server on `127.0.0.1` only, with sign-in turned off. It logs a warning at every start. **Never use it in production.**

See the [Authentication & Service Accounts guide](/docs/operate/keyring) for the full workflow — creating your first service account, managing tokens, pairing with another workspace, and recovering access.

### Embedding provider

Configure the provider used for [semantic search](/docs/guides/search). Without a provider, `POST /v1/records/search` returns `503 SEMANTIC_SEARCH_DISABLED`, and `spl search` reports `disabled: true`.

Managed via `spl config embedding-provider set|show|clear` (see the [CLI reference](/docs/reference/cli#embedding-provider)). Each command saves a settings record, and the change applies without a restart.

```bash
spl config embedding-provider set ollama --endpoint http://localhost:11434 --model nomic-embed-text
```

| Field | Type | Default | Description |
|---|---|---|---|
| `topic` | string | — | Must be `"embedding_provider"` |
| `provider` | object \| null | `null` | Provider config. Set `null` to clear (disables semantic search while retaining stored vectors) |
| `provider.kind` | string | — | Provider kind. Only `"ollama"` is supported |
| `provider.endpoint` | string | `"http://localhost:11434"` | HTTP endpoint of the embedding service (Ollama) |
| `provider.model` | string | `"nomic-embed-text"` | Model name. Changing the model is a "different embedder" — old vectors become inactive (retained but unused until cleared) |

After enabling a provider, backfill existing records with `spl embed --loop` (or `POST /v1/records/embed` in a shell loop). New records are indexed automatically as they arrive.

### Async-federation relay

Configure one or more store-and-forward relays for [async federation](/docs/guides/async-federation) — used when peers aren't reliably online at the same time. Each entry links a relay URL to either a specific peer DID or the catch-all value `"all"`. An entry with `enabled: false` is kept but ignored, so you can switch it off without losing the URL.

Managed via `spl config relay set|show|status|clear` (see the [CLI reference](/docs/reference/cli#federation--pair-lifecycle-canonical)). Each command that changes settings saves a settings record:

```bash
spl config relay set https://relay.syncropel.com --for-pair all
```

| Field | Type | Default | Description |
|---|---|---|---|
| `topic` | string | — | Must be `"federation.relay"` |
| `url` | string | — | Relay base URL (no trailing slash required) |
| `for_pair` | string | — | Peer DID this relay is for, or `"all"` as the catch-all |
| `enabled` | bool | `true` | When `false`, the entry is preserved but skipped at lookup time |

When sending, a relay set for that exact peer wins; otherwise the `"all"` relay is used. Restart `spl serve` after adding a new relay URL so that it starts receiving through it.

### Responder overrides

Responder details are filled in automatically from your connected adapters and actors, then merged with your overrides. Overrides let you choose the responders advertised on `/v1/capabilities` and `/.well-known/syncropel` — set a cost model, pin a trust floor, hide a responder from the list, or add a responder that has no automatic entry.

Managed via `spl config responders-add|responders-list|responders-remove` (see the [CLI reference](/docs/reference/cli#authentication)). Each command that changes an override saves a settings record with `topic: "responder_override"`:

```bash
spl config responders-add \
  --did did:sync:agent:dev \
  --kind actor \
  --capability code \
  --capability shell
```

The record has these fields:

| Field | Type | Description |
|---|---|---|
| `topic` | string | Must be `"responder_override"` |
| `did` | string | Target responder DID. Required |
| `kind` | string \| null | `actor`, `llm`, `pattern`, or `system`. If missing, the automatic value is kept |
| `capabilities` | list\<string\> \| null | Replaces the capability list for this DID |
| `trust_floor` | object \| null | Free-form trust-floor object (e.g. `{"code": 0.75}`) |
| `cost_model` | object \| null | Free-form cost-model object (e.g. `{"per_query_usd": 0.04}`) |
| `availability` | object \| null | Free-form availability object (e.g. `{"timezone": "PST"}`) |
| `metadata` | object \| null | Free-form metadata for your own use. The server does not interpret it |
| `remove` | bool | When `true`, hide this responder from the list even if an automatic entry exists |

An override for an existing DID replaces that entry's fields. An override for an unknown DID adds a new responder.

## Data Locations

| Path | Purpose |
|---|---|
| `~/.syncro/config.toml` | Local settings (identity, server, store) |
| `~/.syncro/hub.db` | Record database (SQLite) |
| `~/.syncro/secrets/` | API keys (plaintext files) |
| `~/.syncro-data/tasks/` | Task content files (Markdown) |
| `~/.syncro-data/aliases.toml` | Task alias mappings |
| `~/.local/share/syncropel/backups/` | Automatic database backups |
