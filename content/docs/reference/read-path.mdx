Since v0.279.0 every read has a time budget, a way to be cancelled and a cost the server controls. This page is the contract for what an integrator sees. The release record is the [changelog](https://github.com/syncropic/syncropel-core/blob/main/CHANGELOG.md), section 0.279.0.

## Read refusals

All three answer with a JSON body carrying `code`, and the `X-Syncropel-Refusal` header. A refusal that can succeed later also carries `Retry-After` and `Cache-Control: no-store`.

| Status | Code | When | What to do |
|---|---|---|---|
| `503` | `READ_BUDGET_EXCEEDED` | A read ran past its door class's time budget (interactive reads: 3 s; folds, exports and background loops have their own; every budget is doubled for 60 s after a cold boot), or its client went away. The body is `{code, budget_ms, door, retry_after_secs}`. `/health` never answers it. | Wait `Retry-After` seconds and retry. Narrow the request (a `body.kind` filter, a thread scope, a smaller `limit`) if it keeps happening. |
| `429` | `READ_IN_FLIGHT` | One scanning read per person runs at a time. A second scanning read from the same person waits for the first (in arrival order, at most 16 waiting per person, up to 3 s, holding no reader while it waits) and then answers this. The owner keeps a reader and is not refused. `Retry-After` is the first read's remaining budget. | Send one scanning read at a time per person, and retry after `Retry-After`. |
| `409` | `READ_STOPPED_BY_ERASE` | An export began before an erase and the erase overtook it. None of its output is served. | Run the export again. |

Named limit: a body's first open after a cold start can hold one scan past 3 s, so a client that fires several reads at once can see its later ones refused on that first open only. Every later open answers.

Person-facing words for these codes come from the kernel's words manifest. Quote them, don't paraphrase:

- `READ_BUDGET_EXCEEDED`: "This is taking longer than it should, so it stopped. Try again in a moment."
- `READ_IN_FLIGHT`: "Something you asked for is still loading. Try again in a moment."
- `READ_STOPPED_BY_ERASE`: "This export stopped partway because the workspace changed. Run it again." The screen never says an erase happened. This page can name the cause, but a person-facing message must not.

These three lines (approved D548) join the kernel's words manifest in 0.280. A 0.279 binary does not serve them yet and serves its earlier kernel wording.

## Counts

On a record read (`POST /v1/records/query` and the thread read) the count is bounded:

- A filter on a thread alone counts from the thread's own counts.
- Any other count stops at 250 ms. When it stops, `read.total` is `null` and `read.total_at_least` carries the count reached. `total_at_least` is present only when the count was bounded.
- Send `"total": "skip"` to count nothing. `capped` and `has_more` stay exact. A body older than 0.279 refuses `"skip"` with `400 UNKNOWN_FIELD`.

Read `total_at_least` when `total` is null. Don't treat a null total as zero.

A `created_at` sort is served in `sequence` order.

A ledger page's `limit` is clamped to the ledger's declared `row_ceiling`; follow `next_cursor` for the rest. A ledger that declares no ceiling keeps the default page.

## Page cursors

A page cursor (`next_cursor`, sent back as `cursor`) is opaque and sealed. Send it back unchanged.

- Cursors are encrypted and authenticated, and bind the viewer's own reach (their grants, seats, offices, classes and owner standing). Another person's activity doesn't change or end your walk. A change to your own reach ends it.
- An edited, hand-built or mismatched cursor answers `400 CURSOR_INVALID`. So does a cursor issued by 0.278 or earlier, after the upgrade: start the walk again from its first page.
- A cursor page carries the total, so later pages don't count again. An erase recounts the carried total silently.
- Ledger row cursors (`before=<clock>`) are a different cursor and are unchanged.

Person-facing words for `CURSOR_INVALID`: "This list changed since that page. Start again from the top."

## Filtering is decided by who you are

A filter, sort, group, aggregate, distinct-values call or text search on a field the caller can't read is refused:

```json
{ "code": "QUERY_FIELD_NOT_READABLE", "field": "body.title" }
```

The status is `400`. The answer is decided from the schema and the caller's standing, never from the data, so it is the same whether or not matching records exist. It covers `POST /v1/records/query` (plain and aggregation, and the standing query), MCP `find`, reductions, ledger pages (`filter`, `sort`, `q`, a chosen view) and values, ledger stats, a run's `read_thread` filter and the app read door. It replaces `403 REDUCTION_FIELD_WITHHELD` on aggregates.

Who can filter on what:

- **The owner** (the owner's session or key, local trust, or an unrestricted admin credential) reads everything. An admin credential carrying a grain, a read bound or a rooms marker is narrowed like anyone else.
- **Everyone else** can filter on the routing fields only: `body.kind`, `schema_version`, `idem`, `classes_read`, `declassified`, and the record's own fields (`thread`, `actor`, `act`, `clock`, `id`). A member can't filter, sort or group on other body fields, even ones they can read.
- **Declared surfaces** admit more: a held view on a conversation, and a ledger view or reduction whose `serves.class` names its audience (`views[].serves: {class, level?}`), admit filter, sort, group and values on the columns a plain read serves that class.
- **Own writes.** `POST /v1/records/query` takes `"own_writes": true` and serves the records the caller's own credential wrote (the service account, session or grant). On that surface body filters and sort are admitted, except on a field withheld by class, seal or erase. An aggregate or `group_by` with `own_writes` is `400 INVALID_QUERY`. Own writes follow the service account, so rotating its token (`POST /v1/tokens/{id}/rotate`) keeps them. Minting a replacement account does not. A sparse lineage with no other filter scans to fill a page, so filter by `body.kind`.
- **Find.** A guest's or member's `find` (MCP and `GET /v1/find`) is refused with the same code, because find matches body text. Read the records of the conversations you're in instead: `read_thread`, or `POST /v1/records/query` by kind.

Person-facing words (approved D548): "Only the workspace's owner can search or filter by this." It joins the kernel's words manifest in 0.280. A 0.279 binary serves its earlier kernel wording.

## Sequences a narrowed reader sees are its own

For a guest, a grained credential or a class-bounded run, `as_of_seq` (also `min_seq_met`, a subscription's `watermark_seq`, a watch stream's cursor, a batch's `committed_through`, `rights.as_of_seq`) is the highest sequence among the rows that reader is admitted, its own `min_seq` echoed, or 0. It doesn't move for a write the reader can't see, and it can go down when the reader's access shrinks. Never treat it as global or only-rising. Compare it only with sequences the same reader was served. The owner, an admin and a coarse member keep the workspace value.

Named limit (0.280, SKL-4916): each row a narrowed reader is served still carries its workspace `sequence`, so the gap between two rows it can see counts the writes in between.

## Server-Timing

`Server-Timing` is the owner's alone. The owner class (the owner, the owner's session, an unrestricted admin, the socket) reads it. Every other caller, and the public plane, gets no `Server-Timing` header. On an auth-exempt route (`/health`, `/health/ready`, `/`, `/v1/capabilities`, `/site/*`) it is served only on local trust (the socket, `--insecure-localhost`, or `auth.required=false`), never to a caller that merely sent no credential. To read timing, use the owner's credential on a `/v1` door, or the socket.

## Health

- Anonymous `/health` carries `writeback` as `{attach, attach_fact}` only. A monitor that read `writeback.epoch`, `backlog_now`, `last_attach`, `lists` or `files_backfill` without a credential must send the owner's bearer, read `/v1/health`, or read through the Unix socket (`~/.syncro/run/spl.sock`).
- `/v1/health` serves `read_pool {in_flight_reads, in_flight_writes, pool_size, wal_truncate_owed}` to the owner only, and `revoked_list.reasons_owed`.
