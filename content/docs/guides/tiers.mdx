This page is for people running their own workspace or using the API. If you use a workspace created at syncropel.com, start with [Your hosted workspace](/docs/get-started/your-hosted-workspace).

## Why tiers exist

Every run has limits before it starts. They come from the tier
of the person the run is for: how many turns it may take, how long it may
run, how much it may spend, how many runs may go at once, and how deep it may
start further runs. There are four tiers, in order of increasing capability:

- **Trial**: the safe default for a shared workspace.
- **Paid**: the working tier.
- **Team**: multi-user accounts, higher concurrency and depth.
- **Operator**: the workspace's own owner, on their own machine.

The owner has the final say on their own workspace, so the Operator tier has
effectively no limits on turns, time and tools. It does limit how many further
runs one run can start: a runaway chain of runs spends money just as fast as a
malicious one, so `max_children` (runs one run may start) and `max_tree_loops`
(total runs in one chain) stay finite even there. That guards against a
mistake; it does not limit the owner's authority.

## The limits

These are the built-in defaults. Each is an upper limit: a run gets its tier's
limit, or a lower one if it asks for less.

| axis | Trial | Paid | Team | Operator |
|---|---|---|---|---|
| max turns | 5 | 16 | 50 | unbounded |
| wall clock (s) | 120 | 600 | 1,800 | unbounded |
| token budget | 20,000 | 200,000 | 1,000,000 | none |
| default per-run budget (USD) | 0.25 | 1.00 | 2.00 | 5.00 |
| daily cost cap (USD) | 0.50 | 5.00 | 50.00 | unbounded |
| daily loop cap | 10 | 200 | 2,000 | unbounded |
| concurrency | 1 | 5 | 20 | unbounded |

Trial also forbids `bash`, `write_file` and starting sub-agents; Paid
and Team forbid `bash` and `write_file`. Which tools are forbidden is fixed and cannot be changed through a tier record.

## Changing a tier's limits

Each tier's numeric limits can be changed by writing a `core.engine.tier.v1` record to the
`th_engine_config` thread. The change applies from the next run; no
upgrade is needed. A record only sets numbers; it never gives access to forbidden tools.

A tier record names only the fields it changes; every field it omits keeps its default. To lower Trial's daily spend and raise its turn limit, for example (a record write, as described in [Store bounds](/docs/operate/store-bounds)):

```bash
curl -X POST http://127.0.0.1:9100/v1/records \
  -H "Authorization: Bearer $SPL_TOKEN" -H 'content-type: application/json' \
  -d '{"thread":"th_engine_config","actor":"<your member id>","act":"LEARN","clock":<next clock>,
       "body":{"kind":"core.engine.tier.v1","tier":"trial","max_turns":9,"daily_cost_cap_usd":2.5}}'
```

A tier with no record uses the defaults in the table above. Editable fields are `max_turns`, `wall_clock_secs`,
`token_budget`, `daily_loop_cap`, `concurrency`, `max_depth`, `max_children`,
`max_tree_loops`, `daily_cost_cap_usd`, and `default_budget_usd`.

## Assigning an actor to a tier

By default a defined actor is on Trial. To put an actor on a higher tier,
write an `actor_tier` assignment (also written to `th_engine_config`):

```bash
curl -X POST http://127.0.0.1:9100/v1/records \
  -H "Authorization: Bearer $SPL_TOKEN" -H 'content-type: application/json' \
  -d '{"thread":"th_engine_config","actor":"<your member id>","act":"LEARN","clock":<next clock>,
       "body":{"kind":"core.engine.config.v1","topic":"actor_tier","actor":"did:sync:agent:dev","tier":"paid"}}'
```

The latest assignment wins; an empty `tier` clears it. The actor gets the higher
of its invite's tier and its assignment, up to Team at most. No record can
grant the Operator tier: that belongs to the workspace owner alone.

## Per-actor daily limits

An actor's definition may set its own `daily_cost_cap_usd` and `daily_loop_cap`. The
lower of the actor's value and the tier's applies, so an actor's own limit can
only tighten, never raise. A Trial member whose own limit exceeds Trial's is
refused when it is defined, so a member cannot give itself more room by
asking.

## Entitlements

A subscription status becomes a tier through one HTTP call:

```
POST /v1/entitlement
```

The caller says what the subscription status is; the workspace decides what that
status entitles. The effect is an ordinary `actor_tier` assignment. The
record it writes carries its reason, so you can always see why your limits changed.

The rules:

- `active` and `trialing` map to **Paid**. Everything else, including
  `past_due` and any status the workspace does not recognize, reads as **Trial**.
- An entitlement moves an actor between **Trial and Paid and nothing else**. A
  billing signal can never grant Team or Operator, whatever it says: only the
  owner assigns those, on their own workspace.
- An unrecognized status reads as Trial, so an
  unknown word from a payment processor never grants capacity.
- `past_due` is not a cut-off. A failed card narrows what a workspace may
  spend; it does not take the workspace away. The person keeps their records,
  the workspace keeps answering, and the limits come down until they fix it.

## A hosted workspace follows its plan

On a hosted workspace every run follows the limits of the workspace's plan: a free workspace runs
at the Trial limits, a paid one at the Paid limits. That holds for every way a run starts: a
message you send, an assistant stepping into a conversation, a scheduled trigger, a delegation. A workspace on your own machine has no plan limit.

On a hosted workspace with a plan, the limits come from the plan itself: writing a tier record
or an entitlement is refused (`PLAN_LIMITS_NOT_WRITABLE`), and
an entitlement request that does not come from the hosting service is refused
(`ENTITLEMENT_UNSIGNED`). The Trial limit allows two runs at once, so a scheduled run
never stops you from starting your own.

## Moving up a tier is never automatic

Syncropel can show that an actor is eligible for the next tier once its trust
is high enough over enough reviewed outcomes, but it never applies the change.
Moving an actor up a tier is always an explicit assignment or an entitlement.

## Verify what is in force

The tier limits and the permission state are in the health report:

```bash
curl -s -H "Authorization: Bearer $ADMIN" localhost:9100/v1/engine/health | jq .
```

Check what the running workspace actually uses, not only what you wrote.
