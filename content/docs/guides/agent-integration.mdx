## Overview

Syncropel coordinates AI agents the same way it coordinates people. An agent is an actor. It receives work by dispatch, and it builds trust from reviewed results.

## Supported Agents

Any CLI-based agent that reads a prompt and produces output can integrate. Examples:

| Agent | Binary | Integration |
|---|---|---|
| Claude Code | `claude` | CLI adapter, stream-json output |
| Codex CLI | `codex` | CLI adapter |
| OpenCode | `opencode` | CLI adapter |
| Pi | `pi` | CLI adapter |
| Custom agents | Any binary | CLI adapter with configurable flags |

The steps are the same for every agent: register an actor, add a CLI adapter, and point it at the program. Syncropel runs the program and reads its output.

## Register an Agent

```bash
# Register the actor
spl actor register did:sync:agent:dev --display-name "Dev Agent"

# Bind a CLI adapter
spl adapter add did:sync:agent:dev \
  --family cli \
  --binary claude \
  --timeout 600 \
  --max-concurrent 2
```

## Dispatch Work

Send a task to an agent:

```bash
spl dispatch send dev "Fix the failing authentication tests" \
  --budget 1.0 \
  --timeout 600
```

Or dispatch a structured task with full context:

```bash
spl task dispatch TASK-0001
```

When you dispatch, Syncropel:
1. Builds a goal with context (the task content and the actor's memories).
2. Starts the agent through its CLI adapter.
3. Watches the agent's output for records.
4. Saves the agent's records to the workspace.

## How Agents Report Work

Agents write records on the thread they are assigned to:

- **CALL records** for tool use (shell commands, file reads, API calls)
- **KNOW records** for observations ("tests pass", "found the bug in auth.py")
- **DO records** for actions taken

The agent marks completion with:

```bash
spl task done TASK-0001 --summary "Fixed token validation logic" --domain code
```

## Trust from Agent Work

Agent work follows the same evaluation gate as human work:

1. Agent completes → status: `review`
2. Reviewer approves → status: `approved`, trust evidence created
3. Over time, the agent builds a trust profile in specific domains

```bash
spl trust
```

```
ACTOR                   DOMAIN    SUCCESS   TOTAL   TRUST
did:sync:agent:dev      code            8      10   0.418
```

## Agent Memory

Agents accumulate memories across sessions:

```bash
spl memory list --actor did:sync:agent:dev
```

Memories include conventions, quality checks, past corrections, and domain knowledge. They are sent with each dispatch, so the agent starts every session with what it has learned.

## Remote agents & authentication

When an AI agent runs on a different machine than your workspace (for example, a workflow agent on a CI runner, or a coding agent reaching your laptop), the agent must authenticate over HTTP. See [Authentication & Service Accounts](/docs/operate/keyring) for the pattern:

1. Create a dedicated service account for the agent with scoped capabilities (`records:write` + `records:read` is usually enough)
2. Mint a bearer token, pass it to the agent as an environment variable
3. The agent sends `Authorization: Bearer <token>` on every HTTP call

This gives each agent its own revocable identity without sharing credentials between agents.

A service account suits standing workspace services, and it outlives any member. For an agent that acts for a *person*, using their budget and scopes and ending when they leave, see [Agent credentials](/docs/guides/agent-credentials) for how to choose.
