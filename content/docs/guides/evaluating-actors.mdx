## Overview

Two commands let you measure how well an actor does its work and record a
preference between two results:

- **`spl eval`** scores an eval suite against an actor and reads that
  actor's graded history.
- **`spl judge`** records that one result beat another, along with the features that made the difference.

Together they let you measure a candidate actor definition, compare it with the one it replaces, and keep a lasting record of which was better and why.

## Scoring a suite: `spl eval score`

An eval suite is a thread of test cases (`core.eval.case.v1` records). Scoring compares those cases with an actor's runs and writes **one** result record (`core.eval.run.v1`).

```bash
spl eval score <suite> \
  --actor <did> \
  --definition <64-hex>
```

| Argument / flag | Meaning |
|---|---|
| `<suite>` | The eval thread holding the `core.eval.case.v1` records |
| `--actor <did>` | The actor whose runs are scored |
| `--definition <64-hex>` | The ID of the definition being graded |

The definition is required, so every grade names what it measured. Scoring refuses to grade if no runs used that definition, so a grade always reflects work that actually ran under it.

### Execution is a separate step

`spl eval score` does not run the cases. A suite is many runs of 30 to 60 seconds each, so run the cases first against the actor, then score the runs that exist.

### Structure and substance are scored apart

The score keeps two axes separate and **never averages them**:

- **Structure** is whether the run was well-formed (for example, it finished with no failed tool calls).
- **Substance** is whether it did the right thing.

A case with **no run** is left out of the substance figure instead of counting as a failure. Each substance figure shows how many cases it covers, so compare two scores only when they cover the same cases.

## Reading the history: `spl eval history`

```bash
spl eval history <actor>
```

This shows an actor's graded history by definition: is it getting better,
and on which axis. Because the two axes are never blended, a candidate that
fixed every failed tool call but started answering the wrong question shows
structure up and substance down, rather than one blended number that hides the regression.

## A definition is identified by how the actor behaves

Who installed a definition, where it came from, and how much it is trusted can all change without changing how the actor behaves. Scoring therefore identifies a definition by its behaviour (its "facet"), not by its record ID. A candidate you measure **before** approval is recognized as the same definition **after** approval.

A **trial** applies a candidate definition to a single run and installs nothing. It follows the same checks as a real install, so you can measure a candidate against the current definition without changing your workspace.

## Judging one record over another: `spl judge`

`spl judge` records a preference between two records, by ID:

```bash
spl judge <winner> over <loser> \
  --feature "cited its sources" \
  --loser-feature "faster" \
  --basis "the winner grounded every claim"
```

The literal word `over` goes between the two 64-character record IDs. Options:

| Flag | Meaning |
|---|---|
| `--feature <TEXT>` | A feature the winner has and the loser lacks (repeatable) |
| `--loser-feature <TEXT>` | A feature the loser has and the winner lacks (repeatable) |
| `--basis <TEXT>` | One sentence of why |
| `--thread <THREAD>` | The thread the verdict lands on (default: the winner's thread) |
| `--actor <ACTOR>` | The judging actor (default from `SPL_ACTOR` or config) |

This writes a verdict (`core.verdict.pair.v1`) naming the features that differed. Each definition is compared with the one it replaced, axis by axis, so a verdict is a lasting record of which result was better and why.

## Machine-readable output

Both commands emit raw results with `--json`:

```bash
spl eval score <suite> --actor <did> --definition <64-hex> --json
spl eval history <actor> --json
spl judge <winner> over <loser> --json
```
