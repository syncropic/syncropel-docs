## Overview

Find answers the question _"where is that thing?"_ across everything your
workspace holds:

- **Names** — files matched by name or path
- **Content** — the full text inside your files
- **Conversations** — messages in your threads, so "the chat where we
  discussed the launch budget" is one query away even if nothing was ever
  saved as a file

Results are ranked together: an exact filename match comes first, then the best content and conversation matches. Each result has a **snippet** with the matched words, so you can see why it matched before opening it.

Find needs **no setup** and works on every workspace, including hosted ones. It complements two other tools:

| Tool | When to use it |
|---|---|
| **Find** | You know words that appear in the thing — a name, a phrase, an identifier |
| [Query](./query) | You know the *shape* of what you want — a kind, a field value, a thread |
| [Semantic Search](./search) | You know the *idea* but not the words (needs an embedding provider) |

## Searching

From the CLI:

```bash
spl find "quarterly budget"
```

```
  /files/lib/budget-notes.md  (name+content)
      planning notes  the quarterly budget plan needs revising
  th_a1b2c3…  (conversation: Planning the spring release)
      let us discuss the launch budget for spring
```

Over HTTP:

```bash
curl "$BASE/v1/find?q=quarterly+budget" -H "Authorization: Bearer $TOKEN"
```

```json
{
  "hits": [
    {
      "type": "material",
      "node": { "name": "budget-notes.md", "path": "/files/lib/budget-notes.md", "...": "..." },
      "snippet": { "text": "the quarterly budget plan needs revising", "offsets": [[14, 20]] },
      "why": ["name", "content"]
    },
    {
      "type": "thread",
      "thread": "th_a1b2c3…",
      "gist": "Planning the spring release",
      "snippet": { "text": "let us discuss the launch budget for spring", "offsets": [[26, 32]] },
      "participants": ["did:sync:user:you"]
    }
  ],
  "planes_served": ["names", "content", "threads"],
  "planes_degraded": []
}
```

Two hit types come back:

- **`material`** — a file. `node` has the same shape as a file in the library. `why` says whether the name, the content, or both matched.
- **`thread`** — a conversation. Each thread appears once however many messages matched, with the snippet taken from the best-matching message.

A snippet is plain text plus `offsets`, the byte ranges of the matched words inside `text`. Use the offsets to highlight matches. The text never contains markup.

### Parameters

| Param | Default | What it does |
|---|---|---|
| `q` | — | The search text. Special characters are safe — they're treated as plain text, never as query operators |
| `limit` | 20 | Max hits (up to 100) |
| `types` | both | `material` or `thread` to filter hit types |
| `prefix` | false | Type-ahead mode: the last word matches as a prefix, so `quart` finds "quarterly" as you type |
| `explain` | false | Adds, for each result, which kinds of content matched and how it was ranked |

### What gets searched

File content is indexed for **text-like files**: plain text, Markdown,
code, CSV, JSON, YAML, and similar. **PDFs and images are not searched by content.** They still match by file name. Conversations are indexed from the
messages you and your assistant exchange.

The search stays up to date as you work:

- A saved file is findable within seconds.
- A **deleted or renamed** file disappears from results immediately.
- An **edited** file is found by its new content only. Text from the old version never matches.

### Partial results are reported

The response lists which kinds of content were searched (`planes_served`: names, content, threads) and which, if any, had a problem (`planes_degraded`). A problem with one never hides results from the others.

## For agents

AI clients connected over [MCP](/docs/integrate/ai-clients) get the same
search as a `find` tool, so an assistant can locate a file or a past
conversation before acting on it:

```json
{ "name": "find", "arguments": { "q": "deploy checklist", "limit": 5 } }
```

This is the owner's tool. For a guest or a member, `find` (over MCP and `GET /v1/find`) is refused with `400 QUERY_FIELD_NOT_READABLE`, the same answer whether or not the term exists, because find matches body text. A non-owner reads the records of the conversations they're in with `read_thread`, or with `POST /v1/records/query` by kind. See [Reads, budgets and cursors](/docs/reference/read-path#filtering-is-decided-by-who-you-are).

## Index health and rebuild

The index keeps itself up to date: content is indexed as you save, and a background check fills any gaps. In the rare case you want to look closer, use:

```bash
spl find --stats        # coverage, pending items, last indexing failure
spl find --rebuild      # rebuild the index (safe to run while the workspace is in use)
```

```bash
curl "$BASE/v1/search/stats" -H "Authorization: Bearer $TOKEN"
curl -X POST "$BASE/v1/search/rebuild" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"scope": "all"}'
```

A rebuild runs in small batches in the background and never blocks the workspace. `--stats` shows its progress.

## Limits

- Searches are rate-limited for each actor, with at most two at the same time. Type-ahead search boxes should wait for a pause in typing before searching.
- You get at most 100 results. For exhaustive listings, use
  [Query](./query) or browse the library.
- Word-based matching works best for languages with space-separated
  words; Chinese, Japanese and Korean text matches on whole phrases.
