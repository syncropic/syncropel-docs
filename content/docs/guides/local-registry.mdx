`spl serve` starts a full governance-aware registry on your machine. It's not a mock or a dev stub — it runs the same governance logic, the same API surface, and the same validation pipeline as the production registry.

## Starting the Registry

```bash
spl serve
```

```
Registry started at http://localhost:9100
Database: ~/.syncro/hub.db (persistent)
```

The registry auto-configures the CLI: it writes `registry_url: http://localhost:9100` to `~/.syncro/config.yaml` so all `spl` commands automatically hit your local instance.

### Options

| Flag | Description |
|------|------------|
| `--port N` | Use a custom port (default: 9100) |
| `--open` | Open a browser to the dashboard on start |

## What's Inside

### Storage

All data persists at `~/.syncro/hub.db` — a single file. It survives restarts, and you can back it up by copying the file.

The database stores namespaces, policies, sessions, effects, governance tokens, patterns, observations, trust scores, consent edges, revocation lists, approval requests, settlements, audit logs, and peer registry configurations. Schema migrations are automatic on startup.

### 160+ API Routes

The server exposes a full API surface covering:

| Group | Example Routes | Purpose |
|-------|---------------|---------|
| Namespaces | `GET/POST/DELETE /api/namespaces/...` | CRUD + hierarchy resolution |
| Policies | `GET/PUT/DELETE /api/policies/...` | Capability/deny/budget management |
| Trust | `GET /api/trust/...` | Trust scores and computation |
| Observations | `POST /api/observations/...` | Record execution outcomes |
| Governance | `GET/POST /api/governance/...` | SCT computation, validation |
| Federation | `GET/POST /api/federation/...` | Consent edges, observation sync |
| HITL | `GET/POST /api/hitl/...` | Approval workflow |
| Settlements | `POST /api/settlements/...` | Settlement execution |
| Audit | `GET /api/audit/...` | Audit trail queries |
| Auth | `POST /api/auth/...` | Service account management |
| Traces | `GET/POST /api/traces/...` | Session trace management |
| Health | `GET /health` | Liveness check |

These are the same URLs as the production registry. An SDK configured with `registry_url="http://localhost:9100"` works identically against `api.syncropel.com`.

## The Governance Stack

Everything that runs in production runs locally: session capability token issuance, the full governance validation pipeline, trust computation, namespace resolution with monotonic narrowing, observation recording, immutable audit trail, service account revocation, federation consent management, and human-in-the-loop approval workflows.

## Persistence

| Item | Location | Behavior |
|------|----------|----------|
| Database | `~/.syncro/hub.db` | Persistent, survives restarts |
| Config | `~/.syncro/config.yaml` | Written by `spl serve`, read by all commands |
| Traces | `~/.syncro/traces/` | Populated by integration hooks |
| Seeds | `~/.syncro/seeds/` | Loaded on startup if present |

### Backup

```bash
# Stop the registry, then copy the database
cp ~/.syncro/hub.db ~/.syncro/hub.db.backup
```

### Reset

```bash
# Delete the database to start fresh
rm ~/.syncro/hub.db
spl serve  # Creates a new empty database
```

## Connecting SDKs

Any Syncropel SDK can connect to your local registry:

```python
# Python SDK
from syncropel import Client
client = Client(registry_url="http://localhost:9100")
```

```typescript
// TypeScript SDK
import { SyncropelClient } from '@syncropic/syncropel-js';
const client = new SyncropelClient({ registryUrl: 'http://localhost:9100' });
```

When `spl serve` is running, the `SPL_REGISTRY_URL` environment variable is automatically set, so many tools detect the local registry without explicit configuration.
