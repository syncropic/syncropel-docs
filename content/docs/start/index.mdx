The shortest path from zero to a working Syncropel loop. Eight commands. About five minutes.

> **Prefer hosted?** Skip install entirely — sign up at [syncropel.com/signup](https://syncropel.com/signup) and follow [Hosted instance signup](/docs/get-started/hosted). Same protocol, same CLI, no machine to maintain.

## In a hurry — just the commands

```bash
# 1. Install
curl -sSf https://get.syncropic.com/spl | sh           # Linux / WSL — Windows: irm https://get.syncropic.com/spl.ps1 | iex

# 2. Initialize
spl init

# 3. Start the daemon
spl serve --daemon

# 4. Add → start → complete → approve a task
spl task add "Read the Syncropel quickstart" --priority high --domain meta
spl task start TASK-0001
spl task done TASK-0001 --summary "Read it. Set up local kernel." --domain meta
SPL_ACTOR=did:sync:agent:director spl task approve TASK-0001 --domain meta --notes "Quickstart complete"

# 5. See your first trust evidence
spl trust
```

If those eight commands ran clean, you're done. The rest of this page explains what each step did and where to go next.

## What just happened

You produced four immutable, content-addressed records on a thread, accumulated trust evidence in the `meta` domain (where Syncropel groups infrastructure/process/onboarding work), and proved the loop works. Every other Syncropel feature — federation, AI agent dispatch, CEL automation, namespaces — composes on top of this primitive.

| Step | What ran | What got recorded |
|---|---|---|
| `spl init` | Created `~/.syncro/` (config, logs, secrets dir) | — |
| `spl serve --daemon` | Started the kernel on `127.0.0.1:9100`, opened `~/.syncro/hub.db` | The kernel's bootstrap LEARN on `th_engine_config` |
| `spl task add` | Created task thread `TASK-0001` | INTEND record — task creation |
| `spl task start` | Marked active | DO record — work-started |
| `spl task done` | Submitted for evaluation | KNOW record — completion claim |
| `spl task approve` | Director-actor evaluated and accepted | KNOW record — verdict; trust evidence accumulates |

`spl thread records TASK-0001` shows all four; `spl trust` shows the evidence the verdict produced.

## Why a separate actor for `approve`?

Syncropel's trust model gates self-evaluation: a record's evaluator must be a different actor than its emitter. The `SPL_ACTOR=did:sync:agent:director` shown above is a built-in director actor that ships with `spl init`. For solo work it's the canonical evaluator; for team work, real reviewers approve their teammates' work.

The trust function `wilson_lb(success, total)` rejects evaluations where executor == evaluator with the CUSUM detector. Trying to self-approve raises an explicit error message; the env-var workaround above is the documented single-user pattern.

## Common pitfalls

**`spl serve --daemon` says ready, but `spl status` shows nothing.**
The daemon may have failed to bind port 9100. Check `~/.syncro/logs/spl.log` — most common cause is a previous instance still bound. Use `pgrep -af "spl serve"` and `kill <pid>` to clean up, then retry.

**`spl task done` complains about uncommitted git changes.**
The task-completion gate refuses to attribute completion when the working tree is dirty (so wrong commits don't get tied to the wrong task). Either `git commit` first, or pass `--force` if the changes are unrelated.

**`spl serve --stop` says "not running" but a daemon clearly is.**
The PID file got orphaned (rare but real). Use `pgrep -af "spl serve"` then `kill <pid>` directly. See [Operator Runbook → Daemon orphan recovery](/docs/operate/runbook#when-spl-serve---stop-says-not-running-but-the-daemon-clearly-is) for the full procedure.

**You're on macOS.**
Prebuilt macOS binaries are on the near-term roadmap. Until they ship, three working paths:

- Run `spl` in a Linux VM/Docker, expose port 9100 to the Mac
- Run `spl serve` on a remote Linux host, pair the local browser via [Pairing](/docs/get-started/pairing)
- Use WSL on a Windows machine

See the [install page macOS section](/docs/get-started/install#macos) for full alternatives.
