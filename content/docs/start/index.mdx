This page is for people running Syncropel on their own computer or using the API. If you use a workspace created at syncropel.com, start with [Your hosted workspace](/docs/get-started/your-hosted-workspace).

This is the shortest path from nothing to a working setup: a few commands, about five minutes.

> **Prefer hosted?** Skip the install. Sign up at [syncropel.com/sign-up](https://syncropel.com/sign-up) and follow [Create your workspace](/docs/get-started/hosted). It is the same product and the same command line, with no machine to look after.

## Just the commands

```bash
# 1. Install
curl -sSf https://get.syncropic.com/spl | sh           # Linux / macOS / WSL. Windows: irm https://get.syncropic.com/spl.ps1 | iex

# 2. Set up
spl init

# 3. Start your workspace (it runs in the background)
spl start

# 4. Add a task, start it, finish it, then have someone else approve it
spl task add "Read the Syncropel quickstart" --alias TASK-0001 --priority high --domain meta
spl task start TASK-0001
spl task done TASK-0001 --summary "Read it. Set up local Syncropel." --domain meta
SPL_ACTOR=did:sync:agent:reviewer spl task approve TASK-0001 --domain meta --notes "Quickstart complete"

# 5. See your first trust
spl trust
```

If those commands ran without errors, you're done. The rest of this page explains what each step did.

## What just happened

You created a task, moved it through its steps, and had it approved. Each step was saved as a record on the task's thread, and the approval gave the person who did the work their first trust, in the `meta` domain (the area Syncropel uses for setup and process work).

| Step | What it did | What was saved |
|---|---|---|
| `spl init` | Created the `~/.syncro/` folder (settings, logs, secrets) | Nothing |
| `spl start` | Started your workspace in the background on `127.0.0.1:9100` | A start-up record |
| `spl task add` | Created the task `TASK-0001` | A record that the task was created |
| `spl task start` | Marked the task as started | A record that work began |
| `spl task done` | Marked the task as done and ready for review | A record claiming it is complete |
| `spl task approve` | A reviewer accepted it | A record of the decision, which builds trust |

`spl thread records TASK-0001` shows all four task records. `spl trust` shows the trust the approval produced. It can take a few seconds to appear, so if `spl trust` shows nothing the first time, run it again.

## Why does a different person approve?

Nobody can approve their own work. The approver must be a different actor than the one who did the work. `SPL_ACTOR=did:sync:agent:reviewer` is just an example: any identity other than your own works. If you try to approve your own work, `spl` tells you so.

Working alone, a separate reviewer identity, as above, is the usual way. In a team, real reviewers approve each other's work.

## Common problems

**`spl start` says it is ready, but `spl status` shows nothing.**
Your workspace may not have been able to use port 9100. Check `~/.syncro/logs/spl.log`. The usual cause is an earlier copy still running. Run `pgrep -af "spl serve"`, then `kill <pid>` for the old one, and try again.

**`spl task done` complains about uncommitted git changes.**
`spl` won't link a finished task to your code while you have uncommitted changes, so the wrong commit isn't attached to the wrong task. Run `git commit` first, or add `--force` if the changes are unrelated.

**`spl stop` says "not running" but your workspace clearly is.**
The record of the running copy was lost. Run `pgrep -af "spl serve"`, then `kill <pid>`. See [the runbook](/docs/operate/runbook#when-spl-stop-says-not-running-but-the-instance-clearly-is) for the full steps.
