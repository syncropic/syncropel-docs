Every Syncropel instance serves a landing page at `GET /`, the first
thing a visitor sees when they open your instance's address, such as
`alice.syncropel.app`. The instance builds that page itself, from information it already has.

The default landing page is a built-in identity card: the instance
name, a generative glyph derived from the instance DID, a one-line
mission, six default links to capabilities and federation surfaces, and
a Connect button to Syncropel Studio. It looks good with zero
configuration. That is the point.

When you want to make it your own, three tiers of customization stack
on top of the default. Each tier adds capability without breaking the
floor.

## The three tiers

**Tier 1: the identity card (always on)**: the floor. A real instance
serves a real-looking page from the moment it boots, with no setup. The
glyph, the typography, the layout: these are built in and cannot be removed. They are what makes one Syncropel instance
visibly the same network as every other one.

**Tier 2: record-driven content overrides**: publish a `core.site.v1`
record on the `th_site` thread to override slots on the identity card. The
name. The kind label under the name. The mission paragraph. The about
paragraph. The links grid (up to six cards replace the default six). The
Connect button label and target. The DID copy footer visibility. This is
what the `spl site` commands write, and what a script can write
directly.

**Tier 3: filesystem overlay** (`~/.syncro/site/`): drop CSS, assets,
and a small allowlist of `<head>` content at known paths on the host
filesystem, and the renderer picks them up on each request. This is the
WordPress-theme-style escape hatch for operators who want full control:
load a custom font, add an Open Graph image, override the accent palette
across both light and dark themes. Only a short list of `<head>` content is accepted (no inline scripts, no
arbitrary HTML), so the identity card stays intact even with overlays
applied.

## What the renderer produces

The page is one HTML document, under 100 KB including inlined CSS. It uses no JavaScript framework. The only script is a small helper for the DID copy button, served from the same origin. Visitors see the page on first paint.

The page is built from three parts:

- The **identity card**, derived from the instance's identity. Always present.
- Your **content overrides** (a `core.site.v1` record). Optional.
- Your **filesystem overlay** (theme CSS, head fragment, assets). Optional, and changes show up within 5 seconds.

Your additions and overrides sit on top of the identity card. They never replace its structure.

## When to use which tier

- **Just deployed an instance?** The built-in default is doing its job. Leave
  it. Decide later whether you need to customize.
- **Want to set a name and mission for your team's instance?** Use
  Tier 2. Run [`spl site init` and `spl site set`](/docs/operate/site/content-overrides)
  to author a `core.site.v1` record, then `spl site publish` to make it
  live. Records are part of normal Syncropel coordination state: they
  back up with the rest of the instance, they federate over the Graph,
  and every version is kept.
- **Need to brand the instance for an organization with their own
  visual language?** Combine Tier 2 with [Tier 3 filesystem overlay](/docs/operate/site/filesystem-overlay).
  Tier 2 covers the copy; Tier 3 covers the typography and color and
  custom imagery.

## What's not in scope

The instance site is not a CMS. It's an identity card that publishes
what the instance is and where its capabilities live. If you need
articles, pages, or a navigable site map, that is what a workspace is
for, and workspaces are an entirely separate feature
(see [Workspaces](/docs/concepts/workspaces)).

There is also no JavaScript runtime on the rendered page beyond the DID
copy helper. Interactive surfaces live in workspaces or in Studio at
`syncropel.com`, mounted under their own origins with their own CSP and
their own state.

## How the page is chosen

The page you see at `GET /` is the latest `lifecycle: "published"` `core.site.v1` record on the `th_site` thread, owned by the operator's DID. That means:

- Every change to the landing page leaves a record. Reading the `th_site` thread shows the history of the site.
- To go back to an older version, add that version as a new record.
- Archiving the published record returns the instance to the built-in default. Nothing is lost.
- A draft (`lifecycle: "draft"`) is saved but not shown at `GET /` until you `spl site publish` it.
