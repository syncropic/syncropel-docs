Tier 2 is the record-driven layer of [the instance site](/docs/operate/site).
You author a `core.site.v1` record on the `th_site` thread and the instance applies its `content` slots on top of the built-in default. The
`spl site` commands manage it; the record is the
same one a provisioning script or a backup restore would write.

## The shape

A site record carries the operator's DID as `owner`, a lifecycle flag,
and an optional `content` object. Slots are optional. Leave a slot
absent to keep the built-in default for that field.

```json
{
  "kind": "core.site.v1",
  "schema_version": "1.0.0",
  "lifecycle": "published",
  "owner": "did:sync:user:alice",
  "content": {
    "name": "Acme Research Lab",
    "kind_label": "Coordination Instance",
    "heading": "A working Syncropel instance for the Acme research team.",
    "subheading": "All artifacts are records. Browse the capabilities below.",
    "links": [
      { "label": "Team notes", "href": "/w/handbook" },
      { "label": "GitHub", "href": "https://github.com/acme", "external": true },
      { "label": "Status", "href": "/health", "indicator": "live" }
    ],
    "connect": { "label": "Connect", "href": "https://syncropel.com/connect?url=https%3A%2F%2Facme.syncropel.app" },
    "did_display": true
  },
  "theme": {
    "accent": "#c2410c"
  }
}
```

### `content` slots

Every field is optional. Any slot you leave out keeps the built-in default, so you can set just the name and
leave everything else as is.

| Slot | Type | What it overrides | Default |
| --- | --- | --- | --- |
| `name` | string ≤ 128 | The large serif heading + `<title>` | "A Syncropel Instance" |
| `kind_label` | string ≤ 64 | The small mono uppercase label under the name | "Syncropel Instance" |
| `heading` | string ≤ 500 | The mission paragraph (serif, lead) | A one-line description of the coordination model |
| `subheading` | string ≤ 500 | The about paragraph (sans, muted) | (none) |
| `logo_ref` | string | Replace the generative glyph (`asset:<id>`, `https://...`, or `file:<name>`) | Generative glyph derived from instance DID |
| `links` | array, ≤ 6 | Replace the 6 default link cards | About, Docs, Get started, Capabilities, GitHub, Status |
| `connect` | object | Custom Connect button label + target, or `{"hidden": true}` to drop it | Connect → Studio for this instance |
| `did_display` | bool | Show / hide the DID copy footer | `true` |

### Link card shape

Each entry in `links` is a small object. The renderer encodes external
links with a `↗` glyph and `target="_blank"` automatically when
`external: true`.

```json
{
  "label": "Status",
  "href": "/health",
  "external": false,
  "indicator": "live"
}
```

The `indicator` field accepts `"live"`, which shows a small
animated green dot next to the label, used for status surfaces. 

### `theme` (limit)

The `theme.accent` field is part of the record, but the page does not apply it. Setting `theme.accent` in the record has no visible effect. To change the accent, use `theme.css` in the [Tier 3 filesystem overlay](/docs/operate/site/filesystem-overlay).

## The `spl site` family

The CLI manages the record for you. Every command reads or writes records;
there is no separate state file.

### Initialise a draft

```bash
spl site init
```

Creates an empty `core.site.v1` draft record on `th_site` for your
operator DID. Fails if a draft already exists. Pass `--force` to
overwrite. A draft is invisible to `GET /`; the built-in default keeps
serving until you publish.

### Inspect what you have

```bash
spl site show              # shows the draft if any, else the published record
spl site show --published  # forces the published view
spl site show --json       # JSON shape for scripting / piping
```

### Patch content slots

```bash
spl site set --name "Acme Research Lab"
spl site set --kind-label "Coordination Instance"
spl site set --heading "A working Syncropel instance for the Acme team."
spl site set --subheading "All artifacts are records. Browse the capabilities below."
spl site set --did-display true
```

`set` is a patch: flags you don't pass leave the corresponding slot
unchanged. To clear a slot and fall back to the built-in default, use
`--unset`:

```bash
spl site set --unset heading           # clear one slot
spl site set --unset name kind_label   # clear several at once
```

### Manage the links grid

```bash
# Append a link (up to 6 in total; they replace the default links)
spl site link add --label "Status" --href "/health" --indicator live
spl site link add --label "GitHub" --href "https://github.com/acme" --external
spl site link add --label "Team notes" --href "/w/handbook"

# Remove the Nth link (0-indexed)
spl site link remove 2

# Clear all overrides and fall back to the 6 default links
spl site link clear
```

### Manage the Connect button

```bash
# Custom Connect button label + target
spl site connect set --label "Open in Studio" --href "https://syncropel.com/connect?url=https%3A%2F%2Facme.syncropel.app"

# Hide the Connect button entirely
spl site connect hide

# Clear the override and restore the default Connect → Studio
spl site connect unset
```

### Theme accent

```bash
spl site theme --accent "#c2410c"   # set the accent (no visible effect; see the limit above)
spl site theme --unset              # clear the override
```

### Preview before publishing

```bash
spl site preview                              # writes /tmp/spl-site-preview.html
spl site preview --out ./preview.html         # custom output path
spl site preview --out ./preview.html --published  # preview the published version
```

Opens nothing. The verb only writes the file. Open it in your browser
to verify the look before promoting the draft.

### Publish

```bash
spl site publish
```

Promotes the current draft to `lifecycle: "published"`. The next
`GET /` serves it. Publishing adds a new record, so the old version is kept, and reading `th_site` shows the full history of edits.

### Archive

```bash
spl site archive
```

Archives the current published record. After archival the instance
falls back to the built-in default. To return to
the published content, publish a new draft.

## What the history looks like

After a typical editing session, the `th_site` thread holds one or two records per version:

```
th_site
├── PUT  clock=0   lifecycle=draft       (spl site init)
├── PUT  clock=1   lifecycle=draft       (spl site set --name ...)
├── PUT  clock=2   lifecycle=draft       (spl site set --heading ...)
├── PUT  clock=3   lifecycle=published   (spl site publish)
├── PUT  clock=4   lifecycle=draft       (next iteration)
└── PUT  clock=5   lifecycle=published   (spl site publish again)
```

To read it:

```bash
spl thread records th_site -o json | jq '.records[] | {clock, lifecycle: .body.lifecycle}'
```

To go back to an earlier published version, copy that record's `body` and write it again as a new record. Nothing is ever overwritten; every change is added.

## Fleet seeding

For instances provisioned from a blueprint or scripted from a fleet
runbook, the record is what you check in. Keep your `core.site.v1`
document in version control alongside your provisioning scripts, then
POST it through `/v1/records` with the operator's DID as `actor` as a
post-provision step. The same file produces the same site on every instance you seed it into, so a checked-in site record is the simplest way to keep a fleet's landing pages consistent.
