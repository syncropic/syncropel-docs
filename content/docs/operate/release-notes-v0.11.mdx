## TL;DR

v0.11.0 is the **Fleet release** — the first Syncropel release where multi-instance stops being possible-but-uncoordinated (v0.10.0's isolation primitives) and becomes coordinated-parallel-work. A single operator can now direct a fleet of worker instances from one CLI, fan out parallelizable tasks across them, watch the barrier join, and stop anything going wrong via a three-level kill switch.

This is the release where "my spl daemon" becomes "my spl fleet" and the system delivers on the core value prop identified in [research/compute-plane/06](https://github.com/syncropic/syncropel-research/blob/main/docs/compute-plane/06-distributed-execution-topology.md): **parallel velocity without the single-node ceiling**.

Upgrading from v0.10.x is zero-touch: instances without fleet config behave exactly like v0.10.0. No data migration. No breaking changes.

## Headline features

### Instance registry + three-level kill switch (ADR-021)

Every v0.11+ instance can emit heartbeat records at a configured interval to a nominated coordinator instance. The coordinator folds these into a live-instance map queryable via `spl fleet list`, `spl fleet status`, `spl fleet ping`, and a new `GET /v1/fleet/status` HTTP endpoint.

A three-level kill switch built as LEARN records on `th_fleet_control` lets operators freeze or emergency-stop work at the namespace or fleet-wide level, with audit trail preserved as records:

- **Soft freeze** — deny new `INTEND`/`DO`/`CALL` in a namespace; allow `KNOW`/`LEARN` so in-flight work drains cleanly
- **Hard freeze** — soft plus a configurable grace window after which all ingest is refused
- **Emergency stop** — fleet-wide dial to zero, no new work anywhere, state remains inspectable

All levels reversed by counter-records. Permission rules back the enforcement via three new CEL stdlib bindings: `fleet_frozen_namespaces()`, `fleet_hard_frozen_past_grace()`, `fleet_emergency_active()`.

See [ADR-021](https://github.com/syncropic/syncropel-spec/blob/main/15-decisions/ADR-021-instance-registry-and-kill-switch.md) for the full design.

### Task fan-out + barrier join (ADR-022)

A parent INTEND can declare `body.subtasks` as a list of descriptors (`goal`, `target` worker, `budget_usd`, `timeout_secs`, `depends_on`) and `body.join` as a predicate. The engine's fan-out reconciler spawns one child INTEND per descriptor via the instance registry, each worker executes its subtask autonomously through the existing unified dispatch pipeline, and a join fold reads completion records back to the coordinator to emit the parent KNOW when the predicate is satisfied.

Join predicates accept shorthand (`"all"`, `"any"`, `"k_of_n:K"`) or full CEL expressions against a new `children` binding (list of `ChildResult` with `verdict`/`cost_usd`/`wall_time_secs`/`summary` per child). The `join` context is the eighth CEL context, following Trigger, Routing, Precondition, FoldRule, HealthCheck, AITL, and Permission.

Four built-in routing strategies: `worker-<alias>` direct, `specific:<did>` exact, `least-loaded-worker` (lowest `active_dispatches` from heartbeats), `round-robin` (deterministic by parent + index hash).

CLI surface: `spl task fan-out <alias> --subtask '...' --subtask '...' --join all`, `spl task join-status <parent-alias>`, `spl task retry <parent> --subtask <index>`. Each `--subtask` flag accepts a comma-separated list of `key=value` pairs for `goal`, `target`, `budget`, `timeout`, and `depends` (plus-separated indices for sequential dependencies).

Content-addressed child thread IDs (`sha256(parent.id + index + goal)`) make re-spawning idempotent; a hiccup during spawn can be safely retried and does not produce duplicate children.

See [ADR-022](https://github.com/syncropic/syncropel-spec/blob/main/15-decisions/ADR-022-task-fan-out-and-barrier.md) for the full design.

### Fleet convenience CLI

- `spl fleet start --workers N [--share THREADS]` — boot 1 coordinator + N workers locally with auto-assigned `SYNCROPEL_HOME` paths and ports. Workers auto-register via heartbeat. The `--share` flag (default: `--shared-system`) snapshots the coordinator's shared system threads (`th_engine_config`, `th_actor_registry`, `th_namespace_registry`, `th_fleet_control`) and restores them into each worker, so workers inherit the coordinator's adapter registry and routing rules and can immediately dispatch real work.
- `spl fleet stop --workers` — stop workers, keep coordinator running (common end-of-day).
- `spl fleet stop --all` — tear down everything.

Worker state roots are persistent across fleet restarts, so `spl fleet start --workers 2` tomorrow picks up where you left off.

### Thread snapshot/restore primitive (ADR-023)

v0.11.0 introduces a foundational replication primitive: **thread snapshot/restore**. This is the operation underneath `spl fleet start --share` and is also exposed as user-facing CLI commands and HTTP routes for backup, migration, and Phase 4 federation.

- **`spl thread snapshot <thread> [--out FILE]`** — serialize a thread's records into a deterministic JSONL file (`.snap.jsonl`, content-type `application/x-ndjson`). Supports `--threads th_a,th_b,th_c` for multi-thread snapshots, `--shared-system` for the four reserved system threads, `--all` for the entire instance, `--include-l0` to control hash level inclusion, `--causal-closure` to follow parent references across threads.
- **`spl thread restore [--in FILE]`** — ingest a snapshot file into the local store. Supports `--dry-run` (validate without ingesting), `--on-conflict skip|fail|accept-existing`. Restore is **idempotent** — re-running with a snapshot whose records already exist is a no-op for those records. Records are validated (canonical hash recomputed and matched, parents checked, fields validated) before ingest, so a tampered snapshot file cannot corrupt the destination.
- **`GET /v1/threads/snapshot`** and **`POST /v1/threads/restore`** — the HTTP routes wrapping the store-trait methods. Permission-gated via two new resources: `thread_snapshot` and `thread_restore`. Operators who have CEL permission enforcement enabled (per [SKL-0204 lockout protection](/docs/guides/cel-expressions)) MUST include these resources in their admin allow rule.

The primitive is the foundation that backup, migration, audit-export unification, and Phase 4 federation will all extend. The architecture is layered (per ADR-023 §"Layered Architecture"): v0.11 ships L0 (the primitive) + L1 (`spl fleet start --share` wiring); v0.12 will add L2 (reactive sync, adopting the CouchDB Replication Protocol v2 semantics); Phase 4 will add L5 (federation, gated by the consent records specified in §08-governance/06).

The full design is in **ADR-023** with a Prior Art Alignment table mapping every decision to the giant it stands on (Git bundle, IPFS/IPLD, CouchDB, Hypercore, EventStoreDB, OAuth, Solid, GDPR, Matrix). The prior-art survey itself is at `research/compute-plane/10-replication-prior-art.md`.

### Foundation F8 revised — L0 sharing as a consent-gated policy (ADR-024)

v0.11.0 includes the **first revision of a Frozen Foundation in Syncropel's history**. Foundation F8 — the L0 sharing rule — has been revised from absolute prohibition to a default-closed, consent-gated policy:

| | Before v0.11.0 | v0.11.0 onward |
|---|---|---|
| Wording | "L0 hashes MUST NEVER leave the local namespace" | "L0 hashes MUST NOT cross namespace boundaries without explicit mutual consent. Intra-namespace sharing is permitted." |
| Intra-namespace sharing (workers under same operator) | Forbidden by literal reading | **Permitted by default** (no consent records needed) |
| Cross-namespace sharing (different trust domains) | Forbidden full-stop | **Default closed**, gated by mutual consent records on `th_consent` |
| Privacy invariant | Preserved by absolute rule | **Preserved by default-closed policy** |

**What this changes for you**:

- **Intra-namespace operations now legal**: fleet bootstrap, backup, migration, and multi-machine deployment under one operator now work without violating F8. The `spl fleet start --share` command (above) is the immediate beneficiary.
- **Phase 4 federation has a foundation**: the consent record schema in §08-governance/06 is the contract that future federation will implement against. v0.11.0 reserves the `th_consent` thread name and ships the schema; the cross-namespace enforcement layer ships in Phase 4.
- **No action required for existing deployments**: the revision is strictly more permissive than the original. Anything that was legal under the old F8 is still legal. New behavior (intra-namespace L0 sharing) was previously a grey area but never enforced — it is now officially legal.

The full reasoning, the six alternatives considered and rejected, and the consent record schema are in **ADR-024**. The prior-art justification (GDPR, Solid, Matrix, OAuth, Mastodon allow-lists) is in `research/compute-plane/10` §"Consent and privacy models". The revised F8 wording is in §14-reference/03-frozen-foundations.

This is the first foundation revision; it sets the precedent that foundations CAN be revised when they are demonstrably wrong, but only with explicit operator approval through an ADR.

### Measured parallel velocity

**Pass criterion committed pre-release** (per [measurement methodology](https://github.com/syncropic/syncropel-research/blob/main/docs/compute-plane/09-v0.11-bootstrap-measurement-methodology.md)): at least 2 of 3 real bootstrap drills show a parallel speedup ratio ≥ 1.5×, with no naked regressions (any drill below 1.0× must have a named confounder, not anomalous overhead).

**Bootstrap drill results** (run 2026-04-14 against real v0.11 release-doc work on a sandboxed 2-instance fleet):

- **Drill 1** — 3-subtask fan-out across 3 instances writing 3 independent markdown docs (snapshot inspection guide, fleet architecture doc, v0.11 launch blog draft). Serial baseline 186s, parallel 190s, **speedup 0.98×**. Confounder: 3-way concurrent claude subprocess dispatches hit a substrate ceiling at Anthropic API account-level concurrency + local CPU/memory pressure. Not a Syncropel engine limit; per methodology this confounded drill does not disqualify the gate.
- **Drill 2** — 2-subtask fan-out across 2 instances writing the fleet CLI reference + .snap.jsonl format reference. Serial 143.0s, parallel 52.9s, **speedup 2.71×**. Clean pass. Total cost $1.77.
- **Drill 3** — 2-subtask fan-out across 2 instances writing the v0.10 → v0.11 migration guide + v0.11 release-notes draft (heterogeneous prompts). Serial 175.1s, parallel 78.8s, **speedup 2.22×**. Clean pass. Total cost $1.51.

**Gate disposition: PASS.** 2 of 3 drills show ≥1.5× speedup (drills 2 and 3) and the one drill below 1.0× has a named substrate confounder. Aggregate: 10 real files produced across the drill set, all subsequently merged or available as release-doc source material.

**Key finding**: 2-way fleet fan-out delivers clean parallel speedup. 3-way concurrency hits a substrate ceiling bounded by LLM provider concurrency + local resources, not the Syncropel engine. For real v0.11 workloads the practical shipping recommendation is 2-way fan-out until the substrate ceiling is diagnosed further in v0.11.x.

## Migration from v0.10.x

### What you don't need to do

- **No data migration.** v0.11 reads v0.10 SQLite stores byte-identically. No schema change, no fold replay discrepancy, no trust reset.
- **No config migration by default.** The `[fleet]` config section is additive. Instances with no fleet config behave exactly like v0.10.0 — single-instance mode, no heartbeats, no coordinator involvement.
- **No record format change.** The 8 fields of the record are unchanged. v0.11 adds optional fields like `body.subtasks` and `body.join` that v0.10 would simply ignore as unknown body fields.
- **No CLI surface removal.** Every v0.10 command still works identically. The v0.11 additions (`spl fleet`, `spl kill`, `spl task fan-out`, `spl task join-status`, `spl task retry`) are additive.
- **No CEL context removal.** The seven existing contexts (Trigger, Routing, Precondition, FoldRule, HealthCheck, AITL, Permission) behave identically. The eighth (Join) is additive and only evaluated for fan-out parent INTENDs.

In short: if your v0.10.x deployment does not opt into multi-instance operation, the upgrade is a drop-in binary replacement.

### What you do if you want multi-instance

1. **Upgrade the binary.** `curl https://get.syncropic.com/spl | sh` installs v0.11.0 over v0.10.x. The binary replacement is atomic (Linux `rename(2)` semantics).
2. **Restart the prod daemon** cleanly: `spl serve --stop && spl serve --daemon`. It'll re-open the SQLite store at `~/.syncro/hub.db`, rebuild trust from records, and come up on v0.11.0.
3. **Verify health**: `spl doctor` should pass 7/7. `spl status` should report `v0.11.0`.
4. **Configure fleet operation**, choose one approach:

   **Approach A — Single-laptop worktree fleet** (recommended starting point):

   ```bash
   spl fleet start --workers 2
   ```

   This boots the existing prod daemon as coordinator plus two worker daemons at `~/.syncro-worker-{a,b}` on ports 9201 and 9202. Each worker's config.toml gets `[fleet] coordinator_url = "http://127.0.0.1:9100"` automatically.

   **Approach B — Manual multi-host fleet**: edit each instance's `~/.syncro/config.toml` to add a `[fleet]` section, then restart each daemon:

   ```toml
   [fleet]
   coordinator_url = "http://coordinator.example.com:9100"
   heartbeat_interval_secs = 15
   advertised_endpoint = "http://worker-a.example.com:9100"
   ```

   The advertised endpoint is the URL other instances should use to reach this one. `SPL_FLEET_COORDINATOR_URL` env var takes precedence over the config file if set.

5. **Verify the fleet is live**: `spl fleet list` should show all instances with status `live` and recent heartbeats.

See the [Operator Runbook: Multi-instance fleet operations](/docs/operate/runbook#multi-instance-fleet-operations) for day-2 procedures (coordinator failover, worker crash recovery, fleet-wide upgrade, teardown, kill drills).

### What you can safely ignore

If you're running a single-node deployment and will continue to, everything in v0.11 is opt-in. You don't need to learn the fleet CLI, the kill switch commands, the fan-out descriptor format, or any of the new CEL bindings. Your existing workflows work identically.

## New CLI commands at a glance

```bash
# Fleet lifecycle (local convenience wrapper)
spl fleet start [--workers N]
spl fleet stop [--workers | --all]

# Fleet observability
spl fleet list                         # instances by DID, endpoint, status, role, uptime, load
spl fleet show <did>                   # detailed view of one instance
spl fleet ping <did>                   # HTTP reachability + latency
spl fleet status [--live]              # aggregate: live/stale/archived + frozen namespaces

# Kill switch
spl kill --namespace <ns> --level soft [--reason "..."]
spl kill --namespace <ns> --level hard [--grace <secs>] [--reason "..."]
spl kill --emergency [--reason "..."]
spl unkill --namespace <ns>
spl unkill --emergency

# Task fan-out
spl task fan-out <alias> \
  --subtask 'goal=...,target=worker-a,budget=2.00,timeout=1800' \
  --subtask 'goal=...,target=worker-b,budget=2.00,timeout=1800' \
  --subtask 'goal=...,target=least-loaded-worker,depends=0+1' \
  --join all
spl task join-status <parent-alias>
spl task retry <parent-alias> --subtask <index> [--hint "..."]
```

Full reference: [`spl fleet` + `spl kill`](/docs/reference/cli#fleet-v0110).

## What's explicitly NOT in v0.11

Honest scope discipline. These are valid concerns we are deferring, not gaps we are denying:

- **Autonomous budget enforcement.** The `budget_usd` field on fan-out descriptors is advisory; the engine does not refuse a subtask for budget reasons. Budget accounting is Phase 3, shipping in v0.12. The kill switch is the manual stop-gap.
- **Merge queue.** Parallel workers still write to their own git branches; integrating them into main is manual and can hit text-level conflicts that v0.11 does not arbitrate. Phase 3.
- **Automatic worker reassignment on crash.** v0.11 requires operator intervention (`spl task retry --subtask <index>`) when a worker dies mid-subtask. Phase 3.
- **Cross-instance record sync (federation).** The fleet in v0.11 uses targeted HTTP POST for parent-child communication. General record sync, trust propagation across instances, and CRDT convergence are Phase 4 (v0.13+).
- **Coordinator election / automatic failover.** The coordinator is a single nominated instance. If it dies, workers continue operating locally but lose fleet coordination until an operator manually promotes a new coordinator. Phase 4.
- **Managed hosting on Kubernetes.** The primitives v0.11 ships are the same primitives a k8s deployment would need, but the deployment layer, per-user pod provisioning, ingress routing, and billing hooks are Phase 5 (v1.0+).
- **Recursive fan-out.** A child can be an INTEND with its own `body.subtasks`, but the v0.11 reconciler only handles one-level flat fan-out. Recursive cases are deferred to when they're concretely needed.
- **General DAG dependencies.** `depends_on` is a simple sequential marker (index list, cycle-checked at parse). Complex DAGs with merges, conditional branches, or loops are out of scope.

For a single-tenant deployment or trusted-actor multi-tenant setup, v0.11 is production-ready. For untrusted multi-tenant where workers must be isolated from each other's state beyond what namespaces provide, you want Phase 3 + Phase 4 gaps closed first.

## What's next — v0.12 preview

v0.12 is the **Safety release**. It turns human-gated parallelism (v0.11) into autonomous-ready parallelism by shipping the Phase 3 primitives:

- **Budget + quota enforcement** — live accounting in the TICK loop, CEL rules deny new work when namespace budget is exhausted
- **Merge queue** — serialized integration of parallel workers' git work, with record-level and text-level conflict detection
- **Graceful drain** — a state machine where an instance rejects new intents while completing in-flight ones with a configurable grace window
- **Chaos testing harness** — scripted failure injection against the Docker fleet, recovery verification
- **Automatic worker reassignment on crash** — the operator step that v0.11 requires becomes automatic

v0.13 (Federation) and v1.0 (Managed hosting) follow. See [research/compute-plane/06 §10 roadmap](https://github.com/syncropic/syncropel-research/blob/main/docs/compute-plane/06-distributed-execution-topology.md#10-phased-implementation-roadmap) for the full five-phase trajectory.

## Known limitations

- `fleet.rs` is a single 854-LOC module. It exceeds the project's 800-line "acceptable" file size band by a modest margin. Splitting is deferred until Phase 2 Full's fan-out code pressures the module further; defensible because the `InstanceRegistry` + `FleetControlRegistry` + `FleetSnapshot` surface is tightly coupled and a premature split would hurt cohesion.
- `GET /v1/fleet/status` re-folds from the SQLite store on every request instead of using a cached snapshot. This keeps the endpoint working in test harnesses where the reconciler loop isn't running, at the cost of a small per-request overhead. For v0.11 scale (3-10 instance fleets), this is a non-issue; v0.12 may add caching when fleet sizes grow.
- Instance DIDs in v0.11 use a fallback `hash(HOSTNAME + advertised_endpoint)` derivation because ADR-020 Part 2 (canonical bootstrap-derived DID) has not yet shipped. The fallback is collision-free as long as co-resident instances have distinct `advertised_endpoint` values (which the `spl fleet start` wrapper enforces). Part 2 of ADR-020, planned for v0.12, stabilizes the DID format; existing v0.11 fleets will auto-upgrade their DIDs on next restart when that ships.
