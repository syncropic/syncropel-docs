## Audience

This page is for the operator standing up an `spl serve` instance for real work: laptop, server, container, or a Syncropic-hosted instance. It covers the lifecycle from `spl init` to teardown.

If something is broken right now, jump to [Recovery](/docs/operate/runbook#recovery-from-corruption-or-data-loss) on the runbook page. The lifecycle below assumes you're starting clean.

## 1. Provisioning

### Self-hosted (laptop, server, VPS)

Install the binary, then run the setup wizard:

```bash
curl -sSf https://get.syncropic.com/spl | sh
spl init
```

`spl init` creates `~/.syncro/`, generates an instance identity (or surfaces the existing one), and prints the next-step commands. It does not start the instance.

Start the instance as a foreground process the first time so you can see what it's doing:

```bash
spl serve
```

You should see a startup banner naming the bind address, the SQLite path, and the backup destination. `Ctrl-C` to stop. Once you're satisfied, run it in the background:

```bash
spl serve --daemon
spl status
```

For an instance that survives reboots, see [Keeping Your Instance Running](/docs/operate/persist-instance): `systemd` user units on Linux, `launchd` plists on macOS, and Windows Service wrappers are all documented there.

### Hosted

Hosted instances are provisioned for you: sign in at syncropel.com and the instance comes up at `<label>.syncropel.app`. You connect with the code shown at sign-up, and every recipe on this page that uses the CLI works against it from there.

## 2. First-run bootstrap

A fresh database has zero service accounts. The auth middleware rejects every unauthenticated request, including the request you'd use to mint your first SA. Two paths through the chicken-and-egg:

### Path A: `--insecure-localhost` (laptop dev)

Restart the instance with `--insecure-localhost`. It binds 127.0.0.1 only and disables auth. Mint an SA via the bootstrap endpoint:

```bash
spl stop
spl serve --insecure-localhost &

curl -fsS -X POST http://127.0.0.1:9100/v1/bootstrap/service-account \
  -H 'content-type: application/json' \
  -d '{"sa_id":"sa-admin","scopes":["admin"]}'
# → 201 + bearer token; copy the token (it is shown once).

spl token save "$BEARER"
spl stop
spl serve
```

This is the path documented in [Authentication & Service Accounts](/docs/operate/keyring) and is fine for a single-user laptop. Avoid it on multi-tenant hosts: any local user can curl 127.0.0.1.

### Path B: hosted (no shell access)

Sign in at syncropel.com and provision. The instance is bootstrapped for you and you receive a working `https://<label>.syncropel.app` URL; connect with the code shown at sign-up.

## 3. Auth posture for production

Once bootstrapped, treat `auth.required = true` as load-bearing. It is the default and every route enforces it (including the federation surface). Specifics live in [Authentication & Service Accounts](/docs/operate/keyring); the operational rules are:

- One service account per tool/agent/integration. Closed scope per SA: `records:read,records:write` for an emitter, `admin` only when minting tokens or setting policy.
- Tokens carry a snapshot of the SA's scopes at issuance time. Live-edit the SA's scopes for new tokens; revoke + re-mint the existing token only when scopes shrink.
- Save the token once via `spl token save <bearer>`; the CLI auto-injects it for every subsequent invocation.
- Permission rules (written as CEL expressions) fail closed: a request no rule allows is denied. Before turning on a permission rule, run `spl config permissions-enable`. Its preflight refuses unless allow-rules cover `record_write`, `thread_read`, and `config_read` for the instance's own actor. Skipping the preflight is how operators lock themselves out.

If the instance is ever exposed beyond loopback, stand up a CORS allowlist before the first cross-origin browser hit:

```bash
spl config auth-set-cors-origins https://syncropel.com https://app.example.com
```

## 4. Backup discipline

> **CRITICAL: read this section twice.** Syncropel's startup backup is a safety net, not a backup system. It will not save you if you don't supplement it with off-host copies. 

### What the instance does for you

On every startup, `spl serve` snapshots `~/.syncro/hub.db` to `~/.local/share/syncropel/backups/<instance-key>/hub.db.bak`. The destination lives outside `~/.syncro/`, so a `rm -rf ~/.syncro/` does not nuke the backup.

The `<instance-key>` is normally `instance-<did-tail>`, the 24-hex tail of the instance DID. To find your directory:

```bash
curl -s localhost:9100/health | jq -r .instance_did
ls ~/.local/share/syncropel/backups/instance-<tail>/
```

The daily backup job writes timestamped `hub.db.<YYYYMMDD-HHMMSS>` copies into the same per-instance directory.

### What the instance does NOT do

The startup backup is **destructive on every restart**. If `hub.db` is empty, corrupt, or wrong when the instance starts, that empty/corrupt/wrong file overwrites the backup. By the time you notice, the good copy is gone.

### What you should do instead

Schedule an off-host snapshot of the rolling backup. Daily is enough for most workloads:

```bash
DEST=$HOME/backups/syncropel
mkdir -p "$DEST"
cp ~/.local/share/syncropel/backups/*/hub.db.bak \
   "$DEST/hub.db.$(date +%Y%m%d-%H%M%S).bak"
find "$DEST" -name 'hub.db.*.bak' -mtime +14 -delete
```

For containerised deployments, mount a host directory into the backup path so the rolling backup survives the container's ephemeral filesystem.

### Manual snapshot (before risky operations)

Right before an upgrade, a permission rule rollout, or a destructive migration:

```bash
cp ~/.syncro/hub.db ~/.local/share/syncropel/backups/hub.db.before-$(date +%Y%m%d-%H%M%S)
```

You do not need to stop the instance, but avoid doing this during a burst of heavy writing. Watch `spl status` first.

### Restore

```bash
spl stop
cp ~/.local/share/syncropel/backups/<instance-key>/hub.db.bak ~/.syncro/hub.db
spl serve
```

On startup, trust scores and configuration are rebuilt from your records. Task content files and alias mappings live in `~/.syncro-data/` and are unaffected by `hub.db` operations. They survive on their own.

> **WSL2 / UNC paths.** If `~/.syncro/` resolves to a UNC path (`\\wsl.localhost\...`) when accessed from Windows tooling, SQLite's file locks behave erratically. Keep `hub.db` on a native Linux filesystem (the WSL home directory itself) and copy backups out via `cp` rather than letting Windows Explorer touch them.

## 5. Health probes

Three probe surfaces, three intended consumers.

| Path | Returns | Use for |
|---|---|---|
| `GET /health` | `200 ok` if process is alive and bound | Load-balancer liveness / platform health checks |
| `GET /v1/engine/health` | JSON with processing counters, queue depth, and pending decision count | Operator readiness, alerting |
| `GET /v1/engine/health` (with `details=true`) | Full breakdown including rule-cache stats | Capacity planning, debugging |

Liveness:

```bash
curl -fsS http://localhost:9100/health
# ok
```

Readiness (sample):

```bash
curl -fsS http://localhost:9100/v1/engine/health | jq
# {
#   "ingested_total": 18432,
#   "reconciled_total": 18391,
#   "reconcile_queue_depth": 2,
#   "decisions_pending": 0,
#   "intelligence_enabled": true,
#   "uptime_secs": 86400
# }
```

`reconcile_queue_depth` should be near zero when things are steady. A growing queue while records keep arriving means an adapter has stalled; check `/v1/engine/health?details=true` for which thread is backed up, then `spl debug replay <thread>` to walk the records.

Rule cache statistics:

```bash
curl -fsS http://localhost:9100/v1/engine/expression_cache/stats | jq
# Healthy: hit rate > 99%, average compile time < 100μs, size well under the capacity (1024).
```

A spike in compile errors usually means a bad rule was added; check `spl config list-rules` and the most recent configuration record.

## 6. Teardown

Tearing down for real (decommissioning the host, moving to another machine, retiring an instance):

### Drain

Refuse new dispatches but let in-flight ones finish:

```bash
spl drain start
spl drain status   # waits until in-flight = 0
```

### Stop the instance gracefully

```bash
spl stop
```

This sends `SIGTERM`. The instance finishes pending writes, closes the socket, and removes its PID file. If `spl stop` reports "not running" but the port is still bound, see the [orphan-recovery section on the runbook](/docs/operate/runbook).

### Reclaim space (optional)

The store file does not shrink on its own after an upgrade or a large deletion. With the instance stopped, compact the store file with your database tooling to reclaim it. Budget roughly twice the file size in free disk and expect an exclusive lock for the duration (minutes on multi-gigabyte ledgers). Do not compact a running instance.

### Archive

```bash
TS=$(date +%Y%m%d-%H%M%S)
tar czf ~/syncropel-archive-$TS.tar.gz \
    -C "$HOME" .syncro .syncro-data .local/share/syncropel
```

The three directories together capture everything: `~/.syncro/` is the instance state and identity, `~/.syncro-data/` is task content + alias mappings, `~/.local/share/syncropel/` is the rolling backup history. Move the tarball off-host before deleting the originals.

### Delete

Only after the archive is verified somewhere durable:

```bash
rm -rf ~/.syncro ~/.syncro-data ~/.local/share/syncropel
```

If the instance had a federation pair, run `spl federation revoke <pair-id>` against the peer first. See [Federation Pairing](/docs/operate/federation-pairing) for the full pair-revocation procedure.
