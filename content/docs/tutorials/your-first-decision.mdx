## What you'll learn

In about 30 minutes, you'll use the **decision gate**, which lets your workspace learn. You'll write a record that Syncropel doesn't yet know how to route, see it raise a **decision request** for your approval, approve it, and check that the next similar record routes without any new reasoning.

Syncropel never silently changes routing or permissions. It proposes, you decide, and your decision is saved as a record that is reused later.

<Callout type="info">
A proposal is a `core.work.decision_request.v1` record, and you answer it with `spl decisions`. Syncropel proposes, a person decides, and the decision is kept.
</Callout>

## Before you start

- `spl` installed (`spl --version`)
- A running workspace — either local (`spl serve`) or hosted (`<label>.syncropel.app`).
- `spl status` returns `healthy`.
- A model provider key configured (`spl config set-key anthropic <key>`), because Syncropel needs a model to reason about new routing. On a hosted workspace the key is already set up.

If you've never emitted a record before, do [Your first thread](./first-thread) first. This tutorial assumes you can read `spl thread records <id>` output.

## 1. Confirm proposals are enabled

Proposals (Syncropel reasoning about unrouted work and suggesting a rule) are off by default on local installs. Check:

```bash
spl config show | grep -i intelligence
```

If you see `intelligence_enabled: false` (or no entry at all), enable it by giving Syncropel a model to use:

```bash
spl config set-key anthropic <your-key>
spl config model claude-sonnet-4-6
```

The change applies right away, with no restart.

## 2. Emit a record with no matching routing rule

Pick a body kind the workspace hasn't seen. The simplest is a fresh thread with a do-something intent:

```bash
spl intend "Translate the README.md to French" --thread th_fr_translate
```

Output includes a record id and thread id:

```
✓ Record created
  thread:  th_fr_translate
  record:  rec_8a3c...
  act:     INTEND
```

Syncropel checks for a matching rule or pattern and finds none. That miss is what triggers a proposal.

## 3. See the proposal land in the decision queue

Within a few seconds, Syncropel reasons about the unrouted intent. Because it isn't confident enough to apply the rule on its own, it raises a **decision request** and waits for you. List the pending decisions:

```bash
spl decisions list
```

You'll see something like:

```
◈  72%  Intelligence proposal (confidence 72%): Add a new routing rule
        that matches INTENDs like "translate <doc> to <lang>" and routes
        them to the translator agent.
        id: e6a0f87dfc917aba...
        spl decisions approve e6a0f87dfc917aba

1 pending
```

The request includes the matching expression Syncropel suggests, the recommended target actor, and a confidence score. The full body is visible with:

```bash
spl decisions list --json | jq '.[0]'
```

Until you act, no rule exists and no future record will route differently. The pending decision also shows up in `spl resume` under **NEEDS**. The decision gate is the one place for everything waiting on you.

## 4. Approve the proposal

`spl decisions approve` is shorthand for `choose <id> approve`. Approving a routing proposal applies it:

```bash
spl decisions approve e6a0f87dfc917aba
```

Output:

```
✓ Decision answered
  request:  e6a0f87dfc917aba...
  response: approve
  result:   routing_rule_added (name: routing_translator_v1)
```

What happened: your approval is itself a record, a DO with `body.fulfills` pointing at the `core.work.decision_request.v1`. Syncropel saw the answer, recognized a routing-rule proposal, and saved a `routing_rule.add.v1` LEARN on `th_engine_config`. The rule applies right away. It is stored as records, so it survives restarts and travels with `spl export` and `spl import`.

Verify the rule landed:

```bash
spl config list-rules
```

You should see `routing_translator_v1` in the list.

<Callout type="info">
**Three ways to answer a decision.** Not every decision is yes or no. A `core.work.decision_request.v1` asks for one of three kinds of answer, and the CLI has a command for each:

- **CHOOSE** — pick from declared options. `spl decisions choose <id> <option-id>`; `approve` / `reject` are sugar for the common two-option case.
- **PROVIDE** — supply an open value. `spl decisions provide <id> --value <json-or-string>`.
- **ACKNOWLEDGE** — a plain "seen it". `spl decisions ack <id>`.

It is the same gate and audit trail whoever is asking: Syncropel itself, a paused work loop, a `spl decompose` plan or a paired workspace.
</Callout>

## 5. Emit a similar record and watch it route automatically

```bash
spl intend "Translate the CONTRIBUTING.md to Spanish" --thread th_es_translate
```

This time the new rule matches, and the work goes to the translator agent without any new reasoning. Inspect the thread:

```bash
spl thread records th_es_translate
```

You should see two records back-to-back: your INTEND, and a follow-on DO from Syncropel with `body.dispatch_handled: true`, showing the route was used.

Compare to step 2's thread, which has only your bare INTEND with no follow-on — that is the difference between reasoning every time and reusing a learned rule.

## 6. Inspect the audit trail

The proposal, your answer, and the rule application are all records. The decision request opened on its own thread; the answer fulfills it; the rule application lands on `th_engine_config`. Export the security-relevant slice — `spl audit export` emits one JSON record per line — and filter it:

```bash
spl audit export --since 1h | jq 'select(.body.kind | test("decision|routing_rule"))'
```

Every decision is a record, so the trail is complete (see [Governance](/docs/concepts/governance)).

## What just happened

You exercised Syncropel's **decision-record loop**:

1. **No match is useful.** When routing finds no match, Syncropel doesn't fall back to a default. It raises a `core.work.decision_request.v1` and waits.
2. **Your answer is a record.** It is a DO that fulfills the request, and it stays on record through export, import and audit.
3. **Rules are records.** Routing rules are stored as LEARN records on `th_engine_config`.
4. **Reuse closes the loop.** The next similar record matches and skips reasoning, so the cost goes from one model call to checking one expression (see [patterns](/docs/concepts/patterns)).

Syncropel proposes, you decide, and your decision becomes a lasting record.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `spl decisions list` always returns empty | Proposals are disabled, so nothing was proposed. | Confirm `spl config show` reports a model and provider key. Enable with `spl config set-key <provider> <key>` and `spl config model <name>`. |
| A decision stays pending forever | You're reading from a paired workspace, not the one where the record was written. Decisions belong to the workspace that raised them. | Run `spl decisions list` against the workspace where the original record was written. Check `spl actor list` to confirm which DID is the active actor. |
| `spl decisions approve` returns `403 forbidden` | Default-secure auth on a hosted workspace — answering a decision emits a record, and the bearer token lacks write scope. | Mint a service account with write scope: `spl service-account create --name "Decider" --scopes records:write --with-token`, then `spl token save <token>`. |
| Approved rule didn't fire on the next similar record | The proposed rule is too narrow and matches only the exact first record. | Inspect with `spl config list-rules`, find the rule, and broaden its `match` expression. |
| `spl audit` shows no decision records after approving | The approve command ran against a different namespace from the one you're reading. | Pass `--namespace <ns>` to match the namespace the original record was emitted into. |
