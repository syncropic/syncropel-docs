## What you'll build

You've been running `spl serve` on your laptop, building up records, threads, federation pairs and trust. You want a hosted workspace with the same records, reachable from anywhere, with no `--insecure-localhost` flags. This tutorial walks through it: export locally, create a hosted workspace, import, point your CLI at it, verify, and pair again with the workspaces you were paired with.

Hosted and self-hosted workspaces run the same software. `spl export` and `spl import` copy your records from one to the other, and every record keeps its ID. The hosted workspace keeps the identity it was created with. It doesn't become your laptop's workspace, so the workspaces you paired with are paired again from it (see [Federation](/docs/concepts/federation)).

Allow about 30 minutes, most of it creating the workspace and verifying.

## Before you start

- `spl` installed (`spl --version`)
- A local workspace with some real content: a few threads and records, ideally one federation pair. If you're starting fresh, do [Working with threads](./first-thread) first so you have something to move.
- A browser to sign up at `syncropel.com`.
- No budget: hosted workspaces are free, up to three per account (see the [hosted plan](/docs/get-started/hosted)).

You can do this in one session, or rehearse it first. `spl import` is safe to run again.

## 1. Inspect what you're migrating

Before the export, see what is on your local workspace:

```bash
spl status
spl thread list
spl federation list
spl actor list
```

Note your pairings. They come across as records and don't work from the hosted workspace, so you'll make each one again in step 7.

Also note the record and thread counts on the `Store:` line of `spl status`. After the import, the hosted workspace holds these records and its own starting ones, so its count is higher.

## 2. Export the local workspace

```bash
spl export --no-identity --out ~/migration.tar.zst
```

Output:

```
wrote /home/you/migration.tar.zst (20005 bytes, tar.zst)
  carries: identity key no, credentials no
```

`--no-identity` leaves your local workspace's private key out of the bundle. An import never installs that key, so the hosted workspace has no use for it.

The bundle is a `tar.zst` archive containing:
- Every record
- A record of each pairing, your consent grants and your settings
- A signed manifest tying the bundle to the workspace that made it

Inspect what's in there without unpacking:

```bash
tar --zstd -tf ~/migration.tar.zst | head
```

You'll see `manifest.json`, `manifest.sig`, `records/<thread>/` and so on.

The bundle holds every record in your workspace, so keep it where only you can read it. By default `spl export` does **not** include bearer tokens, so a stolen bundle can't be used to sign in to your workspace. If you need tokens to keep working, pass `--carry-tokens`, but consider creating fresh tokens on the new workspace instead.

For more on what a bundle contains, see [Portability](/docs/guides/portability).

## 3. Provision a hosted workspace

Open a browser and go to `https://syncropel.com/signup`. Pick a label, which becomes your subdomain (for example `myteam.syncropel.app`; hosted workspaces live at `*.syncropel.app`), and confirm the plan.

What happens:
1. Your label is reserved.
2. A hosted workspace is created, running the same `spl serve` you have locally, with its own storage.
3. You land in your workspace, already connected. Your syncropel.com account owns it.

The ready screen shows:
- Your hosted URL (`<label>.syncropel.app`)
- A CLI access option that creates a device token (copy it if you work from a terminal)
- The commands to "Connect the CLI"

For setup failures (label already taken, workspace limit, timeout), see [Hosted onboarding: if setup doesn't finish](/docs/get-started/hosted#if-setup-doesnt-finish).

## 4. Connect your CLI to the hosted workspace

The ready screen gives you the commands. Here they are with placeholders:

```bash
export SPL_SERVE_URL=https://myteam.syncropel.app
spl token save <your-device-token>
spl status
```

`spl status` should report `Status:  ok`, and its `Store:` line shows the hosted workspace's store and not the one on your laptop. Your CLI now talks to the hosted workspace for the rest of this shell session. To make it permanent across shells:

```bash
echo 'export SPL_SERVE_URL=https://myteam.syncropel.app' >> ~/.bashrc   # or ~/.zshrc
```

Or save the URL in your shell profile (`spl config path` shows where your settings are).

## 5. Import the bundle into the hosted workspace

A workspace that has been started always holds some records of its own, so `spl import` refuses without `--force-overwrite`. Despite its name the flag replaces nothing: the import adds your records beside the ones already there. Check that `spl status` is answering from the hosted workspace (step 4), then:

```bash
spl import ~/migration.tar.zst --force-overwrite
```

Output:

```
imported from did:sync:instance:c530ad12a9e0810882aa0b2e
  bundle: 82 records / 23 threads / 1 pairs / 0 secret refs
  carries: identity key no, credentials no, file bytes yes
  this workspace answers as did:key:z6Mkgt9c...DL2K (its own identity, not the copy's)
  inserted: 58, deduplicated: 18, skipped: 6, failed: 0
    skipped 3a6c13303a72 (clock_taken): core.migration.v1 on th_audit_migrations by did:sync:system:engine at clock 0
    ...
  service-account tokens were revoked at export: re-mint with `spl service-account` if needed
```

The line to read is `this workspace answers as`. Your hosted workspace is still the workspace it was created as, now holding your records. The skipped records are starting records of your local workspace. The hosted one already holds its own.

## 6. Verify the round-trip

```bash
spl status
spl thread list | head -10
spl federation list
spl actor list
```

Compare with what you saw in step 1 on the local workspace:
- Your threads are listed, with the same thread IDs
- Your actors are listed
- Your pairings are listed, as records of what was paired (step 7)
- The record count on the `Store:` line is higher than it was locally, by the hosted workspace's own starting records

To check a thread, list its records on both sides:

```bash
spl thread records <some_thread_id>
```

Run this against both your local workspace (`SPL_SERVE_URL=http://localhost:9100 spl thread records ...`) and your hosted one (`SPL_SERVE_URL=https://myteam.syncropel.app spl thread records ...`). The record IDs should match. Each ID comes from the record's content, so a difference means something changed in transit.

An import does not change your records.

## 7. Pair again with other workspaces

If your local workspace was paired with other workspaces, those pairings don't work from the hosted one. Each of the other workspaces knows your local workspace, and the hosted workspace is a different one.

For each pairing you noted in step 1, pair again from the hosted side:

```bash
spl federation pair add <the other workspace's address>
```

The other workspace's owner approves it as they would any first pairing. You don't have to remove the copied record first. When you retire the local workspace (step 9), the other owner can revoke their pairing with it.

For the full flow, see [Pairing workspaces](/docs/guides/federation-pair).

## 8. Pair a second device (optional)

While your hosted workspace is fresh, this is a good moment to add a second device, such as your phone, a second laptop or an office machine. From the **hosted** side:

```bash
spl pair --device "iPhone" --url https://myteam.syncropel.app --scopes records:write
```

This creates a one-time code and prints a link and QR code. Open the link on the second device's Syncropel app (or paste the code into the app's "pair device" prompt). Both devices are now signed in to the same hosted workspace, each with its own token that you can revoke separately.

For the full device pairing model, see [pairing a second device](/docs/get-started/pairing).

## 9. Retire the local workspace (when ready)

Don't shut down the local workspace yet. Give yourself a few days to confirm the hosted workspace does what you need.

When you're ready to retire it:

```bash
# Stop the local instance
spl stop

# Move the local data dir to an archive location (don't delete, see warning)
mv ~/.syncro ~/.syncro.archived-$(date +%Y%m%d)
```

<Callout type="warn">
**Don't `rm -rf ~/.syncro`** unless you're certain the hosted workspace has all your records. The archived folder is your local workspace itself, with its identity and keys. The bundle holds its records and not its identity.
</Callout>

To go back, move the archived folder into place again and start it. That is your original workspace, identity included. Records written on the hosted workspace since then can be copied down the same way: export there, import locally.

## What just happened

1. **Your records came across unchanged.** Every record and thread was exported as a signed archive and imported with the same record IDs and thread IDs.
2. **The hosted workspace is its own workspace.** It signs with the identity it was created with, and your local workspace keeps its own. You paired again from the hosted side.
3. **The copy works in both directions.** Hosted to local works the same way as local to hosted.
4. **You can always leave.** `spl export` works on any workspace, hosted or self-hosted, and the bundle imports into a workspace you run yourself.

Hosted Syncropel differs from most services because your data and the system that reads it are both portable. You pay for someone else to run the same `spl` you run on your laptop, with the same APIs, the same records and the same way out.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `spl import` reports `import refused: local store has N records; pass --force-overwrite to import anyway` | Expected without `--force-overwrite`. A workspace that has been started always holds records of its own. | Check that `spl status` is answering from the hosted workspace, then run the import with `--force-overwrite`. It adds your records and replaces nothing. |
| `bundle malformed: signature verification failed` | The bundle was changed, damaged in transit, or made by an incompatible version. | Re-export from the source. If the issue persists, check `spl version` on both sides: very different versions may not be compatible. |
| A pairing copied from the local workspace doesn't sync | Expected. The other workspace knows your local workspace, and the hosted one is a different workspace. | Pair again from the hosted side: `spl federation pair add <address>` (step 7). |
| `spl status` after token save returns `401` | The device token has expired or was revoked. | Open your workspace in the Studio and create a fresh device token from Settings → Connections, then `spl token save` it. |
| The hosted workspace's identity differs from the local one's | Expected. An import copies records and never installs an identity, whatever the bundle carries. | Nothing to fix. Pair again from the hosted side (step 7). |
