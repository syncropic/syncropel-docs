## What you'll build

You've been running `spl serve` on your laptop, building up records, threads, federation pairs and trust. You want to move to a hosted workspace with the same identity and records, reachable from anywhere, with no `--insecure-localhost` flags. This tutorial walks through the move: export locally, create a hosted workspace, import, point your CLI at it and verify.

Hosted and self-hosted workspaces are the same thing: either can become the other, and neither is a lesser copy. You move with `spl export` and `spl import`, and records keep their identity through the move (see [Federation](/docs/concepts/federation)).

Allow about 30 minutes, most of it creating the workspace and verifying.

## Before you start

- `spl` installed (`spl --version`)
- A local workspace with some real content: a few threads and records, ideally one federation pair. If you're starting fresh, do [Working with threads](./first-thread) first so you have something to move.
- A browser to sign up at `syncropel.com`.
- No budget: hosted workspaces are free, up to three per account (see the [hosted plan](/docs/get-started/hosted)).

You can do this in one session, or rehearse it first. `spl import` is safe to run again.

## 1. Inspect what you're migrating

Before the export, see what is on your local workspace:

```bash
spl status
spl thread list
spl federation list
spl actor list
```

Note the local DID. After the move, the hosted workspace will have the **same DID**. That is how your identity carries over.

Also note the rough record count (`spl status` reports it). After import on the hosted side, this count should match.

## 2. Export the local workspace

```bash
spl export --out ~/migration.tar.zst
```

Output:

```
✓ Bundle written to ~/migration.tar.zst
  records:       247
  threads:       18
  federation pairs: 1
  consent grants:   3
  identity:      included (did:sync:instance:local-...)
  signed:        yes
```

The bundle is a `tar.zst` archive containing:
- Every record
- Your identity (DID document and private key). Without it, the imported workspace can't sign new records as the same DID.
- Federation pairs, consent grants and settings: everything that is "you"
- A signed manifest tying the bundle to your DID

Inspect what's in there without unpacking:

```bash
tar --zstd -tf ~/migration.tar.zst | head
```

You'll see `manifest.json`, `manifest.sig`, `identity/`, `records/<thread>/` and so on.

Because the bundle carries your private key, treat it as a secret: whoever holds it can act as your workspace. By default `spl export` does **not** include bearer tokens, so a stolen bundle can't be used to sign in to your workspace. If you need tokens to keep working, pass `--carry-tokens`, but consider creating fresh tokens on the new workspace instead.

For more on what a bundle contains, see [Portability](/docs/guides/portability).

## 3. Provision a hosted workspace

Open a browser and go to `https://syncropel.com/signup`. Pick a label, which becomes your subdomain (for example `myteam.syncropel.app`; hosted workspaces live at `*.syncropel.app`), and confirm the plan.

What happens:
1. Your label is reserved.
2. A hosted workspace is created, running the same `spl serve` you have locally, with its own storage.
3. You land in your workspace, already connected. Your syncropel.com account owns it.

The ready screen shows:
- Your hosted URL (`<label>.syncropel.app`)
- A CLI access option that creates a device token (copy it if you work from a terminal)
- The commands to "Connect the CLI"

For setup failures (label already taken, workspace limit, timeout), see [Hosted onboarding: if setup doesn't finish](/docs/get-started/hosted#if-setup-doesnt-finish).

## 4. Connect your CLI to the hosted workspace

The ready screen gives you the commands. Here they are with placeholders:

```bash
export SPL_SERVE_URL=https://myteam.syncropel.app
spl token save <your-device-token>
spl status
```

`spl status` should report the hosted workspace's DID and a green health check. Your CLI now talks to the hosted workspace for the rest of this shell session. To make it permanent across shells:

```bash
echo 'export SPL_SERVE_URL=https://myteam.syncropel.app' >> ~/.bashrc   # or ~/.zshrc
```

Or save the URL in your shell profile (`spl config path` shows where your settings are).

## 5. Import the bundle into the hosted workspace

The hosted workspace is new (no records), so `spl import` accepts the bundle without `--force-overwrite`:

```bash
spl import ~/migration.tar.zst
```

Output:

```
✓ Bundle verified
  signature:     valid
  source DID:    did:sync:instance:local-...

→ Importing...
  records inserted:    247
  records deduplicated: 0
  threads:             18
  federation pairs:    1
  identity:            adopted (private key matches incoming bundle)

✓ Import complete
```

The `identity adopted` line is the important one. Your hosted workspace now signs records with the **same DID** your local one used. Federation pairs you had locally now treat this hosted workspace as you. The address is updated on first contact, so you don't need to pair again.

## 6. Verify the round-trip

```bash
spl status
spl thread list | head -10
spl federation list
spl actor list
```

These should match what you saw in step 1 on the local workspace:
- Same `instance_did`
- Same thread count
- Same federation pair (now with `last_sync: never` on the hosted side until the next sync)
- Same actors

To check that nothing changed, compare the records:

```bash
spl thread records <some_thread_id> | sha256sum
```

Run this against both your local workspace (`SPL_SERVE_URL=http://localhost:9100 spl thread records ...`) and your hosted one (`SPL_SERVE_URL=https://myteam.syncropel.app spl thread records ...`). The record IDs should match. Each ID comes from the record's content, so a difference means something changed in transit.

Moving a workspace does not change your records.

## 7. Pair a second device (optional)

While your hosted workspace is fresh, this is a good moment to add a second device, such as your phone, a second laptop or an office machine. From the **hosted** side:

```bash
spl pair --device "iPhone" --url https://myteam.syncropel.app --scopes records:write
```

This creates a one-time code and prints a link and QR code. Open the link on the second device's Syncropel app (or paste the code into the app's "pair device" prompt). Both devices are now signed in to the same hosted workspace, each with its own token that you can revoke separately.

For the full device pairing model, see [pairing a second device](/docs/get-started/pairing).

## 8. Retire the local workspace (when ready)

Don't shut down the local workspace yet. Give yourself a few days to confirm the hosted workspace does what you need.

When you're ready to retire it:

```bash
# Stop the local instance
spl stop

# Move the local data dir to an archive location (don't delete — see warning)
mv ~/.syncro ~/.syncro.archived-$(date +%Y%m%d)
```

<Callout type="warn">
**Don't `rm -rf ~/.syncro`** unless you're certain the hosted workspace has all your records and you've verified at least one independent copy of the bundle (`~/migration.tar.zst`) exists. The bundle alone is enough to rebuild your workspace, but only if it is somewhere safe.
</Callout>

To go back to a local workspace, run `spl serve` for a fresh one and `spl import ~/migration.tar.zst` to fill it. The move works in both directions.

## What just happened

1. **The bundle is everything.** Every record, thread and federation pair is exported as a signed archive and imported into a new workspace with the same record IDs, thread IDs and pair IDs.
2. **Your identity moves with you.** The hosted workspace signs records as your DID, not a new one. Paired workspaces still see you.
3. **The move is reversible.** Hosted to local works the same way as local to hosted.
4. **You can always leave.** `spl export` works on any workspace, hosted or self-hosted, and the bundle imports into a workspace you run yourself.

Hosted Syncropel differs from most services because your data and the system that reads it are both portable. You pay for someone else to run the same `spl` you run on your laptop, with the same APIs, the same records and the same way out.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `spl import` reports `import refused: local store has N records; pass --force-overwrite to import anyway` | The hosted workspace already has records (someone or something started using it before the import). | Check `spl thread list` on the hosted side. If those records are throwaway (for example a first-run banner acknowledgement), it's safe to pass `--force-overwrite`. If they're unexpected, find out where they came from before overwriting. |
| `bundle malformed: signature verification failed` | The bundle was changed, damaged in transit, or made by an incompatible version. | Re-export from the source. If the issue persists, check `spl version` on both sides: very different versions may not be compatible. |
| Federation pair shows stale URL after import | Expected: the pair was set up with the local address. | The address updates on the first sync. If the peer can't be reached at the old address and its DID can't be found, run `spl federation refresh <peer-did>` manually. |
| `spl status` after token save returns `401` | The device token has expired or was revoked. | Open your workspace in the Studio and create a fresh device token from Settings → Connections, then `spl token save` it. |
| Hosted DID doesn't match local DID after import | The bundle was exported with `--no-identity`, so the hosted workspace created its own new DID. | Re-export with identity included (the default): `spl export --out ~/migration.tar.zst`. Use `--no-identity` only when you want the new workspace to get a new DID. |
