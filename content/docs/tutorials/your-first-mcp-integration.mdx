## What you'll build

In about 30 minutes, you'll connect an AI client — Claude Code is the canonical example, but any [MCP](https://modelcontextprotocol.io/) client works the same way — to your local Syncropel workspace. You'll use a tool from the client, watch a record appear in your workspace, and inspect it with `spl thread list`.

Every action an AI client takes is recorded on a thread, signed by the actor that did it. You get a complete audit trail with no separate logging.

## Before you start

- `spl` installed (`spl --version`; install with `curl get.syncropic.com/spl | sh`)
- A workspace running locally with `spl serve`. Hosted workspaces also work but the bearer token must reach the MCP client (covered below).
- An MCP-compatible AI client. This tutorial walks Claude Code in detail; the same pattern applies to Cursor, Cline, Zed, Kiro, OpenCode, Gemini CLI, Claude Desktop, Codex, etc.
- The `claude` binary on your PATH if you're using Claude Code (`claude --version`).

For all nine clients and the config paths on each system, see [AI Clients — three integration patterns](/docs/integrate/ai-clients).

## 1. Confirm MCP works

`spl` includes an MCP server, so you don't install anything extra.

```bash
spl mcp serve --help
```

You should see help output for the MCP server. It talks to the client over stdio, so the AI client starts it itself and you don't run it by hand.

You can sanity-check the server by piping a list-tools call yourself:

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | spl mcp serve | head -c 500
```

You should see a JSON response listing tools — `intend`, `do`, `know`, `learn`, `thread_list`, `thread_show`, etc. If the call hangs, the workspace isn't running — start it with `spl serve` and retry.

## 2. Configure Claude Code

Claude Code owns its own MCP registry via its `mcp` subcommand. The simplest path is the bundled setup helper:

```bash
spl mcp setup-claude-code
```

Output:

```
✓ Registered syncropel MCP server with Claude Code
  command: spl
  args:    [mcp, serve]
  scope:   user
```

This runs `claude mcp add syncropel -- spl mcp serve` for you. You can verify Claude Code now knows about it:

```bash
claude mcp list
```

You should see `syncropel` in the list with status `running` (or it'll spin up on first use).

For other clients — Cursor, Cline, Zed, etc. — the corresponding setup verbs are `spl mcp setup-cursor`, `spl mcp setup-cline`, `spl mcp setup-zed`, and so on. Each one writes to that client's own config location and is safe to run again.

## 3. Open Claude Code and discover the tools

Start a Claude Code session in a workspace directory (any directory works for this test):

```bash
cd /tmp && claude
```

Inside Claude Code, type `/mcp` to see registered servers and their tools. You should see `syncropel` in the list with the available tools (`intend`, `do`, `know`, `learn`, plus thread + record helpers).

If `/mcp` shows `syncropel` but with `disabled` or `error`, jump to the Troubleshooting section — the most common cause is the workspace not running on the expected port.

## 4. Invoke a tool from Claude Code

Ask Claude Code to record an intent, then to read the thread back. A natural prompt:

```
Use the syncropel MCP server to record this intent: "Try out the MCP integration".
Then list my recent threads and show me the one that was just created.
```

Claude Code will (in order):
1. Call `mcp__syncropel__intend` with the body.
2. Call `mcp__syncropel__thread_list`.
3. Call `mcp__syncropel__thread_show` on the new thread id.

After the model finishes, you'll see in Claude Code's UI which tools fired and what they returned. Each call **ran against your local workspace**, was signed by an actor DID, and is now part of your record log.

## 5. Verify the records arrived

In a separate terminal:

```bash
spl thread list
```

You should see the new thread at the top of the list with a single INTEND record. Inspect it:

```bash
spl thread records <thread_id>
```

```
ACTOR                              ACT       BODY (excerpt)
did:sync:agent:claude-code         INTEND    Try out the MCP integration
```

The actor DID is the one Claude Code authenticated as — by default `did:sync:agent:claude-code`, but this is configurable via `claude mcp add ... --env SYNCROPEL_ACTOR=did:sync:agent:my-team-claude` if you run several clients under different identities.

## 6. Watch records appear in Studio in real time

Open Syncropel Studio at [`syncropel.com`](https://syncropel.com) (connected to your local workspace) — or pair it explicitly with `syncropel.com/connect?url=http://127.0.0.1:9100` — or for a hosted workspace, `syncropel.com/connect?url=https://<label>.syncropel.app`. The thread appears at the top of the thread list within about a second of the MCP call. You can see the whole path: the tool call, the record and the screen.

You can also subscribe from the CLI:

```bash
spl watch <thread_id>
```

Now go back to Claude Code and prompt:

```
Record an observation that the integration is working: KNOW "MCP integration verified, records flowing".
```

The new record streams into your terminal in real time as Claude Code executes the tool call.

## 7. Inspect the actor's trust and audit trail

Every MCP tool call is a record signed by the actor. Over time, reviews of that work build trust. List the actor:

```bash
spl actor show did:sync:agent:claude-code
```

You'll see the actor's record history, the threads it takes part in, and trust scores per area of work as reviewers approve or reject its work.

For an audit-grade view of every MCP call:

```bash
spl thread records th_audit_records --json | jq '.[] | select(.body.actor | startswith("did:sync:agent:claude"))'
```

The audit thread `th_audit_records` has a record for each write. There is no separate MCP call log.

## What just happened

You used Syncropel's **MCP integration** end to end:

1. **Any MCP client can connect.** `spl mcp serve` offers Syncropel's verbs (intend, do, know, learn and thread queries) as MCP tools, with no middleware.
2. **Tool calls are records.** Every MCP call is a record on a thread, signed by the agent's DID. Anything that didn't produce a record didn't happen (see [Governance](/docs/concepts/governance)).
3. **One identity everywhere.** The same actor DID is used through MCP, the SDKs, the `spl` CLI and the HTTP API.
4. **Audit comes built in.** `th_audit_records` is ordinary records, kept alongside the rest of your data.
5. **Tools are discovered automatically.** The MCP tool list is generated from Syncropel's own commands, so a new command appears as a new tool.

An AI client doesn't need to know what Syncropel is. It just sees a few well-shaped tools and uses them, and Syncropel keeps the trail.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `/mcp` in Claude Code shows `syncropel` with `error` or `disabled` | The workspace isn't running, or `spl` isn't on the PATH that Claude Code uses (common on macOS). | Confirm `spl status` works in a fresh shell. If it does but Claude Code still can't find it, pass an absolute path: `claude mcp remove syncropel && claude mcp add syncropel -- /usr/local/bin/spl mcp serve`. |
| Tools list is empty | The workspace is on a non-default port and the MCP server is using the wrong URL. | Pass an explicit URL via env: `claude mcp add syncropel --env SPL_SERVE_URL=http://127.0.0.1:9200 -- spl mcp serve`. |
| MCP calls return `401 unauthorized` | Sign-in is required (the default) and no bearer token is set for the MCP server. | Mint a service-account token: `spl service-account create --name "claude-code" --scopes records:write --with-token`, save the token: `spl token save <token>`, then re-launch Claude Code so the subprocess re-reads `~/.syncro/token`. |
| MCP calls succeed but records don't appear in Studio | The browser is connected to a different workspace URL than the one MCP wrote to. | Open `/settings/connections` (or the workspace switcher in the header) and check the active URL matches the workspace Claude Code wrote to. Switch if not. |
| CORS errors in browser console after MCP calls landed records | The web app's address isn't in your workspace's list of allowed origins. | Add it: `spl config auth-set-cors-origins http://localhost:3000` (or whichever address the app runs on). |
