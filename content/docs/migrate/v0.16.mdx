title: Migrating to v0.16 (Default-Secure)
description: Upgrade guide for operators moving from v0.15 to v0.16. Bearer-token authentication is now enforced by default. Three operator archetypes, recovery paths, and rollback.
---

## TL;DR

- **The kernel now rejects unauthenticated requests by default.** `auth.required` flipped from `false` (v0.15) to `true` (v0.16).
- **The CLI now reads bearer tokens automatically** — precedence: `--token` flag, `SPL_TOKEN` env, then `~/.syncro/token` file.
- **New subcommands**: `spl token save`, `spl token unset`, `spl token show-source`.
- **A one-command escape hatch**: `spl serve --insecure-localhost` forces 127.0.0.1 bind and disables auth. For local dev only.
- **Downgrading to v0.15.0 is always safe** — same database schema, same record formats.

Three operator archetypes below. Find the one that matches you.

## Archetype A — Single-user laptop, localhost-only daemon

**Who**: you run `spl serve --daemon` on one machine that nobody else reaches. The daemon binds `127.0.0.1:9100`. Your `spl task list` / `spl intend` workflow has always Just Worked.

**What breaks on upgrade**: the daemon won't start cleanly on v0.16 because the preflight check refuses to run with `auth.required=true` and no service account authorizing your configured user DID. You'll see:

```text
error: auth.required is enabled but no service account authorizes did:sync:user:<you>.
```

The daemon exits before binding. This is intentional — it's preventing you from accidentally locking yourself out. To get running on v0.16 you first create a service account that authorizes your user DID, then restart normally.

### Recovery — the three-phase path

**Phase 1 — find your daemon's configured user DID.** `spl init` picked this when you first ran it; it's stored at `~/.syncro/config.toml`:

```bash
awk -F'"' '/^actor/{print $2}' ~/.syncro/config.toml
# → did:sync:user:<your-name>
```

Keep this exact string. You'll use it as `--actors` in the next step. This is important — if you use `whoami` or `$USER` and the daemon chose something different at init time, the SA you create won't authorize the right DID and startup will keep failing.

**Phase 2 — start the daemon in insecure-localhost mode so you can bootstrap.**

```bash
# Run in the foreground (or via nohup & if you want the shell back).
# --insecure-localhost force-binds 127.0.0.1 and skips auth enforcement
# so the bootstrap endpoint can be reached.
nohup spl serve --insecure-localhost > /tmp/spl-bootstrap.log 2>&1 &
sleep 3
```

**Phase 3 — create the SA, save the token, restart normally.**

```bash
# Replace <DAEMON_ACTOR> with the DID you found in Phase 1.
spl service-account create --bootstrap \
    --name local --scopes admin --with-token \
    --actors <DAEMON_ACTOR>

# Copy the printed token (shown once only) and save it.
spl token save spl_prod_sa_<crockford>_<secret>

# Shut down the insecure daemon.
pkill -f "spl serve.*insecure-localhost"

# Restart cleanly with auth enforced.
spl serve --daemon

# Verify.
spl token show-source   # should print "in use: ~/.syncro/token file"
spl task list            # should succeed
```

<Callout type="warn">
**Known v0.16.0 gotcha**: `spl serve --daemon --insecure-localhost` in combination does not skip the preflight — the daemon mode spawns a background process that runs the check anyway. The workaround shown above (foreground `nohup spl serve --insecure-localhost &`) is the supported path until v0.16.1 patches the combined-flag behavior.
</Callout>

### Alternate — stay on v0.15 behavior (not recommended)

If you prefer v0.15's "trust localhost, no auth" model, emit one LEARN record on `th_engine_config`:

```bash
# Opt-out: restore auth.required=false for this install.
# The daemon reads this on every startup via the config reload path.
curl -s -X POST http://127.0.0.1:9100/v1/records \
    -H 'content-type: application/json' \
    -d '{
      "actor":"did:sync:user:your-username",
      "act":"LEARN",
      "body":{"topic":"auth_required","enabled":false},
      "clock":0,
      "thread":"th_engine_config"
    }'
```

You can only emit this record while auth is off. If you already restarted with auth on, start the daemon in foreground with `nohup spl serve --insecure-localhost > /tmp/spl.log 2>&1 &` once, emit the LEARN record, kill the daemon, and restart normally. See the [Phase 2 bootstrap flow](#recovery--the-three-phase-path) above for the exact commands.

### Alternate — ephemeral dev daemons

If you spin up `spl serve --memory` daemons for testing, add `--insecure-localhost`:

```bash
spl serve --memory --insecure-localhost --port 9200
```

The flag forces 127.0.0.1 bind regardless of `--host`, so you can't accidentally expose an unauthenticated daemon to the LAN by passing `--host 0.0.0.0`.

## Archetype B — Shared server with auth already enabled

**Who**: you followed the [Authentication & Service Accounts guide](/docs/operate/keyring) and turned on `auth.required=true` via a config LEARN record. Your operators already have tokens.

**What breaks on upgrade**: nothing. Your config record is still in the store, the reload path replays it on startup, and `auth.required=true` stays on either way. The only difference now is that a fresh install with no config record will also default to `true` — which is what the default-flip delivers.

**Action required**: none.

**Recommended**: verify your operators' tokens still work after the upgrade via a quick health probe:

```bash
spl thread list -o json | head
```

## Archetype C — Multi-user server without auth

**Who**: you run `spl serve` on a host several operators reach (LAN, VPN), but you never turned on `auth.required`. Everyone has been emitting records under their own `X-Syncropel-Actor` header.

**What breaks on upgrade**: every operator's first command returns 401 (same error as Archetype A).

### C.1 Turn on auth — recommended

Now is the time. See the full [Authentication & Service Accounts guide](/docs/operate/keyring) for the playbook. Short version:

```bash
# 1. Bootstrap the first SA on the server.
spl service-account create --bootstrap --name bootstrap-admin \
    --with-token \
    --scopes admin \
    --actors did:sync:user:admin

# 2. For each operator, create a service account + token.
spl service-account create --name alice \
    --scopes records:read,records:write,threads:write \
    --actors did:sync:user:alice

spl token create --sa <alice_sa_id>
# → prints the token — hand to Alice over a secure channel

# 3. Each operator saves their token locally.
alice$ spl token save spl_prod_sa_<alice_id>_<secret>

# 4. No config change needed — auth.required=true is the v0.16 default.
```

### C.2 Explicit opt-out — stay unauthenticated (strongly discouraged)

Same as Archetype A's opt-out. Emit a LEARN record with `{"topic":"auth_required","enabled":false}` and the daemon preserves v0.15 behavior.

**Why this is strongly discouraged for shared hosts**: records carry `actor` fields that downstream projections trust (trust scores, judged-by chains, thread merges). An unauthenticated caller can impersonate any actor, corrupting the lineage the protocol depends on. If multiple operators reach the host, enabling auth is the correct path.

## Rollback

v0.15.0 runs safely against a v0.16-touched database:

- Same record schema — no v0.16 migrations ran.
- Same store backend — no file-format changes.
- Same config LEARN records.
- The only new artifact `spl` writes at `~/.syncro/` is a plaintext `token` file. v0.15 ignores it.

Rollback:

```bash
# 1. Stop the v0.16 daemon.
spl serve --stop

# 2. Install the v0.15.0 binary.
curl -fsSL https://get.syncropic.com/spl | sh -s -- --version 0.15.0

# 3. Restart.
spl serve --daemon
```

The only v0.16-only behavior your v0.15 daemon will NOT replicate is the `auth.required=true` default. If you had manually turned auth on via a config LEARN record, that record is still in the store and still applies — no action needed. If you relied on the v0.16 default, you're back on v0.15's "auth off" default.

## Common pitfalls

**`spl token save <token>` warns "token does not match the expected shape".** You pasted something that isn't `spl_<env>_<sa_id>_<secret>`. The file saves anyway (the client is permissive), but the daemon will 401 on the next request. Re-run `spl service-account create --bootstrap --with-token` or `spl token create --sa <sa_id>` and save the exact string it prints.

**`spl token save` fails with "insecure permissions".** The file already exists with group-readable or world-readable bits. Fix with `chmod 600 ~/.syncro/token`, then re-run save.

**401 persists after `spl token save`.** Run `spl token show-source`. If it reports `SPL_TOKEN env` as the active source but you expected the file, unset the env var (`unset SPL_TOKEN`) and retry. Env beats file per the precedence rule.

**The daemon rejects a newly-minted token with "token not recognized".** The SA or token may have been revoked. `spl service-account describe <sa_id>` shows the SA's current `revoked` state; `spl token list --sa <sa_id>` shows active tokens. If the SA is revoked, mint a new one and update saved state.
