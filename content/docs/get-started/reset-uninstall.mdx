title: Reset and uninstall
description: Start over with a fresh `~/.syncro/` folder, or remove `spl` from your computer. Includes what is kept in each case.
---

There are two different things you can do.

- **Reset** wipes `~/.syncro/` (identity, keys, records, token, config) but leaves the `spl` binary installed and `~/.syncro-data/` (your task content) untouched. Use this when you want to start fresh without reinstalling.
- **Uninstall** removes the `spl` binary itself. Use this when you're done with Syncropel on this machine.

Automatic backups under `~/.local/share/syncropel/backups/instance-<did-tail>/` (a folder named after this workspace's identity) are kept outside `~/.syncro/`, so they survive a **reset but not a full cleanup of your disk**. Each start of the workspace overwrites the backup. If you care about your records, copy them to another computer before doing either of the things on this page.

## Clean reset with `spl reset`

`spl reset` wipes `~/.syncro/` back to a fresh state. It refuses to run while the workspace is running, shows what it will remove, asks you to confirm, and saves a dated backup of `hub.db` before deleting anything.

```bash
spl stop                                # stop the workspace first
systemctl --user stop spl-serve.service         # if you use a systemd unit (reset will refuse otherwise)
spl reset                                       # shows what it will remove, asks y/N, backs up hub.db, then wipes
spl init                                        # create a new identity and settings (no --force needed)
spl serve                              # start fresh
```

`spl reset` deletes **everything inside `~/.syncro/`**, then `~/.syncro/` itself, except anything you keep with a `--keep-*` flag. That includes files that build up over time, such as `vfs.db*`, `agent/`, `content/`, `serve.log` and old backup files.

What `spl reset` **never** deletes:

| Path | Why |
|---|---|
| `~/.syncro-data/` | Your task content files (Markdown) and task nicknames. This is content you wrote, so it is kept apart from `.syncro/` |
| `~/.local/share/syncropel/backups/` | Automatic `hub.db` backups, plus the `hub.db.pre-reset.<iso8601>` copy this command makes |
| OS keyring entries | If your identity is stored in the system keyring (Linux secret service, macOS Keychain, Windows), it is not touched. `spl init` replaces it the next time it runs |

`~/.syncro/` itself is also removed when **no** `--keep-*` flag is passed, so the next `spl init` works without `--force`. With any `--keep-*` flag, the folder stays, holding only what you kept, and the next `spl init` needs `--force`.

### How reset knows the workspace is running

`spl reset` refuses to run if any of these is true:

1. The file `~/.syncro/run/spl.pid` points at a running process.
2. The local socket `~/.syncro/run/spl.sock` accepts a connection.
3. (Default `~/.syncro/` folder only) `127.0.0.1:9100` accepts a connection.
4. (Linux, default folder only) `systemctl --user is-active spl-serve.service` says `active`.

Checks 3 and 4 only apply to the default `~/.syncro/` folder, so a workspace in another folder (set with `SYNCROPEL_HOME=/some/other/path`) isn't blocked by an unrelated one. If you use a systemd service to keep `spl serve` running, stop the service first. Ending the process with `kill` isn't enough, because the service would restart it as soon as its data is deleted.

### Common flags

```bash
spl reset --dry-run         # show what it would remove and exit. Nothing is changed.
spl reset --json            # machine-readable output for scripts
spl reset --force           # skip the y/N confirmation
spl reset --keep-keys       # keep your identity (the same after `spl init`)
spl reset --keep-config     # keep config.toml (API keys and routing rules survive)
spl reset --keep-secrets    # keep the secrets/ folder
spl reset --wipe-task-data  # also delete ~/.syncro-data/ (asks for extra confirmation)
```

`--dry-run` lets you see what would be deleted before you commit to it:

```bash
spl reset --dry-run --json | jq '.plan[] | select(.action == "delete")'
```

### Windows

```powershell
spl stop
spl reset
spl init
spl serve
```

### Fallback: when `spl reset` itself can't run

If `spl` itself is broken (a failed upgrade, a workspace that won't stop, or a leftover file confusing it), do it by hand:

```bash
# Linux / macOS
spl stop || pkill -f "spl serve"
rm -rf ~/.syncro
spl init
```

```powershell
# Windows
spl stop
Remove-Item -Recurse -Force $env:USERPROFILE\.syncro
spl init
```

Deleting by hand does NOT back up `hub.db` first, so copy anything you want to keep to another computer before you run this. The backup made when the workspace started, at `~/.local/share/syncropel/backups/instance-<did-tail>/hub.db.bak`, is your last resort afterwards.

Either way, you're back at the beginning. `spl init` prints the next steps: open your workspace at `http://127.0.0.1:9100/` or connect the Studio at `https://syncropel.com/connect?url=http://127.0.0.1:9100`.

### First boot after reset

After a reset, run:

```bash
spl init       # create your identity and settings
spl serve      # start the workspace
# Verify
spl status   # workspace is healthy
spl doctor   # all green
```

`spl task add "..."`, `spl thread list`, `spl status` and every other command work straight away, with no service account or token. The command line connects through a local socket at `~/.syncro/run/spl.sock` that only your user can use.

You only need a service account to give limited access to something else: a browser, a phone, an AI client, another computer, or another workspace you sync with. See [Service accounts and tokens](/docs/get-started/service-accounts).

On older versions that don't use the local socket, you need the older steps (`--insecure-localhost`, `service-account create --bootstrap`, `token save`, then restart). Upgrading (`curl get.syncropic.com/spl | sh`) avoids them.

## Full uninstall

### Linux

```bash
spl stop                                   # stop the workspace
rm ~/.local/bin/spl                                # remove the program
rm -rf ~/.syncro                                   # remove your data
rm -rf ~/.local/share/syncropel                    # remove backups
```

If you added `~/.local/bin` to `PATH` specifically for `spl`, clean that line out of your shell rc:

```bash
grep -n "/.local/bin" ~/.bashrc ~/.zshrc ~/.config/fish/config.fish 2>/dev/null
```

Edit by hand to remove.

### Windows

```powershell
spl stop
Remove-Item "$env:LOCALAPPDATA\Programs\spl" -Recurse -Force
Remove-Item $env:USERPROFILE\.syncro -Recurse -Force
Remove-Item "$env:LOCALAPPDATA\syncropel" -Recurse -Force -ErrorAction SilentlyContinue
```

Clean the user `PATH`:

```powershell
$current = [Environment]::GetEnvironmentVariable('Path','User')
$updated = ($current -split ';' | Where-Object { $_ -notmatch 'spl' }) -join ';'
[Environment]::SetEnvironmentVariable('Path', $updated, 'User')
```

Close and reopen PowerShell for the `PATH` change to apply.

### macOS

```bash
spl stop
rm ~/.local/bin/spl
rm -rf ~/.syncro
rm -rf ~/.local/share/syncropel
```

### If you installed the Windows Service wrapper

Uninstall the service **before** removing the binary. Windows needs `spl.exe` to still be there to remove the service.

```powershell
# From elevated PowerShell
spl serve --uninstall-service
# then proceed with the uninstall steps above
```

See the [Operator runbook](/docs/operate/runbook) for Windows-specific service notes.

### If you installed a systemd user unit (Linux)

```bash
systemctl --user stop spl-serve.service
systemctl --user disable spl-serve.service
rm ~/.config/systemd/user/spl-serve.service
systemctl --user daemon-reload
```

## What survives

### What a reset leaves alone

- The `spl` binary itself.
- Any entries you added to your shell's `PATH`.
- `~/.syncro-data/` (task content + alias mappings): your own content is kept apart from `.syncro/` for this reason. `spl reset` never touches it unless you pass `--wipe-task-data` and confirm the extra prompt. Manual `rm -rf ~/.syncro` doesn't touch it either.
- Backups at `~/.local/share/syncropel/backups/`. The pre-reset snapshot `hub.db.pre-reset.<iso8601>` that `spl reset` writes lands here too, so a reset can be undone. Only the full uninstall steps remove this folder.
- OS keyring entries (if you use a keyring backend). `spl init` replaces the entry the next time it runs.

### What an uninstall leaves alone

- System-level `PATH` entries set by another tool.
- Any data you've copied out of `~/.syncro/` to elsewhere on disk.

### What neither removes

- Records that were already synced to another workspace. Those stay on that workspace.
- Git repos, source checkouts, or other project state that happens to be adjacent on disk.

## Restoring from backup after a reset

If you reset by mistake, the most recent backup, made when the workspace last started, is at:

```
~/.local/share/syncropel/backups/instance-<did-tail>/hub.db.bak
```

The folder name ends with 24 characters taken from the workspace's identity. After a reset you can't look that up, so list what is there:

```bash
ls ~/.local/share/syncropel/backups/*/
```

Restore:

```bash
spl stop
cp ~/.local/share/syncropel/backups/instance-<tail>/hub.db.bak ~/.syncro/hub.db
spl serve
```

The identity in `config.toml` is separate from the records file, so a restored `hub.db` works with your current identity as long as you haven't set up a new one in between. If you have, the records will still restore but they stay signed with the old key. See [Operator runbook → Recovery](/docs/operate/runbook) for the full steps.
