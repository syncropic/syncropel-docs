Use this page when something that should work isn't working. Each section names a symptom, says what is going on, and gives the command to fix it.

For a full check of your setup, run [`spl doctor`](/docs/operate/doctor) first: it runs a series of checks and tells you which one fails.

## "Failed to start spl serve" after install

```
$ spl serve
Error: failed to start spl serve
```

Read the full error:

```bash
spl serve --logs
# or directly
tail -n 50 ~/.syncro/logs/spl.log
```

The most common causes and their fixes:

### `unable to open database file`

The workspace could not open `hub.db`. Either the path is wrong, the folder isn't writable, or you are in a folder that doesn't support file locking well (such as a network path or WSL folder on Windows).

Try giving the path explicitly:

```bash
spl serve --store ~/.syncro/hub.db
```

If that works, the path was the problem. On Linux and macOS the workspace always uses `~/.syncro/hub.db`; `--store` just says so explicitly. On Windows, run from a native PowerShell (not a WSL shell).

### `auth.required is enabled but no service accounts exist`

On Linux and macOS this is not an error: the command line connects through a local socket that only your user can use, so a workspace with no service accounts is normal. If you see this message anyway:

- **On Windows**: the local socket isn't used on Windows. Create a token with [`spl pair --device local-windows --url http://127.0.0.1:9100 --scopes admin`](/docs/get-started/pairing) and save the printed token.
- **You turned off the local socket** (`[auth] unix_socket = false` in `config.toml`). Every command then needs a token; see [Service accounts](/docs/get-started/service-accounts).
- **You're on an older version**: upgrade with `curl -sSf https://get.syncropic.com/spl | sh`.

The older way (`--insecure-localhost`, then `spl service-account create --bootstrap`, then `spl token save`) still works, but you don't need it on a first run.

### `address already in use`

Something else is already using port 9100: a leftover copy of `spl`, another `spl serve`, or a different program.

```bash
# Linux / macOS
ss -tlnp | grep 9100          # find the process
lsof -iTCP:9100 -sTCP:LISTEN  # alternative

# Windows (PowerShell)
Get-NetTCPConnection -LocalPort 9100
```

If it is a leftover `spl`, see "Stale PID file" below. If it is a different program, stop it or start the workspace on another port with `--port`.

## "Database is locked"

The records file is locked. There are two common causes.

### A leftover `spl.exe` still holds the file (Windows)

```powershell
Get-Process spl
```

If a process is listed, end it:

```powershell
Stop-Process -Id <pid> -Force
```

Then start the workspace again.

### Running from a WSL folder (Windows)

Running `spl.exe` from a WSL shell starts it in a folder under `\\wsl$\<distro>\...`, where Windows cannot lock files properly. You see `database is locked` errors that go away after a reboot and return the next time you start from WSL.

Fix: run `spl` from a native Windows terminal (PowerShell or Windows Terminal), not from a WSL shell.

### Linux equivalent

Rare but possible. Check for leftover processes:

```bash
pgrep -af "spl serve"
```

If a PID is listed but `spl stop` can't find it, see "Stale PID file" below.

## Dashboard shows "connected" but no records

The browser paired and can reach `/health`, but every request for records returns 401 or 403.

Cause: the browser has no token, or its token doesn't include `records:read`.

Fix: pair again with the right scopes.

```bash
spl pair \
  --device "My browser" \
  --url "http://127.0.0.1:9100" \
  --scopes records:read,records:write
```

If it still fails, check that the dashboard is on the allowed list for web pages (CORS):

```bash
spl config show | grep -i cors
spl config auth-set-cors-origins https://syncropel.com
```

## Windows: command hangs on first install

The install script runs `spl.exe` briefly to check the version. Windows Defender and Windows Firewall both prompt on first run of a new executable. If the prompt lands behind other windows, the install appears to hang.

Check for a hidden prompt:

```powershell
wf.msc
```

Accept the firewall prompt (or add an inbound rule for `spl.exe` in `wf.msc`). The install continues once `spl.exe` is allowed.

## `where.exe spl` returns nothing after install

```powershell
where.exe spl
# (empty)
```

Your current PowerShell session predates the `PATH` registry update. The install script added `spl` to your `PATH`, but only new windows see that.

Fix: close the terminal and open a new one. `where.exe spl` should then report `%LOCALAPPDATA%\Programs\spl\spl.exe`.

If the new session still can't find it, check that the `PATH` change was saved:

```powershell
[Environment]::GetEnvironmentVariable('Path','User')
```

The output should include `%LOCALAPPDATA%\Programs\spl` (or the expanded path).

## Stale PID file

`spl stop` says the workspace isn't running, but `spl status` or `curl http://127.0.0.1:9100/health` shows that it is. The file that records the running copy has been left behind.

Recovery:

```bash
# Linux / macOS
pgrep -af "spl serve"             # find the actual PID
kill <pid>                        # ask it to stop
# if it doesn't exit within ~10 seconds:
kill -9 <pid>                     # force it to stop
rm ~/.syncro/run/spl.pid          # remove the leftover file
spl serve                         # start fresh
```

```powershell
# Windows
Get-Process spl
Stop-Process -Id <pid> -Force
Remove-Item $env:USERPROFILE\.syncro\run\spl.pid -ErrorAction SilentlyContinue
spl serve
```

`spl doctor` finds this problem and prints the command to fix it.

## Corrupted record store or stuck locks

If `hub.db` is damaged and not just locked (for example after the disk filled up or the computer crashed while writing), the last resort is to wipe `~/.syncro/` and start again:

```bash
# First, make a backup if the file is at all recoverable:
cp ~/.syncro/hub.db ~/hub.db.broken.$(date +%s)

# Then wipe:
rm -rf ~/.syncro

# Set up again:
spl init
spl serve --insecure-localhost
spl service-account create --bootstrap \
  --name admin \
  --actors did:sync:user:$(whoami) \
  --scopes admin \
  --with-token
spl token save <token>
spl stop
spl serve
```

Any records you had are gone. Automatic backups under `~/.local/share/syncropel/backups/instance-<did-tail>/` (a folder named after this workspace's identity) may contain a recent snapshot: see [Operator runbook → Recovery](/docs/operate/runbook) for how to restore.

## Data went to `System32` (Windows)

If you ran `spl serve` from an elevated `cmd.exe` whose working directory was `C:\Windows\System32\`, `hub.db` may have been created in `System32`. You would see no data in `%USERPROFILE%\.syncro\` even though the workspace reports records.

Fix: stop the workspace, move the file, and point the workspace at the right place.

```powershell
spl stop
Get-ChildItem C:\Windows\System32\hub.db -ErrorAction SilentlyContinue
# If found:
Move-Item C:\Windows\System32\hub.db $env:USERPROFILE\.syncro\hub.db
spl serve --store $env:USERPROFILE\.syncro\hub.db
```

Always start `spl serve` from a working directory you control (your home directory is safe). Never run as Administrator unless you have a specific reason: the install does not need it.

## Hosted workspace

These apply to a workspace created at syncropel.com.

- **A connection error right after a quiet period.** The workspace was asleep and is waking up. This usually takes a couple of seconds; try again.
- **A `401` after reconnecting a machine.** This computer's key is no longer accepted. Connect it again and save the new key with `spl token save <token>`; see [Connect the command line](/docs/get-started/connect-the-command-line).
- **Storage full on the free plan.** A free workspace has 1 GB of storage; a storage-full error means it has reached that limit. See [Plans and billing](/docs/get-started/pricing) for what each plan includes.

## Still stuck

Run the full diagnostic:

```bash
spl doctor --json
```

Every check reports `pass`, `warn` or `fail`, with a fix. If everything passes but something is still wrong, look at the log (`~/.syncro/logs/spl.log`) around the time of the problem. You can attach the output of `spl doctor --json` when you ask for help.
