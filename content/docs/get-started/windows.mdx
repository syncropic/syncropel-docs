Most of Syncropel works identically on Windows and Linux. A few Windows details catch new users out; this page collects them.

For boot-time autostart via the Service Control Manager, see [Windows Service](/docs/operate/windows-service).

## Don't run `spl.exe` from a WSL shell

`spl.exe` is a native Windows program. If you start it from a WSL shell, it works from a folder under `\\wsl$\<distro>\...`, and Windows cannot lock files properly there. You will see `database is locked` errors that go away after a reboot and come back later.

Always run `spl.exe` from a native Windows terminal:

- **Windows Terminal** (recommended; install from the Microsoft Store).
- **PowerShell** (PowerShell 7 or the built-in Windows PowerShell).
- **Command Prompt** (`cmd.exe`).

If you must start `spl` from a WSL session, first `cd` into a Windows path:

```bash
# Inside WSL
cd /mnt/c/Users/$USER
/mnt/c/Users/$USER/AppData/Local/Programs/spl/spl.exe version
```

This is not supported. A native Windows terminal is always better.

## Windows Defender

Windows Defender can scan your records file (`hub.db`) on every read or write, which slows down a busy workspace. It can also flag a newly downloaded `spl.exe` as "unknown" and ask you before the first run.

### Optional: Defender exclusions

You can tell Defender to skip the Syncropel folders:

```powershell
# Run from elevated PowerShell
Add-MpPreference -ExclusionPath "$env:USERPROFILE\.syncro"
Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\Programs\spl"
```

Do this only on your own computer. On shared or work computers, follow your administrator's policy.

### "Unknown publisher" prompt

If Defender prompts with an "unknown publisher" warning the first time you run `spl.exe`, click **Run anyway**. The `spl-windows-x86_64.exe` build is signed, and the warning goes away as more people run it. You can also check the file's checksum against `releases.syncropic.com/spl/<version>/SHA256SUMS.txt` before running.

## Windows Firewall

The first time `spl serve` opens a network port, Windows Firewall asks for inbound network permission. The prompt can appear behind other windows. If the install seems to hang while it checks the result, this is almost certainly why.

### Find a hidden prompt

```powershell
wf.msc
```

This opens Windows Defender Firewall with Advanced Security. A waiting request is listed under **Inbound Rules**.

### Pre-authorize the binary

You can add the firewall rule ahead of time from PowerShell run as administrator:

```powershell
New-NetFirewallRule `
  -DisplayName "spl serve" `
  -Direction Inbound `
  -Program "$env:LOCALAPPDATA\Programs\spl\spl.exe" `
  -Action Allow `
  -Profile Private,Domain
```

This allows inbound connections on Private and Domain networks (which includes most LAN and private VPN scenarios) but not Public. If you need Public network access, replace `-Profile Private,Domain` with `-Profile Any`, but only if you are sure you want that.

### Removing the rule

```powershell
Remove-NetFirewallRule -DisplayName "spl serve"
```

## PATH: no administrator needed

The Windows install script adds `spl` to your own `PATH`, not the whole machine's, and installs it here:

```
%LOCALAPPDATA%\Programs\spl\spl.exe
```

No administrator rights are needed. To check your `PATH`:

```powershell
[Environment]::GetEnvironmentVariable('Path','User')
```

The output should contain `%LOCALAPPDATA%\Programs\spl` (or the expanded form).

Changes to the user `PATH` only take effect in **new** terminal sessions. If `where.exe spl` is empty immediately after install, close and reopen PowerShell.

## Long path names

Windows truncates many paths at 260 characters by default. If `%USERPROFILE%` is unusually long (common on Azure AD joined machines, for example `C:\Users\long.user.name@directory.tenantname.onmicrosoft.com\`), `spl` may fail to find `hub.db` or to rotate its logs, with no error.

Enable long path support:

```powershell
# From elevated PowerShell. Requires a reboot to take effect.
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
  -Name LongPathsEnabled -Value 1 -Type DWord
```

After reboot, long paths in `%USERPROFILE%` are handled correctly by `spl`.

If you can't enable long paths (for example, on a work computer you don't control), install `spl` and its data in a shorter folder instead:

```powershell
$env:INSTALL_DIR = "C:\spl"
$env:SYNCROPEL_HOME = "C:\spl\home"
irm https://get.syncropic.com/spl.ps1 | iex
```

`SYNCROPEL_HOME` replaces the default `~/.syncro/` location every time you run `spl`.

## PowerShell and commas

A few flags take a comma-separated list. PowerShell splits on commas, so put the whole value in quotes:

```powershell
# Wrong: PowerShell splits on the comma
spl pair --scopes records:read,records:write

# Right
spl pair --scopes "records:read,records:write"
```

The same applies to `--actors` in `spl service-account create`.

## Where the logs live

```
%USERPROFILE%\.syncro\logs\spl.log
```

Open it in Notepad or any editor, or follow it in PowerShell:

```powershell
Get-Content -Path $env:USERPROFILE\.syncro\logs\spl.log -Tail 200 -Wait
```

`-Wait` follows the file like `tail -f` on Linux.
