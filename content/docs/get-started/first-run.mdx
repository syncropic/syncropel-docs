This page is for people running their own workspace or using the API. If you use a workspace created at syncropel.com, start with [Your hosted workspace](/docs/get-started/your-hosted-workspace).

<Callout type="info" title="First run on Linux or macOS takes three commands">
```bash
spl init --preset recommended   # create your identity and settings, install the assistant
spl serve          # start the workspace
spl task add "..." # works straight away: no service account or token needed
```

Once it is running, read [Your first hour](/docs/get-started/first-hour). A new
workspace asks you one question, and answering it opens your first thread.

On your own computer the command line talks to the workspace through a local socket at `~/.syncro/run/spl.sock`. Only your user account can use it, so no token is needed. Tokens are for giving someone or something else limited access: see [Service accounts and tokens](/docs/get-started/service-accounts) when you want to connect a browser, phone, AI client, another computer, or another workspace.

`spl start`, `spl stop` and `spl restart` are the everyday commands. `spl serve` runs the workspace in the foreground, which is what services such as systemd and Docker use.
</Callout>

After `spl version` prints a version, run `spl init` once to create your `~/.syncro/` folder.

## `spl init`

```bash
spl init --preset recommended
```

This creates `~/.syncro/` with default contents and a new identity, and
applies the `recommended` preset: the assistant is installed, and one question
("What are you working on?") is waiting for you when the workspace starts.
Pass `--preset blank` for a workspace with nothing installed and no question.
A plain `spl init` with no `--preset` does neither: the workspace starts with no
assistant and no question until you choose a preset (the Studio's first-run
card offers them). An unknown preset name is refused before anything is written.

The new folder:

```
~/.syncro/
├── config.toml              Identity, default model, server settings
├── token                    Token for the command line (created later; see Service accounts and tokens)
├── keys/                    Keys that sign your records
│   ├── primary.pub                    Public key
│   └── did_sync_user_<name>.priv     Private key (mode 0600), named after your `actor` value
├── logs/                    Workspace logs (populated on first start)
├── run/                     Running-copy file and local socket (filled in on first start)
├── secrets/                 API keys for upstream providers (empty until you add)
└── hub.db                   Your records (created at init; grows as you use it)
```

On Windows, the same tree lives under `%USERPROFILE%\.syncro\`.

## Your identity

`spl init` creates your identity and writes it into `config.toml`:

```toml
[identity]
actor = "did:sync:user:you"
did = "did:key:z6Mk..."
method = "key"
key_path = "/home/you/.syncro/keys/primary"
```

- **`actor`** is the name you'll see on every record you write. It defaults to `did:sync:user:<your-username>`, the same username your OS reports.
- **`did`** is your identity as a key. A new pair of keys is made; the public half becomes the `did:key:` text, and the private half is stored under `~/.syncro/keys/` (named after your `actor` value) so only you can read it (`0600`).
- **`method`** is the kind of identity (`key` on a new install; `web` or `sync` after an [upgrade](#identity-types)).
- **`key_path`** is where the keys your workspace signs with are kept.

Inspect the result:

```bash
spl identity show
```

You should see:

```
Identity:
  DID:         did:key:z6Mk...
  Method:      key
  Key path:    /home/you/.syncro/keys/primary
  Actor:       did:sync:user:you
```

## Inspecting `config.toml`

```bash
cat ~/.syncro/config.toml
```

The file is short. It has these sections:

- **`[identity]`**: your identity and keys, as above.
- **`[server]`**: address (`127.0.0.1`), port (`9100`), data folder and backup folder.
- **`[intelligence]`**: which language model your workspace uses, and your own provider key. On a local workspace you will need this; see the note below.
- **`[fleet]`**: for running several machines together (you can ignore it on one machine).

<Callout type="warn" title="A local workspace has no model until you give it a key">
A hosted workspace arrives with managed model access (free plans include a
one-time allowance). A workspace on your own
machine does not: the assistant is installed by the preset but has nothing to
answer with until you supply a provider key. Run
`spl config set-key anthropic <your key>`, then `spl stop` and
`spl serve --daemon`. Until then the assistant is silent, and `spl run` says
so rather than failing quietly.
</Callout>

### The assistant and the first question (self-host)

Every preset except `blank` installs the **chief of staff** (the chief), the
member that answers when you type in a thread, and seeds the one question a
fresh workspace asks: "What are you working on?" Answering it opens your first
thread, titled by your words. [Your first hour](/docs/get-started/first-hour)
walks through it.

A `blank` workspace starts deliberately empty: nothing answers and nothing is
asked until you choose what runs on it. To add the assistant later:

```bash
spl blueprint plan <blueprint.json>                        # see what it will install, and get its plan hash
spl blueprint install <blueprint.json> --accept-plan <hash> # install it, at any time
```

See [Blueprints](/docs/concepts/blueprints) for the commands.

Installing the chief later does not add the question; the question only appears when you first choose a preset. On a blank workspace, open your first thread yourself. If you chose blank and the assistant seems silent, this is why, and nothing is broken. (Hosted workspaces come with the assistant already on.)

Editing `config.toml` by hand is supported. Changes take effect on the next start. For settings you can change while it runs (routing rules, permissions, embedding providers), use `spl config …` commands instead: those take effect without a restart.

## When to re-initialize

Almost never. `spl init` is a one-time operation; running it again against an existing `~/.syncro/` is a no-op unless you pass `--force`:

```bash
spl init --force
```

`--force` overwrites `config.toml` and makes new keys. **Your existing `hub.db` is left alone**, so your records survive. But the new keys sign under the same `actor` name as before, so your old records will no longer check out against the new key. Only use `--force` on a machine you have not used for real work.

If you want a fully clean state (new identity and new data), see [Reset and uninstall](/docs/get-started/reset-uninstall).

## Identity types

### This machine's own identity (the default)

What `spl init` creates: an identity whose private key stays on this one machine. If you set up another machine the same way, it gets its own, separate identity. This is the right choice if you use one machine.

Note this is different from **signing in** on the web or to a hosted workspace: there, your content is owned by your sign-in identity, which is the same on every device. See [Your identity & recovery](/docs/get-started/identity) for how that works.

### One identity across your machines

For machines you look after yourself, **master identity mode** gives every device the same identity: each machine's key comes from one root you hold, and a 24-word recovery phrase can rebuild it anywhere. Start a fresh install with:

```bash
spl init --master
```

Choose master mode when you first run `spl init`: an existing per-machine identity can't be switched to it later. (`spl identity upgrade` is different: it moves an existing identity from the `key` method to `web` or `sync`, and the identity stays the same.) Master mode is optional: you can use Syncropel on a single machine without it.

## Permissions

After `spl init`:

```bash
ls -la ~/.syncro/ ~/.syncro/keys/
```

Check that:

- `~/.syncro/config.toml` is never world-writable.
- The private key under `~/.syncro/keys/` is mode `0600`.
- `~/.syncro/token` (once created) is mode `0600`.

The folder itself uses your system's default permissions; the
secrets inside it (keys, tokens) can only be read by you (`0600`). If anything looks
off, `spl doctor` will flag it with the exact `chmod` fix.
