<Callout type="info" title="Updated in v0.65.0 'Welcomed' (ADR-137)">
For first-run on **Linux/macOS**, you no longer need a service account. The local CLI talks to the daemon over the Unix-domain socket at `~/.syncro/run/spl.sock` — filesystem permissions (the socket is mode 0700 owned by your UID) are the authentication, same as Docker, systemd-bus, ssh-agent, and gnupg-agent. The full first run is two commands: `spl init && spl serve --daemon`. See [First run](/docs/get-started/first-run) for the canonical flow.

**You still need a service account when** delegating scoped access to a different principal: a browser via [`spl pair`](/docs/get-started/pairing), a paired phone, an MCP client running with reduced trust, a remote CLI on a different machine, or a federation peer. This page covers those cases.

The old "bootstrap dance" (`spl serve --daemon --insecure-localhost` → `spl service-account create --bootstrap` → `spl token save`) was a workaround for the pre-v0.65 architecture that conflated identity (your keypair) with API auth (bearer tokens). v0.65 separated them. Old scripts that follow that dance still work, but new users don't need it.
</Callout>

## Where service accounts fit (post-v0.65)

| Use case | Recommended path |
|---|---|
| Local CLI on Linux/macOS, talking to local daemon | Unix-socket trust — no SA needed |
| Local CLI on Windows | Use bearer token (Unix sockets work on Win 1803+ but the local-trust path follows in v0.65.1) |
| Browser at `syncropel.com` paired with local daemon | [`spl pair --device browser-<name>`](/docs/get-started/pairing) — mints a scoped browser SA |
| Phone with a scoped session | `spl pair --device phone-<name>` |
| MCP client in sandboxed mode | Scoped SA minted per dispatch (existing pattern) |
| Remote CLI (CI runner, second machine) | Bearer token; copy from `~/.syncro/token` or use `spl pair --device remote-<name>` |
| Federation peer | `spl federation pair <peer-url>` — handshake-based; in v0.65.1 will move to identity-keypair signed challenge per ADR-137 D7 |
| Anonymous web ingest (public form posting to your daemon) | Namespace `write_policy = "anonymous"` — no SA needed; see [exposing your instance](/docs/get-started/exposing) |

## Minting a service account for delegation

Direct path — works on a daemon that's already up. No insecure-mode dance required.

```bash
# Pair a browser (the most common case)
spl pair --device "browser-chrome" --url "http://127.0.0.1:9100" --scopes admin

# Or mint an SA directly with finer control
spl service-account create \
  --name remote-ci \
  --actors did:sync:agent:ci \
  --scopes records:write \
  --with-token
spl token save spl_prod_sa_...   # save under a different SPL_TOKEN env to use as ci's bearer
```

Each pairing produces a bearer token. The token is shown **once** in plaintext; copy it then. Subsequent requests from the paired device include the bearer in the `Authorization: Bearer ...` header.

### Pre-v0.65 bootstrap dance (legacy — only needed in rare edge cases)

If you find yourself on an older daemon (v0.64.x or earlier), or you explicitly disabled Unix-socket trust via `[auth] unix_socket = false`, the original bootstrap flow still works:

```bash
spl serve --daemon --insecure-localhost
spl service-account create --bootstrap --name admin \
  --actors did:sync:user:$(whoami) --scopes admin --with-token
spl token save spl_prod_sa_...
spl serve --stop && spl serve --daemon
```

Upgrade to v0.65+ and you can skip steps 1, 3, and the final restart entirely.

### What each flag does

| Flag | Meaning |
|---|---|
| `--bootstrap` | Routes to the privileged endpoint that works without existing auth. Only succeeds when the namespace has zero service accounts — the "first SA" escape hatch. |
| `--name admin` | Display name for the service account. Purely cosmetic; used in `spl service-account list`. |
| `--actors did:sync:user:$(whoami)` | The DID allowlist for this service account. The token will only succeed when the caller claims to be this actor. For the first account, pass your own DID so the CLI can use this token. |
| `--scopes admin` | Capability grant. `admin` is the superset; narrower scopes cover individual surfaces (see below). |
| `--with-token` | Mint a plaintext token in the same response. Without this flag, the account is created but no token is issued — you'd need `spl token mint` afterwards. |

### If you omit `--actors`

The command will still succeed, but the service account will have no actor allowlist. A token minted against it will not authorize any record writes (the DID claim check will fail on every request). The daemon will start in secure mode, but your CLI won't be able to do anything with it. Recovery: revoke the broken account (`spl service-account revoke <id>`) and redo the bootstrap with `--actors` set correctly.

## Save the token

Step 2's output includes a plaintext token that begins with `spl_prod_sa_`. It is shown **once** — copy it now.

```bash
spl token save spl_prod_sa_XXXXXXXX_YYYYYYYYYYYY
```

This writes `~/.syncro/token` with mode `0600`. Every `spl` command from now on reads that file and injects it as the `Authorization: Bearer` header.

The CLI's token discovery precedence:

1. `--token <value>` — per-command override.
2. `SPL_TOKEN` environment variable — useful in CI.
3. `~/.syncro/token` — the persistent default.

`spl token show-source` reports which source the CLI is currently using, with the token masked.

## The scope system

A closed enum of seven capabilities. Tokens carry a snapshot at issuance time — changes to a service account's scopes don't apply to existing tokens, only to newly minted ones.

| Scope | Grants |
|---|---|
| `records:read` | `GET /v1/records`, `GET /v1/threads/*` |
| `records:write` | `POST /v1/records` |
| `threads:write` | `POST /v1/threads`, `DELETE /v1/threads/{id}` |
| `federation:manage` | All `/v1/sync/*`, `/v1/federation/*`, `/v1/discovery/*` |
| `config:read` | `GET /v1/config/*` |
| `config:write` | `POST /v1/config/*` |
| `admin` | Everything, including service account and token mutations |

Use the narrowest scope that covers the use case. A Grafana dashboard that reads metrics needs `records:read`. A phone client that emits observations needs `records:write`. A federation peer needs `federation:manage`. Only the bootstrap account needs `admin`.

## Creating additional scoped accounts

Once the first account exists and you've saved its token, subsequent accounts are created without the `--bootstrap` flag:

```bash
spl service-account create \
  --name "grafana" \
  --actors did:sync:svc:grafana \
  --scopes records:read \
  --with-token
```

The command uses your admin token to authenticate. The response includes a fresh token for the new account.

## Listing, rotating, revoking service accounts

```bash
# Show every service account and its scopes.
spl service-account list

# Rotate — mint a new token then revoke the old one. Partial-failure-safe:
# if rotation succeeds but old-revoke fails, you have both tokens live.
# Mop up with `spl token revoke` manually.
spl token rotate <sa_id>

# Revoke a single token. The service account survives; other tokens survive.
spl token revoke --sa <sa_id> --token-id <token_id>

# Revoke the entire service account. Every token ever issued is killed;
# no future tokens can be minted for this SA. This is irreversible.
spl service-account revoke <sa_id>
```

### Which revocation to use

| Scenario | Command |
|---|---|
| Scheduled rotation / time-based policy | `spl token rotate <sa_id>` |
| One phone lost; other devices still trusted | `spl token revoke --sa <sa_id> --token-id <token_id>` |
| Laptop stolen; service account keys may be leaked | `spl service-account revoke <sa_id>` |
| Retiring an identity entirely (personnel change, project end) | `spl service-account revoke <sa_id>` |

## Listing tokens and their origins

```bash
spl token list
```

Shows every token issued, with the service account it belongs to, the creation time, and a masked prefix. Useful for auditing which tokens exist and cross-referencing with your device inventory.

## If you lose the bootstrap token

The `--bootstrap` escape hatch only works when the namespace has zero service accounts. Once one exists, the endpoint is closed. If you've lost the bootstrap token but still have shell access to the host:

```bash
spl serve --stop
spl serve --daemon --insecure-localhost
spl service-account list                   # confirm the SA exists
spl token rotate <sa_id>                   # mint a fresh token on the existing SA
spl token save spl_prod_sa_...             # save it
spl serve --stop
spl serve --daemon
```

`--insecure-localhost` bypasses auth on loopback so you can recover.
