This page is for people running their own workspace or using the API. If you use a workspace created at syncropel.com, start with [Your hosted workspace](/docs/get-started/your-hosted-workspace).

<Callout type="info" title="You don't need a service account for a first run on Linux or macOS">
On your own computer the command line connects through a local socket at `~/.syncro/run/spl.sock` that only your user can use, so no token is needed. The full first run is `spl init && spl serve && spl task add "..."`. See [First run](/docs/get-started/first-run).

Service accounts and tokens are for giving **limited access** to something else: a browser, a phone, an AI client you trust less, the command line on another computer, or another workspace you sync with. This page covers those cases.
</Callout>

## Where service accounts fit

| Use case | Recommended path |
|---|---|
| Command line on Linux or macOS, talking to your own workspace | Nothing needed: no service account |
| Command line on Windows | Use a token (create one with the `spl pair` flow below) |
| Browser connected to a workspace on your computer | [`spl pair --device browser-<name>`](/docs/get-started/pairing): creates a limited token for the browser |
| Phone with limited access | `spl pair --device phone-<name>` |
| AI client with reduced access | A limited token created for it |
| Command line on another computer (CI runner, second machine) | Copy the token from `~/.syncro/token` or use `spl pair --device remote-<name>` |
| Syncing with another workspace | `spl federation pair add <peer-url>`: no token copying |
| A public web form that adds records to your workspace | Set the namespace `write_policy = "anonymous"`; see [exposing your workspace](/docs/get-started/exposing) |

## Creating a service account

This works on any running workspace.

```bash
# Pair a browser (the most common case)
spl pair --device "browser-chrome" --url "http://127.0.0.1:9100" --scopes admin

# Or create a service account directly, with more control
spl service-account create \
  --name remote-ci \
  --actors did:sync:agent:ci \
  --scopes records:write \
  --with-token
spl token save spl_prod_sa_...   # to use it as ci's token, set it as SPL_TOKEN instead
```

Each pairing creates a token. The token is shown **once**; copy it then. The paired device sends it in the `Authorization: Bearer ...` header with each request.

### The first account

On a new workspace, the HTTP API answers every request with
`503 BOOTSTRAP_REQUIRED` until the **first** service account exists. Create it
with the commands below. You need this to reach a new workspace over the network (a browser, another computer, or
another workspace):

```bash
spl service-account create --bootstrap --name admin \
  --actors did:sync:user:$(whoami) --scopes admin --with-token
spl token save spl_prod_sa_...
```

These commands work on your own computer against a running workspace, with no
`--insecure-localhost` restart. (The `BOOTSTRAP_REQUIRED` error also prints these commands.)

If you only use the command line on this computer, you can skip this: it needs no token.

### What each flag does

| Flag | Meaning |
|---|---|
| `--bootstrap` | Lets you create an account when none exist yet. It only works when the namespace has no service accounts. |
| `--name admin` | The account's name, shown in `spl service-account list`. |
| `--actors did:sync:user:$(whoami)` | The actors this account may act as. The token only works when the caller says it is one of these actors. For the first account, pass your own identity so the command line can use this token. |
| `--scopes admin` | What the account may do. `admin` allows everything; narrower scopes allow less (see below). |
| `--with-token` | Creates a token at the same time. Without it the account has no token, and you would need `spl token create` afterwards. |

### If you omit `--actors`

The command still succeeds, but the account is not allowed to act as anyone. Its token can't write any records, and the check fails on every request, so your command line can't do anything with it. To fix it, remove the account (`spl service-account revoke <id>`) and create it again with `--actors` set.

## Save the token

The output includes a token that begins with `spl_prod_sa_`. It is shown **once**: copy it now.

```bash
spl token save spl_prod_sa_XXXXXXXX_YYYYYYYYYYYY
```

This writes `~/.syncro/token`, readable only by you. Every `spl` command from now on reads that file and sends the token.

`spl` looks for a token in this order:

1. `--token <value>`: for one command.
2. `SPL_TOKEN` environment variable: useful in automated jobs.
3. `~/.syncro/token`: the default.

`spl token show-source` shows which of these `spl` is using, with the token hidden.

## The scope system

There are seven scopes. A token keeps the scopes it had when it was created: changing an account's scopes affects only new tokens.

| Scope | Grants |
|---|---|
| `records:read` | `GET /v1/records`, `GET /v1/threads/*` |
| `records:write` | `POST /v1/records` |
| `threads:write` | `POST /v1/threads`, `DELETE /v1/threads/{id}` |
| `federation:manage` | All `/v1/sync/*`, `/v1/federation/*`, `/v1/discovery/*` |
| `config:read` | `GET /v1/config/*` |
| `config:write` | `POST /v1/config/*` |
| `admin` | Everything, including service account and token mutations |

Give each token the smallest scope that does the job. A Grafana dashboard that reads metrics needs `records:read`. A phone app that adds observations needs `records:write`. Another workspace needs `federation:manage`. Only the first account needs `admin`.

## Creating additional scoped accounts

Once the first account exists and you've saved its token, create further accounts without `--bootstrap`:

```bash
spl service-account create \
  --name "grafana" \
  --actors did:sync:svc:grafana \
  --scopes records:read \
  --with-token
```

The command uses your admin token. The response includes a new token for the new account.

## Listing, replacing and removing accounts and tokens

```bash
# Show every service account and its scopes.
spl service-account list

# Replace a token: create a new one, then cancel the old one.
# If the old one can't be cancelled, both work until you run
# `spl token revoke` yourself.
spl token rotate <sa_id>

# Cancel one token. The account and its other tokens stay.
spl token revoke --sa <sa_id> --token-id <token_id>

# Remove the whole account. Every token it ever had stops working,
# and no new ones can be created. This cannot be undone.
spl service-account revoke <sa_id>
```

### Which one to use

| Scenario | Command |
|---|---|
| Regular replacement of tokens | `spl token rotate <sa_id>` |
| One phone lost; other devices still trusted | `spl token revoke --sa <sa_id> --token-id <token_id>` |
| Laptop stolen; the account's tokens may have leaked | `spl service-account revoke <sa_id>` |
| Retiring an account entirely (someone leaves, a project ends) | `spl service-account revoke <sa_id>` |

## Listing tokens and their origins

```bash
spl token list
```

Shows every token, with its service account, when it was created, and the start of the token. Use it to check which tokens exist against the devices you own.

### What a listed account and a listed token say

`GET /v1/service-accounts` returns a `class` for each account: `admin` (the first account on a hosted workspace), `run` (created for one job), `device` (a paired browser), `invite` (someone you invited) or `custom` (anything you created). `run` accounts are left out unless you add `?include_runs=true`, so a workspace that has run many jobs doesn't bury your real accounts.

`GET /v1/tokens` returns `expires_at` for each token, which is `null` when the token never expires, and `label`, the name given when it was created.

`POST /v1/tokens` accepts two optional fields beside `sa_id`:

| Field | Meaning |
|---|---|
| `expires_days` | Days until the token expires, from 1 to 365. Other values are refused with `EXPIRY_OUT_OF_RANGE`. Leave it out for no expiry. |
| `label` | A name for the token ("laptop", "the console"), up to 80 characters, with no control characters. Otherwise refused with `LABEL_INVALID`. |

Both are checked first, so a refused request creates nothing.

## If you lose the bootstrap token

`--bootstrap` only works when no service accounts exist. Once one exists, it is closed. If you've lost the first token but can still log in to the computer:

```bash
spl stop
spl serve --insecure-localhost
spl service-account list                   # check the account exists
spl token rotate <sa_id>                   # create a new token on the existing account
spl token save spl_prod_sa_...             # save it
spl stop
spl serve
```

`--insecure-localhost` turns sign-in off on your own computer so you can recover.
